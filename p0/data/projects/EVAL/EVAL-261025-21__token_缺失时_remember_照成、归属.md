# token 缺失时 remember 照成、归属永久错、无修正通道（一次性失误=永久脏数据）

> 编码：EVAL-261025-21 ｜ 类型：lesson ｜ 记录于 2026-10-25T13:00:34Z

## ① 症状（可复现）

凭证缺失/失效时，`remember` **照常写入成功**，只在回执尾部追加一句提示；而归属一旦落成 `unattributed`，**事后无法修正**。

**复现步骤**

1. 不带 `token` 调 `remember(project="EVAL", title="…")`。
2. 回执：
   ```
   EVAL-261025-19
   projects/EVAL/EVAL-261025-19__…md
   ⚠ 本次调用未带会话凭证，归属记为“未归属”（unattributed）。
   ```
   写入成功，记忆已落盘。
3. 服务端审计 `data/_audit/tool-calls.jsonl` 对应行：
   ```
   {"ts":"2026-10-25T20:58:34+08:00","actor":null,"actor_registered":false,
    "session_actor":null,"identity_status":"none","evidence":null,
    "kind":"tool","name":"remember","ok":true}
   ```
4. 试图修正：`supersede` 只能生成**新的编码**并标记旧条为 superseded，**不改 `owner`**。没有工具能改一条已有记忆的归属。

**为什么会发生**（部分未验证）：同会话另 3 次带 token 的调用（`whoami`×2、`remember`×1）归属全部正确，事件本身**未能复现**。服务端只能看到“没收到”，看不到“为什么没收到”。**是客户端未传还是传输层丢失，未验证。**

## ② 影响

- **一次性失误造成永久脏数据**。这是个瞬时故障（一行参数没带上），代价却是该条记忆千秋万代挂在 `unattributed` 名下。而「这是谁写的」恰好是 fish 最在意的属性——`ERR/EVAL` 体系、`resolve_owner` 的吃狗粮事故、2026-10-23 串号事故都指向同一件事。
- **写入与归属错开报错，人容易只看到前半**。回执第一行是成功编码，提示在最末，且格式上是“提醒”而非“错误”。看到 `EVAL-261025-19` 就往下走是自然行为。
- **无法审计“有多少条历史记忆其实是错归属的”**：`unattributed` 既可能是“当时确实没身份”（合理），也可能是“当时丢了 token”（不合理），两种含义混在一个值里，无法区分。这与 `code_index.owner` 用 `'unattributed'` 而不用 NULL 的理由（“同一个 NULL 两种含义 = 审计毒药”）是同一个坑的反向版本。
- 修复代价：只能重新写一条（占用新编码，污染编码序列）+ supersede 旧条，且旧条仍以 `unattributed` 存在。

## ③ 建议

1. **给归属一个事后修正通道**：例如 `remember --fix-owner <code> --citizen <id>`（需主人或该公民本人在场），或扩展现有 `supersede` 支持 `new_owner`。只修 owner、不动正文，风险低于复写。
2. **把归属状态提升到回执第一行**，例如 `EVAL-261025-19（归属：未归属 ⚠）`，而不是编码一行、警告末一行。
3. **区分两种 unattributed**：写入时若数据库里**存在该会话的有效 token** 但本次没收到 → 记 `unattributed?`（可疑，可能是丢参）；若确实从未签发 → 记 `unattributed`（正常）。前一种是真缺陷，值得能被筛出来。
4. （可选）`remember` 在写入前若检测到**同会话有历史 token 记录**而本次未带，返回前弹一次确认——类似查重提示的“写入后提示”模式，不阻断只标记。
