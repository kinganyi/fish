# 看板裁剪顺序与自己的注释理由矛盾：注释说「看板应比错题本/规矩活得久」，代码却先裁看板

> 编码：EVAL-261025-15 ｜ 类型：lesson ｜ 记录于 2026-10-25T11:16:25Z

### ① 症状

`fish.py:6099-6120` 的裁剪链，代码实际顺序是：

```
注意事项 → 看板 → 错题本 → 规矩 → L1条目 → L0铁律
```

也就是“谁活得久”：`规矩 > 错题本 > 看板 > 注意事项`。

但紧上方自己的注释（`fish.py:6106-6108`）写的是：

> 更硬的理由：**它只值 150-200 token**，裁它省不下多少，却裁掉了**时效性最强**的那块。
> 而**注意事项/错题本/规矩都可以离线查回来**（recall / 注入包下一次就有）。

按这段注释，看板应该比“注意事项/错题本/规矩”三者都活得久。实际只比注意事项久，仍然先于错题本与规矩被裁。

### ② 影响

- 这是 EVAL-261025-11 的**部分采纳**：主诉（不该排在注意事项之前）已改，但改后的顺序与自己的理由对不上。
- 按注释的理由推，预紧时反而保住了可离线查的错题本/规矩，丢掉了不可重建的“此刻”。**同一份文件里现在有两种自相矛盾的排序依据**。
- 量级不大（后两位的裁量差），但 fish 自己有一份《实现与规格偏离对账》——**新功能在注释里就先欠了一笔**，这正是那份对账要防的事。

### ③ 建议

二选一，不要两边都留着：

1. **按注释调**：把 `board_text` 的裁剪挪到 `rules_text` 之后（变成 `注意事项 → 错题本 → 规矩 → 看板`）。
2. **按代码改注释**：把那句改成“看板排在注意事项之后（注意事项是当下最可能救命的那条），但仍先于错题本/规矩——因为后两者是长期沉淀，不该为 150 token 让步”。

顺带：这个顺序建议加一个断言测试（如 `test_board.py` 里断言裁剪 `trimmed` 列表的顺序），否则下次重构随时会再漂。
