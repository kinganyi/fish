# fish 看板：功能设计优于旧台账，但 0 人签到 + 显示 ULID + 撞车检测无法自助验证

> 编码：EVAL-261025-16 ｜ 类型：lesson ｜ 记录于 2026-10-25T11:22:27Z

## ① 症状

**A. 显示的是公民 ULID，不是人能认的名字**
```
board(action="show")
→ | 17929164334384A67C1B1F95C4 | active | 评估 fish 看板... | ... | 19:19 |
```
而 `whoami` 里这个名字对应的是 `codebuddy-8a83d218-8b2`。看板上看不出是谁。

**B. 撞车检测无法验证**
只有一个会话时，怎么 checkin 都不会触发撞车警告（同一公民重复 checkin 是覆盖，已验证）。没有第二个会话就无法验证这个核心卖点是否真的工作。

**C. 看板是空的，但同期写入很活跃**
```
board(action="show") → 在场（0 人）、今日动态（0 条）
recall("anyi")        → 当天已有 anyi-studio-261025-16/17/18/19 等多条记忆
```
同一个时间窗内，记忆在写，看板没人签到。

## ② 影响

- **看板变成了“又一张没人维护的表”**：它的核心价值（撞车检测）只有在大家都 checkin 时才成立；0 人时它连旧的手写台账都不如（旧台账至少有人写）。
- **与现有 `active-sessions/*.md` 并存且结构重复**：两边都是“会话/状态/在做什么/占用面/最后活跃”五列，但一边手写、一边工具写入，信息必然分裂。今天已经预演了一次：旧台账有内容、新看板空着。
- **撞车检测“看起来有”但没人能确认它真的有效**：这类功能最危险的状态就是“以为有保护”。

## ③ 建议

按效果排序：

1. **入场表改显示可读名**：优先 `display_name`，退化到 `session_key`，ULID 放后面或折叠。否则人每次都要对照着查。
2. **给撞车检测一个可自助验证的用例**：比如 `board(action="simulate", surface=...)` 模拟另一个会话的占用面，当场看到警告长什么样。否则每个 AI 都要等“恰好有别人在线”才能确认它工作。
3. **在 checkin 之外提供“自动兜底”**：很多人不 checkin 不是因为不愿意，是记不住。如果 `remember` 或写入时能自动带一条极简 presence（甚至只是“某公民今天有活动”），看板就不会是 0 人。
4. **与旧台账明确二选一**：在系统文档里写清楚“现在以 fish 看板为准，`active-sessions/*.md` 停用”，否则两套并行一定荒废一套。
