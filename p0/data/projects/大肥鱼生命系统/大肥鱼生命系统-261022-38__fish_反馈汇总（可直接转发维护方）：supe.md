## 一、影响使用的问题（2 条）

### 1. `supersede` 对已替代条目回显**入参**，不是库内实际替代者

**复现**：对已 superseded 的 `anyi-studio-261022-13` 再调：
```
supersede(code="anyi-studio-261022-13", by="大肥鱼生命系统-261022-33", reason="...")
```

**返回**：
```
anyi-studio-261022-13 已经是 superseded（被 大肥鱼生命系统-261022-33 替代过）
```

**实际**：紧接 `resolve_code("anyi-studio-261022-13")` 显示：
```
- 状态：superseded
- ⚠ 已被 大肥鱼生命系统-261022-10 替代
```

替代者是 `大肥鱼生命系统-261022-10`（另一会话先做的），**不是入参里的 `大肥鱼生命系统-261022-33`**。

**后果**：多会话并发时，后到者得到“假成功”，误以为自己成了权威版本。

**期望**：返回报**实际替代者**；并明确区分「本次生效」与「已是 superseded，本次未生效」；若不允许改替代者，直接报错而非假成功。

---

### 2. `register` 的 `session_name` 绑定**不是每次都生效**

**完整时序（同一会话）**：
| 时间 | 动作 | 结果 |
|---|---|---|
| 06:55 | `register(session_name=...)` | 返回**无**会话名（旧版） |
| 07:10 | 再调一次 | 返回**有**「会话 anyi-studio-开发AI-2」 |
| 07:18 | `remember` | ⚠ 提示「本会话未设 session_name」→ **前两次没绑上** |
| 07:20 | `register`（多传了 `role`） | 返回有会话名 |
| 07:23 | `remember` | ✅ 返回尾部带「，会话 anyi-studio-开发AI-2」→ **绑上了** |

**后果**：调用方会以为已绑定（我就这么以为了，并向用户报告“已确认落库”），但那段期间的写入全部丢归属。

**期望**：要么真的每次绑定并告知「已更新」，要么如实报「未绑定」；**不要回显入参**。

## 二、一个需要修正的说法

### 3. 「修复只在新会话生效」在 WorkBuddy 宿主上**不成立**

**实测**：两次 `ToolSearch`，同一会话、相隔 14 分钟：

| 时间 | `read_body` | `add_project` | `supersede` |
|---|---|---|---|
| 06:55 | ✅ | ❌ | ❌ |
| 07:10 | ✅ | **✅** | **✅** |

工具表**热更了**，会话没重开。若按“必须重开会话”告知用户，会让人白等一轮。

**建议措辞**：「工具表通常热更；若 5~10 分钟后仍未出现，再重开会话」。

## 三、一个共性建议（比单条修复更值）

上面 1、2 是**同一个模式**：**返回的是入参/意图，不是库内状态**。

建议在 `remember` 的返回里**固定输出归属行**（无论是否绑定），例如：
```
anyi-studio-261022-37
projects/ANYI/anyi-studio-261022-37.md，会话 anyi-studio-开发AI-2
```
它是写入的**终点**，最能反映真实状态。调用方每写一条就能核对一次，不必靠猜或靠下一笔验证。

同理，`supersede` / `register` 这类会改变状态的操作，返回应以**改后状态**为准，而不是回显入参。
