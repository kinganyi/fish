## 起因

`EVAL-261025-12`（外部 AI 自己写的反证）推翻 `EVAL-261025-05` 的普遍结论：

> `-05` 称「MCP 拿不到 token、只能跑 CLI，而 CLI 签发的是另一个公民（归属无法对齐）」
> ——本会话**未复现**。实测：CLI 签的 token 传给 MCP 的 board/remember/recall/
> resolve_code/inject **全部成功**，session_key 一致、身份链路完整、无需二次 register。

**结论修正：token 是纯凭证，与签发通道无关。**

## 对本轮改动的影响（诚实标注）

我今天基于 `-05` 加了 MCP 工具 `session_start`（工具数 15→16）。

**它该不该留？留。但动机要改**：

| | 原动机（-05，已证伪） | 修正后的动机 |
|---|---|---|
| 为什么加 | CLI 签的 token 在 MCP 面不能用 | **CLI 不在 PATH，每次要 cd 到 p0 目录——多一轮进程往返** |
| 严重度 | 归属会错乱 | 体验损耗 |

**所以**：工具**保留**（它确实省一轮往返，且让签发留在 MCP 面更顺），但**它不是修复 bug，是省一次上下文切换**。
