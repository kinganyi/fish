# 数据迁移的八个坑：LIKE大小写/自建正则/FTS绕过fts_text/演练七轮才全绿

> 编码：anyi-studio-261025-17 ｜ 类型：lesson ｜ 记录于 2026-10-24T20:26:22Z

## 背景

迁移 204 条记忆、重写 309 处正文引用。**七次副本演练抓出 8 个真 bug**，每一个都会在生产上留下静默损伤。

## 八个 bug（按发现顺序）

| # | Bug | 后果 |
|---|---|---|
| 1 | **SQLite `LIKE` 对 ASCII 大小写不敏感** | `'anyi-studio-*' LIKE 'ANYI-%'` 为真 → 把迁好的 96 条误报成"残留" |
| 2 | 旧目录未归档 | 152 个孤儿 + 688 处引用"不可解析" |
| 3 | 企业智能撞号 | `ANYI-261022-03` 与 `企业智能-261022-03` 同落一个编码 → 后者被跳过，混杂没清掉 |
| 4 | 校验用自建正则 | 中文"编码："被吃进前缀 → 376 处**本来能解析**的引用被误判 |
| 5 | 判据只认 `status='active'` | 已被标 superseded 的条目，其引用被判"不可解析"（设计如此，判据错了） |
| 6 | **`\w` 在 Python 里含中文** | `(?<![\w-])` 挡住"补企业智能-…"，替换失效 |
| 7 | 只扫了 ANYI 目录 | 企业智能正文里的 `ANYI-*` 引用没替换 |
| 8 | **FTS 重建绕过 `fts_text`** | 自己 INSERT 存原文 → **全文检索整个失效**（相似度 0.93→0.02），而七项校验全绿 |

## 三条结构性问题（比单个 bug 重要）

### ① 「校验判据」本身需要被校验

九项校验里**前三版都是错的**（1、4、5）。它们"看起来在检查"，实际要么误报要么漏报。
而第 8 条（FTS）**根本没被覆盖**——"七项全绿"和"检索已坏"同时成立。

→ **迁移脚本的校验，必须先在已知错误的数据上验证它会红。**

### ② 「绕过应用自己的函数」是最容易犯的错

三次：正则、FTS 索引、状态过滤。**每次都发生在"写工具脚本"时**——因为工具脚本天然想"简单点自己实现"。

→ **任何数据操作脚本，涉及解析/索引/过滤的地方，必须调用应用自己的函数。**
这是 D2 纪律（"禁用自建模型代替应用的判定函数"）的真正适用范围——它不只在测试里，**在工具脚本里更容易被违反**。

### ③ 「演练」的价值远大于「仔细检查」

七轮演练，**每一轮都抓到新 bug**；"仔细读代码"一次一个都没抓到。

→ 重大数据操作的正确姿势不是"想清楚再动手"，是**"在副本上跑到全绿"**。
每一轮失败都是一次真实损伤的提前暴露。

## 可复用的做法

1. **`--data-root` 参数**：所有数据操作脚本都该支持指向副本，这是演练的前提。
2. **单事务 + 校验失败自动 ROLLBACK**：校验不过就不提交，比"提交后再修"安全一个数量级。
3. **旧数据归档不删**：`projects/_retired-ANYI-20261025` 保留 150 个旧文件，校验时跳过（下划线开头）。
4. **改名前先确认前缀能不能被正则解析**：`anyi-studio` 含连字符，旧正则返回 None——先用 `test_code_prefix` 验，再动手。
