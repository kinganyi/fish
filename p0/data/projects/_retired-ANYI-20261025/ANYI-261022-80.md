# fish 反馈：跨项目共享规范被各自重写一份，且无 project 过滤 → 规则会分叉

> 编码：ANYI-261022-80 ｜ 类型：lesson ｜ 记录于 2026-10-22T05:45:07Z

**具体场景**：今天两个会话同时在做「把工作空间规则迁入 fish」这件事。我（`ANYI` 前缀）刚写入 `ANYI-261022-75` 包含 **CR-1~CR-15 全文**；回头一查，发现 `企业智能` 前缀下已有 `企业智能-261022-05`（协作铁律·行为层 CR-2/5/6/7/11）与 `企业智能-261022-06`（引用与验证纪律 CR-12/CR-14）。

**卡在哪**：CR / ER 是**跨项目共享的规范**，但现在被每个项目各自迁一遍。后果是：
1. 同一规则存在 **N 份，措辞可能不一致**，没有任何机制说明哪份权威；
2. `recall` **没有 `project` 过滤**（D-5）⇒ 搜 `CR-12` 会同时返回两份，AI 无法判断听谁的；
3. 将来规则一改，要改 N 处——这恰好是任何共享知识库最经典的屎山形成路径。

**期望**（按改动量从小到大）：
1. **最小**：`recall` 补 `project?` 参数时，顺便在回包里标出「同题异项目」的条目（“另有 `企业智能-xxx` 同题”），至少让 AI 知道有分歧；
2. **推荐**：允许一个 **共享前缀**（如 `SHR` / `COMMON`）专门存跨项目规范；各项目条目只存**指针**（`links` 指向共享条），不存副本；
3. **规范层**：在 `02` 里补一条「共享规则不得在项目内重写，只能引用」的写入纪律，否则每个人都会“顺手再写一遍”。

**补充证据（同日实测）**：我用只在**正文**出现的词 `pkill`（`ANYI-261022-74` 的 ER-27 反例）做召回，返回 **0 条**——标题里没有就不命中。这与「以后要存正文、存一切」的需求直接冲突：**存进去但搜不到，等于没存。**
