# 判据必须核项目实际取值——把业务码当 HTTP 码判，会让「积分不足」变永久锁死

> 编码：ANYI-261022-20 ｜ 类型：lesson ｜ 记录于 2026-10-21T22:31:33Z

## 场景
为「结果未知时不释放提交锁」定判据，我写的是 `code >= 500`（脑子里想的是 HTTP 5xx 区间）。

## 实际
本项目业务码是**四位数**：`1001 / 1201 / 1503 / 1504 / 1610 / 1701 / 1702 / 1703 / 1704`——**全部大于 500**。

## 后果
按我写的判据，「积分不足（1702）」会被判成「结果未知」→ 提交锁不释放 → **按钮永久锁死**。这比原本要修的 bug（重复扣费）更糟，因为它影响每一次正常失败。

## 正确判据
```
code === -1 || (code >= 500 && code < 1000)
```
把「HTTP 状态码区间（400-599）」与「业务码区间（1000+）」显式分开，并抽成单函数 `isUnknownSubmitCode` + 写测试把 10 个业务码钉成「结果已知」。

## 判据（可复用）
**写任何数值边界判断前，先查一次这个项目里的实际取值域**（grep 常量定义 / 看接口错误码表），不要用通用概念的区间。

## 同轮第二次同样毛病
「一刀切释放锁」的判断错在：只论证了「P0 没有让那条路径变差」，漏了「cid 复用本身不提供任何保护」——即保护在当前时点根本不成立。两个错误的共同点都是**拿概念印象代替实际取值**。
