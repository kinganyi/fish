# 双键不是多站点的保障，users.tenant_id NOT NULL 才是多站点的枷锁

> 编码：ANYI-261022-111 ｜ 类型：lesson ｜ 记录于 2026-10-22T09:43:23Z

【错误论断】我曾断言「合并成一个 UID = 放弃多站点，这是产品前提不可动」。安逸 2026-10-22 推翻：「合并不意味着放弃多站点，只是意味着需要更正确的架构。用户只有一套 UID 就可以……这些大量页面里的问题之所以存在，就是因为 AI 有时候也搞不懂，这是命门」。

【为什么我错了】只看了 users 表就下结论，没查系统里是否已有表达「用户×站点」的表。

【复核证据】
1) users.tenant_id 是 NOT NULL（PRAGMA table_info 实测）→ 一行只能挂一个租户 = 单站点物理锁。多站点从来不是 users 提供的。
2) tenant_members 10 列，身份×租户 1:N，且早已承载核心逻辑：config.py:250（JWT v2 去 role，二次查 tenant_members）、middleware/auth.py:237（决策 7）、access_scope.py:7、credit_service.py:283（额度扣减）、site_users.py:80（花名册）、identity_service.py:199/220、site_inbound.py:206/321。
3) users 14 列 = 9 复制 + 5 独有。复制：username/password_hash/display_name/role/is_active/created_at/last_login_at/tenant_id/id。独有：phone/email/must_change_password/source（属「人」→ identity_accounts）、team_id（属「站点内」→ tenant_members）。无任何一列需要 users 才能表达。

【正确因果】双键不是多站点的保障，双键才是多站点的障碍。users 是纯冗余旧主表，也是两套 id 空间之间唯一一座「无外键、靠 username 字符串」的桥 → AI 搞不懂的物理根源。

【迁移正解】不是「加一个 identity_id 外键」（那只是给双键加绳子），而是①补列②消灭第二条序列（users.id 重编号成 identity id + 33 个外键列同步，生产仅 43 行、41 已相等）③users 降级为兼容视图 → 写侧改造 → 下线。视图只在「一身份一站一行」时成立，是过渡脚手架非终态。

【代价实测】FROM/JOIN users 生产 26 文件 60 处（含测试全仓 120 处）；指向 users.id 风格外键 33 列/31 表。
