## §2 🔴 A：本轮唯一的实质风险

### 2.1 风险是什么

`004_rls_pilot.sql:10` 原文：

> **RLS 对表 owner 不生效**——应用连接必须用非 owner 角色 `anyi_app`

缺陷 #5 的修法是 `SECURITY DEFINER` 函数：以**函数属主**身份读 `orders`，从而绕过 RLS 拿到跨站合计。

**它成立的前提是：函数属主 = `orders` 表的 owner（或该角色带 BYPASSRLS）。**

- 053 由 `anyi_migrator` 执行 → 函数属主是 `anyi_migrator`；
- 若 `orders` 的 owner 也是 `anyi_migrator` → ✅ 绕过成功；
- **若 `orders` 的 owner 是别人（如 postgres / anyi_owner）→ 函数以非 owner 身份执行，RLS 照常生效 → 返回的仍是"本站合计" → 修复静默失效，缺陷 #5 原样复现。**

文档 §五 已自认"**PG 形态未验证**"，§七 的验收又只查对象存在（`pg_proc`/`pg_indexes`/`information_schema.columns` 三个计数）。**这两件事叠加，正好把唯一的实质风险漏掉了。**

### 2.2 补一条行为断言（可直接抄进 §七 第 1 步）

文档自己给了生产实测数据，正好当期望值：

> team1：t1 = 670.2091、t9 = 74.2543

```sql
-- 在租户会话内跑（模拟 t9 的请求）
BEGIN;
SELECT set_config('app.current_tenant', '9', true);
SELECT team_consumed_total(<team1_id>);
--  ✅ 期望 ≈ 744.4634（670.2091 + 74.2543）
--  ❌ 若返回 ≈ 74.2543 → 函数没绕过 RLS，本修复失效，现场回滚
ROLLBACK;
```

再加一条属主断言，直接定位原因：

```sql
SELECT p.proowner::regrole AS func_owner,
       c.relowner::regrole  AS table_owner,
       p.proowner = c.relowner AS same_owner
FROM pg_proc p, pg_class c
WHERE p.proname = 'team_consumed_total' AND c.relname = 'orders';
```

> **`same_owner = false` 就是本修复失效的充要条件。** 修法：`ALTER FUNCTION ... OWNER TO <orders owner>`。

### 2.3 为什么必须卡在部署前

它不是"测不出来就算了"——**PL/pgSQL 不会报错**，函数照常返回数字，只是数字错。表现就是"团队额度各站点还是不一样"，然后大家会去查别的地方。
