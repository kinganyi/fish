## 一、余额恒 510 —— 真缺陷，已修上线

### 1.1 你猜的方向对，但机制不是"取错账户"

我们核到了根因：**系统里并存两套积分主体键**，`task.validate` 读的是**已经停更的那一套**。

| 主体键 | balance | total_earned | total_spent | updated_at | 性质 |
|---|---|---|---|---|---|
| `users.id = 7`（你的 users 行） | **510** | 1210 | 700 | **10-17** | 任务所有者键 → **早已停更** |
| `identity_accounts.id = 6`（你的平台身份） | **0** | 2250 | 2224 | **10-22 16:06** | **资金主体键** → 真实余额 |

下面那行与 `GET /api/points` 返回的 `balance:0 / total_earned:2250 / total_spent:2224` **完全一致**。

- `task.validate` 旧实现：`users.id(7)` → 读 510（死账户）
- 扣费链 `task_manager`：走 `money_subject_key_for()` 收敛到 `identity(6)` → 扣的是真账户

**所以是「看着 510、扣的是另一本账」。** 它不是与 `paid_*` 同源（那个是**租户**取错，这个是**主体键**取错），但确实属于同一类"取错了键"。

### 1.2 修法

抽出 `_balance_points_for(principal)`：`users.id` 定位档案 → `money_subject_key_for()` 收敛 → `get_account()`。
与扣费链用**同一个收敛入口**，保证"看到的就是要扣的"。

### 1.3 真机验收（同一份数据，修复前后）

```jsonc
// 修复前
{"estimate": {"balance_points": 510}}

// 修复后（2026-10-22 16:45，身份 dayong）
{
  "valid": true,
  "warnings": ["积分为 0——提交可能被计费闸门拒绝"],
  "estimate": {"balance_points": 0}
}
```

不只数字变了，**警告也正确触发**——这才是护栏该有的样子。

部署：单文件热修，PID `1013378` → `1018355`，停机约 20 秒，双域 health 200，traceback 0。
nginx 回执：`16:45:38 POST /mcp/ 200 497`。

## 二、渠道降级与价差 —— 设计行为，口径在此正式裁定

### 2.1 先把事实钉住：notoken 不是"你的选择"

你写「CLI 提交时能指定渠道（传渠道 model_id），落到 notoken 是我们的选择」——**这一条不成立**。

生产 `generations.route_attempts` 完整记录了过程。你标记为 notoken 的 `393-4`：

```
idx1  apimodels-seedance-2.5-global  → skipped（params_incompatible）
idx1  hcatom-seedance-2.5            → failed  [1311] HC-ATOM API 错误: 用户余额不足
idx2  notoken-seedance-2.5           → success（cgt-20261020202847-vG9as）
```

另一笔：

```
idx1  hcatom   → failed  [1313] HC-ATOM 视频下载失败
idx2  notoken  → success
```

**是 hcatom 失败后的自动降级。** 而且 `align_submission_model` 在 `task_manager` 里对 `/api/tasks` 同样生效——
**CLI 也指定不了路由内的渠道**，只有"不属于任何启用路由"的模型才会原样透传。

所以"用 hcatom 省钱"这个策略在你当前的调用方式下**无法保证**，因为它取决于上游当时是否可用。

### 2.2 价差是真的，数字给你

生产实测（720p，按 duration 加权，`orders.balance_delta / duration`）：

| 渠道 | 样本 | 单价 | 30s 单片 |
|---|---|---|---|
| hcatom-seedance-2.5 | 65 条 | **¥1.2680/s** | ¥38.04 |
| notoken-seedance-2.5 | 48 条 | **¥1.3662/s** | ¥41.04 |
| apimodels-seedance-2.5 | 5 条 | **¥1.8333/s** | ¥55.00 |

你算的 **+7.9%** 是对的（1.3662 / 1.2680 = 1.077）。

### 2.3 ⚖️ 站长方裁定（原文口径，可直接执行）

> **不调价、不做补偿、不统一售价。**
>
> 一般用户本来就该以**我们最终返回的金额/余额**为准；
> 预估只是参考，不构成结算承诺。

具体到你的对账口径，三条：

1. **`task.validate` 的 `estimate` 是"预估"，不是"应付"。**
   它的候选解析用的是"当前首位可用候选"，降级后实际执行的是另一个候选，价格可能不同。
2. **结算以 `task.get` 返回的为准**：
   - `paid_points` — 实付积分（全角色可见，**推荐主口径**）
   - `paid_cny` — 实付人民币（你的 `tenant_admin` 角色可见）
3. **不要用预估做预算承诺或客户报价**；预算按实付累计。

### 2.4 为什么你会特别在意这件事（我们的观察）

你是 `tenant_admin`（`money_visible: true`、`channel_visible: true`），**同时能看到渠道名和金额**，
所以"同一公开码两个价"这件事在你这里显形了。

普通用户看不到渠道名、也看不到金额，只看积分——
对他们来说就是"这次扣了多少积分"，没有"为什么比上次贵"的对照面。

换句话说：**这个困惑是权限带来的，不是系统错**。但你的对账需求是合理的，所以口径必须写清（§2.3）。

### 2.5 如果你想让渠道可预期，仍有两条路（不是调价）

| 方案 | 做法 | 谁受益 |
|---|---|---|
| **A · 建独立公开码路由** | 如 `seedance2.5-eco → ["hcatom-seedance-2.5"]` 单候选锁死 | 你能"选便宜线路"，但 hcatom 挂了会**直接失败**而不是降级 |
| B · 平台调候选顺序 | 把 hcatom 固定排首位 | 全局生效，所有租户 |

你上一轮已判断"暂不申请方案 B"——我们同意。若你后面想让"降级就失败、不要悄悄换贵线路"，A 值得试。

>
> 你们已经自行改到 `paid_cny`，处理正确。
