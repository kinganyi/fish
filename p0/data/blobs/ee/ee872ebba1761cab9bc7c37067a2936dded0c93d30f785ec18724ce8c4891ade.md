## 一、反馈 1：`paid_*` 全 null —— 真缺陷，已修并部署

### 1.1 先证实：数据在，是你的数据没错

生产库直接查你点名的那个单：

```sql
SELECT id, status, point_delta, balance_delta, tenant_id
FROM orders WHERE generation_id = 'task_20261020_202839_520fc12b';

→ order_task_20261020_202839_520fc12b | completed | point_delta=13 | balance_delta=12.3039 | tenant_id=1
```

`13` 积分、`¥12.3039` —— 和你们 CLI 侧对账完全一致。**订单行一直都在。**

### 1.2 根因：查的是 `tenant_id = 0`

```python
# 旧实现（capabilities.py，task.get）
get_paid_for_task(int(getattr(principal, "tenant_id", 0) or 0), task_id)
```

`principal.tenant_id` 的语义是 **key 绑定租户**（`services/platform_gate/auth.py:107` 注释原文：
「`tenant_id` = **key 绑定租户**（None = 用户级 key），语义**永不改写**」）。

你的 key 是**用户级**（`api_keys.tenant_id IS NULL`）→ `tenant_id` 是 `None` → `int(None or 0)` = **0**
→ `WHERE tenant_id = 0` → 一行都查不到 → 返回 `(None, None)`。

**静默错**：不报错、只是没有值。这比 500 更难发现。

### 1.3 修法 + 真机回执

新增 `_data_tenant_id(principal)`：取 `effective_tenant_id`（= 成员关系解析出的有效租户 `1`），
回落 key 绑定租户，最后 0。`task.get` 的 `paid_*` 改用它。

**部署**（2026-10-22 14:01，单文件热修，停机约 20 秒）：
后端 PID `1006381` → **`1013378`**，NRestarts=0，三域 health 200，traceback 0。

**真机验证**（HTTPS → nginx → 应用 → DB，用你的那个单）：

```json
{
  "task_id": "task_20261020_202839_520fc12b",
  "status": "completed",
  "paid_points": 13,
  "paid_cny": 12.3039,
  "model_id": "notoken-seedance-2.5",
  "display_code": "seedance2.5",
  "cost_actual": null
}
```

三源回执：① 上面这段 JSON；② nginx `14:01:16 POST /mcp/ 200 674`；③ DB 订单行（§1.1）。

**回归防护**：新增 4 条用例，其中一条是**接线断言**（抓 `get_paid_for_task` 的入参，断言传 1 不是 0）。
反证：把调用改回旧写法，**只有那条变红**（1F/3P），还原后 4P。

### 1.4 关于 `cost_actual` 仍然是 null

这条**不是缺陷**，是设计：
`cost_actual` 在隐私投影的 `TIER_NEVER_NULL` 里——**任何角色**保留键、值置 `null`。
理由：它的语义是**上游成本**（我们付给供货方的钱），不是用户付的钱；同时暴露成本等于暴露毛利。

你如果确实需要它，我们可以单独开一条「平台管理员」通道，但那等于把上游成本给你，需要商业层决定。

## 二、反馈 2：是我写错了，正式更正

v2.0 原文：

> 「`paid_cny` 仅 `tenant_admin`/`platform_admin` 可见 → **你的 key 是 user 级，拿不到**」

**这句话两处都不准确**，你的实测是对的：

| 项 | 实际值 | 证据 |
|---|---|---|
| 你的成员角色 | `admin`（`tenant_members.member_role`） | 生产库查询 |
| 你的 MCP 角色 | `tenant_admin` | `platform.identity` 实测 |
| `money_visible` | `true` | 同上 |
| `paid_cny` 是否对角色可见 | **是**（`TIER_MONEY_DROP` 只对 `user` 删键，管理员保留） | `privacy_projection.py:96-100` |

这两件事在系统里是**正交**的——key 的租户绑定决定数据面上下文，成员关系决定角色视图。我把两句话混成了一句。

所以：**你的金额本该可见**，null 纯粹是 §1 那个租户取错。已随 1.3 一起修好。

## 三、反馈 3：渠道不能指定 —— 设计如此，但我把机制说清楚

### 3.1 为什么三种写法都落到 hcatom

提交时的对齐函数 `align_submission_model`（`services/model_route_service.py:361`）按四步走：

```
① 空值                                    → 原样
② 值不是任何已知内部 model_id             → 当作公开码 display_code 解析成内部 id
③ 该 model_id 不属于任何【启用】路由       → 原样透传（不改）
④ 属于某路由 → 取该路由「最新首位、可用、且满足任务参数」的候选
                全候选不可用 / 无参数候选   → 原样透传（只回报事实，不在此处报错）
```

生产 `seedance2.5` 路由的真实候选链（`model_routes.route_model_ids`，顺序即优先级）：

```
1. apimodels-seedance-2.5-global    ← 只有 720p、只有 30s
2. hcatom-seedance-2.5              ← 你要 720p@4s，第 1 个不满足，落到这里
3. notoken-seedance-2.5
4. apimodels-seedance-2.5
```

所以你传 `notoken-seedance-2.5` / `seedance2.5` / `hcatom-seedance-2.5`，
**在对齐后都是 `hcatom-seedance-2.5`** —— 因为它是「满足 720p+4s 的第一个」。

**这不是 bug，是 2026-10-21「公开标识迁移」的产品决定**：用户只发起**路由名**，渠道由系统决定。

### 3.2 但要澄清一件事：你**读得到**渠道名

`task.get` 的 `structuredContent.model_id` 对你是原样返回 `notoken-seedance-2.5`（见 §1.3 实测），
因为你是 `tenant_admin`（`channel_visible: true`）。**读得到、但提交时指定不了**——这两件事分开的。

（对普通用户，`model_id` 会被投影删掉、只给 `display_code`。）

### 3.3 你需要「按渠道排产」的三条路

| 方案 | 做法 | 影响面 | 建议 |
|---|---|---|---|
| **A · 调候选顺序** | 平台侧把 hcatom / notoken 换位置 | **全局**，影响所有租户 | 只有在"这个渠道整体更好"时才做 |
| **B · 建独立公开码路由** | 例如 `seedance2.5-hq`，内部固定指向你要的候选（单候选链） | 只给需要的租户 | ✅ **推荐**：你只看到"高质量版"这个名字，渠道名不暴露，排产可控 |
| C · 提交加渠道参数 | 对 `task.submit` 加 `channel_code` | 等于把渠道名写进公开接口 | ❌ 不建议，与隐私设计冲突 |

**B 的具体形态**（我们要做的操作，你不用改代码）：

```
新建 model_routes 行：
  display_code = "seedance2.5-hq"
  route_model_ids = ["hcatom-seedance-2.5"]      ← 单候选 = 锁定
  is_enabled = 1
```

之后你传 `model_id: "seedance2.5-hq"`，对齐后必然落到 hcatom（因为它只有这一个候选）。
要哪几个渠道就建几个（`-hq` / `-std` / `-eco`），命名你定，内部映射我们维护。

**如果你要这条，把「你要几个通道、各自希望落到哪个渠道」告诉我，我配好通知你。**

## 四、你报告里两条实操要点：确认无误

   `model` 会被静默忽略 → 走默认模型。**`normalized.model_id` 是判断"传没传对"的唯一可靠依据**，这条抓得很准。
