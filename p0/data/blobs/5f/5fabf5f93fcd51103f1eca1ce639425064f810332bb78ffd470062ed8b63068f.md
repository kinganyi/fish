### Q1. 这把 `ays_*` key 是否具备租户上下文？稳定吗？轮换会回退 403 吗？

**结论：稳定可用；轮换不会回退到那个 403，但有两个坑。**

**1）10-13 的 403 不是 key 变了，是操作约束被放开了。**
策略层判据：`services/platform_gate/policy.py:151-153`

```python
if op.tenant_scoped and principal.tenant_id is None:
    return op, "tenant_scope"
```

2026-10-13 23:19（`98604cf`）把 `asset.list` / `session.list` / `task.validate` 等改为 `tenant_scoped=False`，所以 10-15 复评时 403 消失。
同批还把出站形态从 HTTP 403 改成 **HTTP 200 + `result.isError`**（`app.py:324-335`）——今后即使再撞，也不会是 403，而是 200 里的错误结果。**脚本里的判定别只看 HTTP 码。**

**2）稳定性：你需要的操作都稳定。**
`task.*` / `asset.*` / `model.*` / `session.*` 全部 `tenant_scoped=False`，与你 key 是否绑租户无关。**只有 `dsh.*`（5 个，且当前无 handler）仍是 `tenant_scoped=True`**。

**3）轮换的两个坑（比 403 更容易踩）。**
- 端点：`POST /api/user/keys`（`routes/user_keys.py:134`），`tenant_id` 可选（`:63-65`）。
- **坑一**：不传 `tenant_id` → 新 key 仍是用户级（NULL）。对你当前操作集无影响；想要租户语义就显式传 `tenant_id: 1`（服务端会校验你是该租户有效成员，`:173-183`）。

- 没有 rotate 端点，轮换 = 新建 + 吊销旧的（`:251-296`）。

**4）有没有「租户级 key」？** 没有类型字段，只有 `tenant_id` 是否为空（`007_api_keys.sql:35-48`）。

> 一句话：重建 key 时 **带 `tenant_id: 1` + `scopes: ["*"]`**，否则会掉工具。

#### ✅ 本次修复：`task.validate` 不再误报自有素材不存在

**原来的问题**：`task.validate` 构造的请求对象没有 `user_id`，素材属主校验取 `getattr(task,"user_id",0)` → 恒为 0 → SQL 变成 `user_id IN (0,0)` → **你自己上传的图被判"不存在"**，报 `[1503]`（H3）或 `[1603]`（图生图），而同一请求 `task.submit` 却能成功。

**修复**：`capabilities.py:1103-1104` 现在显式传真实属主：

```python
_validate_owner_id = await _principal_user_id(principal)
await _task_validator.validate(_validate_req, user_id=int(_validate_owner_id) if _validate_owner_id else 0)
```

**状态：已合入 `main` 并部署生产（2026-10-22 07:14，后端 PID 1006381）**。
→ **即日起 `task.validate` 的 `[1503]/[1603]` 可以当真实结论用了**，不必再"以 submit 为准"。

#### `task.retry` 语义（避免误用）

- 重试的是**同一条 generation**，原地重置后重新入队，**不新建任务、不新建计费单**。
- **只有 `interrupted` / `failed` 可接续**，其他状态返回 `[1313]`。
- 默认**先查上游真实状态**：running → 续轮询（零成本）；succeeded → 拉回产物（零成本）；failed/expired → 才真正重跑。
- `force_rerun: true` 跳过上游查询直接重跑，注册表标注「**可能双倍计费**」。**建议恒为 `false`**——这与你们"先查上游再决定"的历史做法一致。

#### `task.cancel` 语义（必须知道）

- 本地置 `cancelled` + **返还预扣积分**。
- **不会打断上游任务**（代码里是明确的 TODO）：上游可能仍跑完，平台侧成本照付，**你侧已退款**。
- MCP 调用配额不回滚。

### Q5. 素材链路

**1）没有 `asset.upload`，是两段式：**

```
① asset.upload_ticket → { upload_url: "/mcp/uploads/<token>", expires_in_s: 600 }
② POST /mcp/uploads/<token>（同一 Bearer key，multipart）→ { asset_id, ... }
   （可选 asset.upload_complete 幂等确认）
```

单文件 50MB（`MAX_UPLOAD_SIZE_MB`），nginx `/mcp/uploads/` 侧 60m。
**REST 的 `POST /api/materials` 只认 JWT**，用 `ays_` key 会 401 —— 纯 MCP 客户端请走上面对两段式。

**2）`asset.list` 可用**：过滤 `type` / `session_id` / `limit(≤200)`；**无分页**；只列**本人**资产（`user_id=本人`），不含 legacy `user_id=0`，无租户内共享。

**3）上传返回的 ID 可直接进 `mentioned_material_ids`**：判据是同一个 `users.id`，**不因"REST 上传 / MCP 提交"而拒绝**。

**4）签名下载链接：不能带 `Authorization`。**
- 形态：`/api/assets/{id}/file?uid=..&exp=..&sig=..`（**相对路径**，需自行拼域名）
- **TTL 600 秒**，签名绑定签发时的租户上下文
- 带 `Authorization: Bearer ays_...` **必然 401**：凭据优先级里 Bearer 高于签名且**无回退**，而 `ays_` 不是 JWT。同理也别带 `anyi_session` Cookie

**5）⚠️ 一定会踩的坑**：按**名字**引用素材（`mentioned_material_names`）是按 `session_id` 解析的，而 MCP 两段式上传**不写 `session_id`** → **MCP 上传的图永远按名字引用不到**，只能按 **ID**。请一律用 `mentioned_material_ids`。

## 四、P2 · 稳定性与运维

### Q7. 「更快更稳定」体现在哪一层？

**先纠正前提：MCP 并不比 REST 快。**

- **同一进程、同一 FastAPI app**：`main.py:1359-1361` `app.mount("/mcp", create_mcp_app())`，单 worker，共用同一 `get_db()` 与同一 `task_manager`
- **MCP 链路步骤更多**：Origin 校验 → Bearer 解析（3 次 DB 查询，无 principal 缓存）→ kill switch → 限流 → JSON-RPC 解析 → policy 授权（含配额 UPSERT 写库）→ handler → 幂等检查 → 会话解析 → create_task → 审计 → 两次 COUNT → 出站投影
- **没有任何缓存/连接池/独立队列**能让 MCP 更快
- **无延迟基准**：耗时埋点只覆盖 `/api/` 写请求，**`/mcp` 完全不采集**

**真实差异是"更严"而不是"更快"**：MCP 建单响应经字段契约 + 隐私投影，`cost_*` 一律不出。

→ 选 MCP 的理由若是"更快"，**不成立**；若是"接口契约稳定、字段受控、可审计"，**成立**。

### Q8. 维护窗口与中断处理

- **无固定维护窗口**；部署按需，会提前告知。今晚（10-22 07:11–07:14）刚做过一次，**对你无感**（MCP 面未变）
- **重启后运行中任务置 `interrupted`**（不是 `failed`），启动时扫描一次：
  1. **自动接续（零成本）**：仅 `rest` 且有上游 id 的任务——running → 续轮询；succeeded → 拉回产物；failed/expired → 置 failed 并退预扣
  2. **需要你调 `task.retry`**：无上游 id（图片/文本/本地算力）或接续查询失败
  3. **重新提交**：最后手段，新建任务并重新计费。**系统明确"绝不自动重跑"**

→ **官方建议：先 `task.status` 看状态；`interrupted` 就 `task.retry`（`force_rerun=false`）。不要直接重新提交。**
