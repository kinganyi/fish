# 协作台（dsh-hive）退役评估 · 与 fish 融合的可行性

> 2026-11-22。所有结论来自真实代码与实跑读数，`F*` 编号可回溯。
> 这不是一份"方案"，是一份**代价清单**——先看清要失去什么，再决定值不值。

---

## 一、先摆事实：两者的真实体量

| | 协作台 dsh-hive | fish |
|---|---|---|
| 语言 | TypeScript | Python |
| 文件数 | **5713 个** | 约 60 个 py |
| 体积 | **238.6 MB**（含 node_modules） | 约 7 MB |
| 形态 | **宿主插件**（进程内） | **MCP 服务**（独立进程）+ hook |
| 依赖 | **9 个 `@deepseek-ai` peer 包** | 纯 stdlib + sqlite |
| 测试 | **40+ 套**（ledger/roster/gate/notify/…） | 2108 条判据 |
| 工具面 | 30+ 个（memory/dtodo/skill/de_*/team_*） | 24 个 MCP 工具 |

**这个体量差本身就是答案的一半**：不是"把 A 融进 B"，是**两个不同物种**。

---

## 二、能力对账：哪些是重复的，哪些是 fish 做不到的

### 2.1 重复的部分（可以迁移）

| 能力 | 协作台 | fish | 说明 |
|---|---|---|---|
| 记忆 | `memory`（**五轨 md 文件**） | `remember`/`recall`（**SQLite**） | **两个时代的两种实现** |
| 记忆注入 | `memory:snapshot` 段 | `fish_session_hook.py`（inject 模式） | **fish 已有机制，DSH 侧没配**（F4） |
| 看板 | 面板视图 | `board` 工具 | 语义不同：hive 是 UI，fish 是数据 |
| 待办 | `dtodo`（四轨） | **无** | 可迁移进 fish |
| 技能 | `skill_manage` | **无** | 可迁移进 fish |

### 2.2 **fish 做不到**的部分（架构决定，不是工作量问题）

| 能力 | 为什么做不到 |
|---|---|
| **主动推送/广播**（`de_notify`/`de_channel_send`/`de_broadcast`） | fish 是 MCP 服务 + hook，**只有被调用时才能递东西**；全仓无 `requests`/`urlopen`/`smtp`/`websocket`（F2） |
| **会话编排**（`de_session` spawn/wake） | MCP 进程不能 fork 宿主会话 |
| **写作用域门**（`de_ws_*` + `writeScopeGate`） | 它在**宿主工具层拦截** `write`/`edit`；MCP 层没有这个拦截点 |
| **面板 UI**（client inject） | MCP 不参与宿主 UI |
| **8 个角色工具**（`team_*`） | 角色 = persona 概念，MCP 只有 tool 概念 |
| **persona 变量**（`ctx.systemPrompt.variable`） | 同上 |
| **COI 调度 / 提示词库 / 模型设置 / 画板 / 书签 / Advisor** | 全部依赖宿主 API |

**这张表是评估的核心**：**六成能力 fish 架构上接不了**。

## 三、退役的直接后果（按痛感排序）

### 🔴 后果 1：**每一轮自动注入的「长期记忆」会消失**

**这是最痛的一条，而且是铁证。**

协作台的 `snapshot.ts` 定义的注入段序，与我这次会话上下文里的标题**逐行对应**：

```
hive 定义的段              我上下文里的实际标题
1.  ## 你的会话 / 会话 ID  → ## 你的会话 ID（记住它：…）        ✓
2.  ## 长期记忆           → ## 长期记忆（所有项目、会话都必须遵循）✓
3.  ## 用户档案           → ## 用户档案                        ✓
4.  ## 本项目关键记忆      → ## 本项目关键记忆（memory 工具…）    ✓
5.  ## 记忆 memory-evolve → ## 记忆 memory-evolve（包含…）       ✓
```

**所以退役 hive 之后，`MEMORY.md` / `USER.md` / `KEY.md` 不再被自动注入。**

**好消息**：fish **有替代机制**——`fish_session_hook.py` 的 `inject` 模式输出 L0 身份 + L1 状态 + L2 索引（F4）。但：

- DSH 现在的 `hooks.json` 指向的是 `fish_dsh_hook.py`（**只签发 token，不注入内容**，F5）
- 要接管得改配置 + 可能要做协议适配

### 🔴 后果 2：**整个团队消失**

8 个角色工具（`team_product_manager` / `team_architect` / `team_engineer` / `team_qa` / `team_reviewer` / `team_security` / `team_release` / `team_retro`）是 hive 提供的。

**退役 = 我不再是"主理人"，多 Agent 协作这套东西从 DSH 里消失。**

### 🟠 后果 3：**跨会话通信归零**

`de_broadcast` / `de_notify` / `de_channel_send` 全部消失。**fish 架构上补不了**（F2）。

你刚问过的"识别活跃会话并推信息过去"——这个能力**只在 hive 里**。

### 🟠 后果 4：**协作账本、任务板、写作用域门全部失效**

- 账本：谁在跑、跑到哪、有没有悬挂
- 任务板：`team_task_*`
- 写作用域门：并发写冲突的护栏

**这三样 fish 一样都接不了。**

### 🟡 后果 5：待办 / 技能 / 提示词库 / 模型设置 需要迁移

这些 fish **能**接（纯数据层），但要写新代码 + 迁移数据。

## 四、三条可选路径及代价

### 路径 A：全退役，能力尽量融入 fish

| 项 | 读数 |
|---|---|
| 能保住 | 记忆（换 fish 实现）、待办、技能、部分看板 |
| **保不住** | 注入段、团队、广播、账本、任务板、写作用域门、面板、COI、提示词库、模型设置、画板、书签、Advisor |
| 工作量 | **极大**（fish 要变成宿主插件，且六成能力仍做不到） |
| 我的判断 | ❌ **不推荐** |

**理由不是工作量大，而是"融不进去"**——fish 是独立进程 + MCP 协议，它没有宿主 API。**把宿主插件的能力"融进"MCP 服务，在物理上不可能。**

### 路径 B：拆掉 hive，只留需要的部分

**做法**：把 hive 拆成"控制面"（保留）与"数据面"（迁到 fish）。

| 保留（控制面） | 迁走（数据面） |
|---|---|
| 注入段、面板、写作用域门、会话编排、广播、8 个角色工具 | MEMORY/USER/KEY 的内容、待办、技能、提示词库 |

| 项 | 读数 |
|---|---|
| 优点 | fish 成为**唯一记忆真相**；hive 只做控制 |
| 缺点 | 要重写 hive（5713 文件的插件拆两半）；**两套插件继续共存** |
| 我的判断 | ⚠️ **可行但不划算**——你并没有省掉维护 hive |

### 路径 C：保留 hive，但把它的「记忆」单向同步进 fish

| 项 | 读数 |
|---|---|
| 做法 | hive 继续注入（每轮自动）；每次写入时同步一份到 fish，让 fish 能跨宿主查 |
| 优点 | **零风险**（hive 不动）、fish 获得全量数据、两套工具都能用 |
| 缺点 | 双写；需要一致性判据 |
| 我的判断 | ✅ **推荐**（如果你只是想"让 fish 也能看到这些记忆"） |

## 五、但真正该先问的是：**你为什么想退役它？**

**三种动机对应三个完全不同的方案：**

| 你的动机 | 正确方案 | 为什么 |
|---|---|---|
| **"太大了 / 太慢了 / 占空间"** | 清 node_modules + 精简，**不退役** | 238 MB 里绝大部分是 node_modules |
| **"它老出问题，我不信任它"** | **先修判据**，不是退役 | 之前发现的"判据绿但能力不存在"是可以修的 |
| **"我只要记忆，不要那套多 Agent 编排"** | **路径 B 的变体**：关掉角色工具/preset，留记忆+通知 | 按需裁剪，不必全拆 |
| **"fish 已经能做大部分事，两套重复了"** | **先对账**——实测重复只有记忆/待办/技能三项，其余五成是 hive 独有 | 重复没你想的多 |
| **"我想集中到一套，减少维护"** | 路径 C（单向同步）或裁掉角色层 | 减少维护 ≠ 全拆 |

## 六、我的结论

**"把协作台融入 fish"这件事，在技术上做不到（六成能力 fish 架构上接不了）。**

**但"你想要的东西"很可能都能达到——只是路径不叫"融合"：**

1. **想省空间** → 清 node_modules（238 MB 里绝大部分是它），不动逻辑
2. **想减少重复** → 把 hive 的 MEMORY/USER/KEY 单向同步进 fish（路径 C）
3. **想减少维护** → 关掉角色层（preset 换成不带 8 个 team_* 的），保留注入+通知
4. **想只要记忆** → 换成 fish 接管注入（改 hooks.json 指向 `fish_session_hook.py`），hive 只留广播+面板

**只有第 4 项是真的"退役"，而它会带走广播、账本、写作用域门、面板、团队。**

---

## 七、要你决定的四件事

1. **动机**：上面五种里哪个最接近？（这决定后续一切）
2. **能不能承受失去广播/团队/账本**？（如果不能，路径 A 直接排除）
3. **"留"的标准是什么**：是"功能够用"，还是"代码还在我这"？
4. **要不要我先做一份"重复度实测"**：把 hive 的 30+ 工具逐个跑一遍，标出哪些 fish 已有等价物、哪些没有——**这是唯一能替代猜测的东西**
