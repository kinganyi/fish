## 0. 摘要（三句话）

1. **把「宿主」从散在四个文件里的 if 分支，收成一张可验证的 `HostSpec` 表 + 一个薄驱动**：接入层（hooks 安装 / MCP 注册 / 安装探测 / 设置表单）的扩展从「改代码」变成「加数据」（0 行代码或一个 codec）；而语料采集的扩展仍是 adapter 类——**这两件事必须分开**，现状把它们都叫「宿主」，是这次要拆的第一个概念。
2. **fish 里其实有三套「宿主」词表**（安装目标 / 会话键前缀 / 公民自报），它们互相打架是 2.5% 一致率的真因。本设计不推翻 97 的裁决（宿主取 `session_key` 前缀），而是把它明确成 **protocol 词表**，同时保留 host id 与自报面两套词表各有各的读者。
3. **`install_hooks.py` 不重写**：保留为 CLI 壳（`--check`/`--apply`/`--restore` 语义、备份命名、合并语义、diff 文案一律不动），只把 `desired_hooks()` 委托给 spec 驱动的新模块。验收标准是既有 17 条锁定判据（`test_surface_naming.py:297-634`）**一行不改全绿**。

### 1.2 三套词表（这是 2.5% 一致率的真因）

| 词表 | 读者 | 取值 | 谁写 |
|---|---|---|---|
| **protocol**（会话键前缀） | 工作台、看板、撞车判定 | `dsh` / `codebuddy` | hook 与 CLI 写进 `session_key`（`fish_activity.py:208-214`） |
| **host id**（安装目标） | 安装器 `--host`、spec 注册表 | `dsh` / `workbuddy` | 人（命令行） |
| **自报 host** | 公民档案 | 10 个值（含大小写重复与空值） | 任何写 `citizens.host` 的代码 |

实测（2026-11-23T21:09:49+08:00，`I:/app/fish-data/data/index.sqlite`，只读）：

```
citizens_all.host : dsh 256 / cli 62 / workbuddy 11 / codebuddy 7 /
                    zcode 1 / unknown 1 / dsh-desktop 1 / codex 1 / ZCode 1 / NULL 1
tool_activity     : 27,759 行，host 列与 session_key 前缀一致 699 行（2.52%）
sqlite_master     : 48 张表，名字含 host/adapter/hook 的 0 张
```

两个解释：
- `tool_activity.host='workbuddy'` 而前缀是 `codebuddy`，**不是写错了**——`fish_activity.py:59` 就是有意把 workbuddy 映射到 codebuddy 前缀。所以那一列是**账号归属**，不是宿主。97 §1.2六 已裁决「宿主一律取 `session_key` 前缀」（`fish_workbench_api.py:459-468`、`fish_ui.py:210-212` 两处实现），本设计沿用。
- `citizens_all` 是**视图**（`citizens UNION ALL citizens_archive`，实测 `sqlite_master` 里是 `view`），所以任何「写侧归一」都要同时管两张表，这让「改库归一」的成本比看起来高。

### 1.3 两个「假真」（读得出来、但不是真相）

**(a) WorkBuddy 的 `--check` 现在就是假红。** `WORKBUDDY_HOME` 未设置（实测为空），`install_hooks.py:92` 的缺省值是占位符 `C:\Users\<用户名>\.workbuddy`，于是 `_target()` 指向一个不存在的文件 → `load_document()` 返回 `{}`（`:449-450`）→ `validate_hooks()` 报「缺事件 SessionStart/UserPromptSubmit/PreToolUse/PostToolUse」（`:311-312`）→ `exit 2`。实测输出（只读，未写盘）：

```
[workbuddy] C:\Users\<用户名>\.workbuddy\settings.json
  ✗ 缺事件 SessionStart …（四个）
  ✗ 采集器数量应为 1，实际 0（无）
EXIT=2
```

真实原因是「路径是占位符、文件不存在」，但输出里一个字都没说——**「判不到」被报成了「红」**。这是三态不分明的典型：用户照提示去 `--apply`，得到的是"写入失败"或"写到别的目录"，而不是"你的宿主家目录没找到"。

**(b) 行尾注释已经漂了。** `install_hooks.py:494` 写「`hooks.json` 现在是 CRLF，`settings.json` 是 LF」，实测 2026-11-23：`hooks.json` 含 CRLF=False（LF）、`settings.json` 含 CRLF=False（LF）、两者都无 BOM。**结论：行尾与 BOM 不能做成「宿主的方言字段」**，它是"读这份文件时的现状"，行为只能是 `preserve`（`_read_text` 的 `newline=""` 与 `_dump_like` 原样保留已经是对的），一旦把它写成 per-host 常量，注释一漂就会有人按错假设改代码。

## 2. 抽象：HostSpec

### 2.1 什么算「宿主」，什么不算

判据三条，**同时成立**才算宿主：

1. **有本机安装痕迹**（配置文件 / 可执行 / 家目录之一），可被无副作用探测；
2. **有至少一条 fish 能接的通道**：hook，或 MCP，或 CLI（三者之一）；
3. **有稳定的会话标识来源**（`session_id` / 模板变量 / token / `session_name` 之一），可被归属。

只有 ①② 没有 ③ 的，是**渠道**不是宿主——它不能被归属，进不来 registry，只能进「未接入清单」。这条判据现在就有用：**ChatGPT 桌面版**在本机没有可探测的家目录（`~/.chatgpt` 实测不存在），也没有已知的 hook 面，按 ③ 判不到 → 本轮不编 spec，列「未验证」（见 §9）。**Codex** 有安装（`I:\app\codex\config.toml`，4,006 B，mtime 2026-11-23 21:02:08）且 MCP 通道已配（`config.toml:84` `[mcp_servers.fish]`），但**没有 hooks**——它是"只有 MCP 一条通道的宿主"，是合法宿主，只是能力矩阵少几格。

### 2.3 哪些差异属于「配置」，哪些属于「代码」

分三档，每档给一条**可判的**界线：

**A 档 · 纯数据（0 行代码）**：差异全部落在上表字段的值域内——同一份 JSON 形状、同一套 `{matcher, hooks:[{type,command,…}]}` 条目结构、同一套 stdout 协议（`hookSpecificOutput.additionalContext`）。新增宿主 = 加一个 spec 字面量。
判据：`python install_hooks.py --host <new> --check` 能跑；对测试用的 `fake` 宿主能 `--apply` 到临时文件且校验通过（§7.2 判据 1）。

**B 档 · 一个 codec 或一个 render 函数（不写 adapter 类）**：配置不是 JSON（TOML/YAML），或条目不是 `{type,command}`（如 Codex 的 `notify = [exe, "turn-ended"]`：单事件、无 matcher、无事件名），或需要模板变量展开（ZCode `${CLAUDE_PLUGIN_ROOT}`）。
判据：`hooks_target.format` 指向一个**已注册**的 codec；未注册 → 响亮失败，不许静默退回 JSON。

**C 档 · 必须写代码：adapter 类**：需要**解析宿主产物**（会话日志、数据库、行流）。这是 `fish_corpus.ADAPTERS`（`fish_corpus.py:51`）的职责，**不是接入层的职责**。
判据：`fish_corpus.ADAPTERS` 里有没有一项。依赖方向：语料层可以读接入层的 `id/protocol` 表，**接入层不许 import 语料层**（否则 hooks 安装会拖进 zstd 解析）。

**三问判据**（把新差异归类）：

- Q1 能否表达成「路径 + 嵌套层 + 字段名 + 单位 + 布尔开关」？→ 能就是 **A 档**。
- Q2 是否需要解析宿主的产物？→ 是就是 **C 档**（语料层），不进接入层。
- Q3 是否需要判断运行时语义（正则还是字面、超时单位、输出 schema）？→ 是的话，**用枚举声明**（仍在 A 档），判断逻辑**收敛在一处代码**。**spec 里不许写可执行代码**——那是"配置里藏程序"，它会让 spec 失去可审计性，也会让第三方宿主获得执行权。

一句话边界：**接入层（hooks/MCP/探测/表单）= A+B 档；语料层（读会话）= C 档。** 现在的 `HOSTS` 一个词同时指这两件事，是本设计要拆的第一刀。

## 3. 注册与发现

### 3.1 注册表放哪：**代码包内的声明式 spec**，不建 hosts 表

结论：`p0/fish_hosts.py` 持有 spec 表（Python 字面量，或 `p0/hosts/*.json` 由它加载），加一个 `register()`/import 期自检。

理由（按重要性）：

1. **spec 是程序资产，不是用户数据**。它描述的是"某个宿主的配置格式"，而配置格式随宿主版本变。它需要 code review、git 历史、单测锁定——这三样 Python 文件天生有，DB 表天生没有。
2. **失败模式对**。spec 坏在 DB 里，安装器就按坏 spec 写配置，症状是"某个功能悄悄没了"（正是这套工具存在的理由）；spec 坏在 Python 里，import 期就报错，进不了生产。
3. **第三方加宿主不需要改 schema**：放一个文件即可，不需迁移、不需重启数据库。
4. **用户要的「可配置的设置界面」不是「宿主定义存数据库」**。设置界面渲染的字段**来自 spec**；用户改的是**每个宿主的取值**（是否启用、装哪些事件、超时、路径覆盖），那是 config，不是 spec。

三层分离（这是本节的核心结论）：

| 层 | 内容 | 存放 | 谁改 | 变更代价 |
|---|---|---|---|---|
| **HostSpec** | 宿主是什么、能干什么（§2.2 二十个字段） | 代码包 | 开发者（PR + 测试） | 版本化，需回归 |
| **HostConfig** | 用户选择：`enabled`、事件子集、超时、显式路径覆盖 | **现有 `config` 表**，键前缀 `host.<id>.*`（`fish_db.py`/`fish.py` 的 `get_config`/`set_config` 已具备） | 设置界面 / `fish config set` | 随时可改，可回退 |
| **HostState** | 探测结果：装没装、版本、配置是否就绪、最后心跳、最近错误 | **不落库**（进程内短 TTL 缓存，≤30s） | 运行时算 | 无（每次重算） |

`HostState` 不落库是刻意的：探测结果是"当下"，一旦落库就变成"看起来装了、其实早卸了"。这条与 fish 既有的"判不到不编值"是同一条纪律。

### 3.2 别名与归一

先把三套词表各自的归并目标说清（不是把三套合成一套）：

- **protocol**（前缀）保持原值，只做小写（`fish_workbench_api.py:459-468` 已经在做，不动）；
- **host id** 由 alias 表归一；
- **自报 host** 由 `canonical_host()` 归一。

两个函数，两种用途（沿用 fish_naming 的"机器面 vs 人类面"铁律）：

- `canonical_host(raw) -> str`：**机器面归并键**。命中 alias → 规范 id；命中 `_NON_HOST`（`unknown`/`null`/空）→ `""`；其余 → 原样小写。
- `host_label(raw) -> str`：**人类面标签**。永远保留原始写法（`ZCode` 显示成 `ZCode`），认不出时显示"未登记宿主 `<原值>`"。

规则：

| R | 规则 | 例子 | 判据 |
|---|---|---|---|
| R1 | 空/None → `""`（不是 `"unknown"`） | NULL → `""` | `canonical_host(None) == ""` |
| R2 | 只做 `strip().lower()`，**不做通用字符串变形** | `ZCode` → `zcode` | `canonical_host("ZCode") == "zcode"` |
| R3 | 只认**显式 alias 表**，不做前缀截断/下划线替换 | `dsh-desktop → dsh`；但 `dsh-anything` ≠ `dsh` | `canonical_host("dsh-foo") == "dsh-foo"`（未命中就原样） |
| R4 | `unknown`/`n/a`/`null` 等自报哨兵全部 → `""`（与空同桶） | `unknown` → `""` | 归一后计数里不再出现 `unknown` 这个"假宿主" |
| R5 | `cli` **保留**为独立值（语义 = 显式"无宿主"，与空值不同） | `cli` → `cli` | `canonical_host("cli") == "cli"` |
| R6 | 一个 protocol 可对应多个 host，**反查不唯一时不猜** | `codebuddy` → `{workbuddy, codebuddy}` | `hosts_for_protocol("codebuddy")` 返回两个，不折成一个 |

### 3.3 能力矩阵怎么表达、怎么被测

表达：

```python
CapEvidence = {"state": "yes"|"no"|"unknown", "evidence": "文件:行号 或 命令", "probe": "命令|None"}
CAPS = {"hooks","mcp","cli","identity_issue","identity_inject","board","push","corpus","notify","agent_sessions"}
```

四条断言（跑在 `test_hosts_contract.py` 里，不是写在文档里）：

1. `caps` 的每个 key ∈ `CAPS`（拼错即红）；
2. `state == "yes"` ⇒ `evidence` 非空（**不许无证据声称支持**）；
3. `state == "yes"` 且 `probe` 非空 ⇒ `probe` 可被 `shlex.split` 解析且首词存在（smoke，不要求真跑宿主——真跑会依赖机器状态）；

第 3 条是"能失败"的关键：把某 cap 的 `probe` 写成不存在的可执行文件名 → 断言 3 必须红；对照组（真 probe）必须绿。

### 4.3 四种宿主方言的实测差异（这是泛化的真实难度）

| 维度 | DSH | WorkBuddy | ZCode | Codex |
|---|---|---|---|---|
| 配置文件 | `~/.dsh/hooks.json` | `~/.workbuddy/settings.json`（43,302 B，共用文件） | `~/.zcode/cli/config.json`（417 B）+ 工作区 `.zcode/config.json` | `I:\app\codex\config.toml`（TOML） |
| 事件表嵌套层 | `hooks.<Event>`（也认裸事件表） | `hooks.<Event>` | **`hooks.events.<Event>`**，且须 `hooks.enabled=true` | **无事件表**；只有顶层 `notify = [exe, "turn-ended"]` |
| 事件集 | 4 个（实测文件里就这 4 个） | 4 个 | **7 个**：`SessionStart/UserPromptSubmit/PreToolUse/PermissionRequest/PostToolUse/PostToolUseFailure/Stop`；`Notification/SubagentStop/PreCompact` **不支持** | 1 个（`turn-ended`） |
| matcher 方言 | 纯字面 → 字面比较；否则编译正则 | 同族（Claude Code 方言） | **永远编译大小写敏感正则**；非法正则**静默永不命中** | 无 matcher |
| 超时字段 | `timeout`（整数） | `timeout`（整数） | `timeout`=**秒**，`timeoutMs`=**毫秒**（后者优先） | 无 |
| 输出协议 | `hookSpecificOutput.additionalContext` | 同 | 同，但 **schema 严格**：多一个键整块作废 | 无 |
| 身份来源 | hook payload `session_id` + `cwd` | hook payload `session_id` | `${CLAUDE_SESSION_ID}` 模板变量，**且同时注入为环境变量** | 无 hook |
| 证据 | 实测 `hooks.json`；`hook_io.py:34-39` | 实测 `settings.json` | `zcode-guide/0.3.0/skills/diagnosing-hooks/SKILL.md:14-36,53`（官方插件自带文档） | 实测 `config.toml:1,84` |

两处关键结论：

1. **ZCode 的配置代码钩子默认是关的**（官方原文：「These are disabled by default — configuration-file hooks must set `hooks.enabled: true` to run」）。所以 ZCode 的 spec 必须带 `enable_flag=("enabled", True)`，而 `--check` 要能报"enabled 未开"这一档——**这一格不写，装上去了也永远不触发**，正是本文件开头说的"某个功能悄悄没了"。
2. **ZCode 的 `SessionStart` matcher 语义不是工具名**，是 `startup|resume|clear|compact`；工具事件的 matcher 才是工具名。所以"给 SessionStart 也加 matcher"在 ZCode 上语义完全不同——渲染器**只允许给 `PreToolUse`/`PostToolUse` 加 matcher**，其它事件加了就报错。这条现在就该写成断言（不是等踩了再补）。

### 4.4 `--check` / `--apply` / `--restore` 的统一语义

| 动作 | 统一语义 | 差异点（按 spec 声明） |
|---|---|---|
| `--check` | 只读；三态分明：**一致 / 不一致（红）/ 判不到（红，但原因不同）**；一律不写盘；退出码 0 或 2 | 宿主不支持某事件 → 报"该宿主不支持 X"（不是"缺事件 X"）；`enable_flag` 未开 → 单独一档"已写入但未启用" |
| `--apply` | 先备份（只在真的要改时）→ **合并**（不删别人的）→ 原子替换 → 打印其它事件"保持不变" | `restore=False` 的宿主：备份照做但 `--restore` 拒绝；`restart=True` 的宿主：收尾必须打印"重启才生效" |
| `--restore` | 按备份**字节还原**，还原后立即校验，坏版本非 0 | `restore=False` → 明确报"该宿主的配置由宿主自管，本工具不提供回滚"，退出码非 0，**不许静默跳过** |
| `--file` | 显式路径（测试/演练），只许配一个宿主 | 不变（`main()` 已有这条校验） |

## 6. 面向未来的设置界面

### 6.1 设置表单即数据（forms as data）

每个宿主在设置页渲染什么，由 `spec.forms` 决定（字段名/类型/默认值/校验/说明/危险级别），UI 不硬编码任何宿主知识：

```json
{"name":"enabled","type":"bool","default":true,
 "label":"在这个宿主上安装 fish hooks","help":"写入后需重启宿主才生效",
 "risk":"write","requires":["installed"]}
```

`type` 取值（一期）：`bool` / `int` / `enum` / `path` / `readonly`（只展示探测结果，不可改）。
`risk` 三档：`read`（只探测）/ `write`（写配置文件）/ `danger`（会删其它事件，如 `--force`）。

**判据**：`forms` 里出现 `type` 不在枚举内 → 加载期报错；`risk=="write"` 的字段必须在 UI 上要求二次确认（§6.3）。

### 6.2 `GET /api/hosts`（orientation 式一次有界）

```json
{"schema":"fish-hosts/1","asOf":"2026-11-23T13:09:49Z",
 "hosts":[{"id":"dsh","display":"DSH","protocol":"dsh","installed":true,
   "version":"0.2.0-rc.2","configPath":"…/.dsh/hooks.json",
   "configState":"ready","caps":{"hooks":{"state":"yes","label":"已接"}, …},
   "lastHeartbeatAt":"…","lastError":null,
   "actions":[{"id":"apply","label":"写入 hooks","risk":"write","needsRestart":true}]}],
 "unregistered":[{"raw":"ZCode","count":1}]}
```

`configState` 五档，**必须分开**（这是 §1.3a 的修法）：`ready` / `stale`（与目标不一致）/ `missing`（文件不存在）/ `unreadable`（读不出/JSON 坏/占位符未解析）/ `disabled`（已写入但 `enable_flag` 未开，如 ZCode）。

**判据**：占位符路径未解析时必须是 `unreadable` + `reason="path_unresolved"`，**不许**是 `missing`，更不许报"缺 4 个事件"。

`lastHeartbeatAt` 来自既有心跳文件（`_audit/hooks/`，`fish_activity.HEARTBEAT_RELDIR`），不新造表。

### 6.3 只读探测 vs 写操作的边界

| 类别 | 允许谁做 | 例子 | 理由 |
|---|---|---|---|
| **读**（探测/比对/渲染预览） | UI 直接做（HTTP GET） | 装没装、版本、`--check` 的差异、表单渲染 | 无副作用；失败只影响展示 |
| **写**（改配置/备份/还原/`--force`） | **不在 HTTP 进程里做**：UI 二次确认后，服务端以子进程调 `install_hooks.py --apply/--restore`，只接受白名单动作 | 写入 hooks、回滚 | 与 CLI 同一条实现（不写第二份）；HTTP 层保持只读纪律（沿用 `fish_workbench_api` 的 `mode=ro`+`query_only` 与"不执行任何写语句"） |
| **危险**（`--force`/删事件） | 必须显式输入确认词 + 展示将被删除的事件清单 | 整层替换 | `diff_hooks`/`cmd_apply` 已强制打印 `dropped`，UI 不许吞掉这段 |

| 3 | 能力矩阵缺项 → UI 显示"该能力未接/未验证" | 给 fake 的一个 cap 标 `state="yes"` 但不给 `evidence` → 契约测试红（不许无证据声称支持）；另一变异：`GET /api/hosts` 把 `unknown` 渲染成"已接" → 端点判据红 | 原样 → `unknown` 渲染"未验证" |
| 4 | 配置被外部改坏 → `--check` 红 | 3a 非法 matcher（既有 `:398-414`）；3b 删一个事件（既有 `:483-497`）；3c **ZCode 的 `enabled` 被改成 false** → 必须是"已写入但未启用"这一档，不是"缺事件" | 原样配置 → `EXIT=0` |
| 5 | `--apply` 后**非目标事件逐字节不变** | 把 `merge_hooks` 临时改成整层替换 → 其它事件消失，判据红 | 原样 → 其它事件（`Stop`/`Notification`）逐字节相同 + 文件 sha256 里"非 hooks 层"的字节区段不变 |

判据 5 的"逐字节"要给具体做法，不能只说"相同"：

```python
# 1) 结构级：其它事件的对象相等（deep equal）
assert before["hooks"].get("Stop") == after["hooks"].get("Stop")
# 2) 字节级：把 hooks 层以外的部分序列化出来比 sha256
def outside_bytes(doc): return json.dumps({k:v for k,v in doc.items() if k!="hooks"},
                                          sort_keys=True, ensure_ascii=False).encode()
assert sha256(outside_bytes(before)) == sha256(outside_bytes(after))
```

### 7.3 测试策略

1. **golden 配置 per host**：`tests/golden/hosts/<id>.json` 是"该宿主应有的 hooks 层"的冻结快照。渲染器改动 → golden diff 必须被审阅过才能更新（更新动作要写进 PR 说明，不许静默 `--update`）。

## 8. 与工作台 / 一期架构的关系

### 8.1 放独立设置页，不塞进右栏

- 右栏（97 §C 的 `/api/stats`、`/api/entry`）回答的是「**此刻谁在动哪块**」——时间尺度是秒到分钟。
- 宿主接入回答的是「**这套东西装没装、能不能用**」——时间尺度是天到月，且操作带"写盘 + 重启宿主"的后果。
- 96 §12 明确「不是管理后台（无设置入口）」是**一期首屏的产品定位**；用户现在要的设置界面是**新增的第二个面**，不是改首屏。所以：**新增 `/settings/hosts` 独立页**，首屏一个字节不动。
- 两者共用同一份真相：`fish_hosts.spec_all()`。右栏继续只读；设置页走 `/api/hosts` + 白名单动作。

### 8.2 `citizens_all.host` 的归一由谁负责

结论（直接回答用户 G-2）：**读取侧负责归并，新写入点顺带归一，历史数据迁移单列且需拍板**。

- 读取侧是**唯一必须做**的：`canonical_host()` 在展示与聚合处调用（`fish_workbench_api.py:1146` 的现成实现改成调它，消掉第二份实现）。
- 写入侧**本轮做不到 100%**：`fish.py` 是冻结区（行数棘轮差 1 行），三处 `INSERT INTO citizens` 不改 → 必须如实标"写侧未收敛"。
- 不做「迁移脚本自动改库」：那是 M3，需用户拍板，且有备份与守恒判据（§3.2）。
- **不许**在读取侧直接改库（那会把只读读口变成写口，违反工作台只读纪律）。

## 附：本设计的三个判断，供裁决

1. **不建 hosts 表**——这条最容易被否（"设置界面当然要有表"）。我的理由写在 §3.1：spec 是程序资产，落库会制造"按坏 spec 写配置"的失败面；用户可配的东西在 `config` 表，不在 hosts 表。（用户点名问的 B-1，我给的是"代码包 + 三层分离"，不是表。）
2. **`workbuddy` 与 `codebuddy` 不合并成同一个 id**——它们共用 `codebuddy:` 前缀（`fish_activity.py:59`），但那是 protocol 层；产品层是两个安装目标。合并会丢掉"装的是哪个产品"这个事实；不合并则要求 §3.2 R6 的"反查不唯一不猜"。
3. **`install_hooks.py` 不重写，只委托**——有人会主张"直接重写 747 行更干净"。但那里有 17 条评审钉死的判据，重写等于把它们全部重新证明一遍；委托式改法能让 17 条判据原样当回归网。这是本轮最省风险的路。
