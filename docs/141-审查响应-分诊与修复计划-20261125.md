## 2. 逐条语义分析（关键项）

### 2.1 P0-1：注入包信任门（阻断）

**审查说**：visitor 可自助拿 token → 写 lesson → 进所有会话的错题本；历史 7 条 visitor rule + 14 条 unknown rule 已在包里。

**代码核实**：`fish_inject._rule_rows`（L29-60）、`count_rule_rows`（L90）、`_lesson_rows`（L147）、`count_lesson_rows`（L97）确实不按 owner 过滤；`fish.py build_short_rules_block` 也对 owner 无感；`fish_trust.py:153` 明写 lesson/fact/episode/artifact 免凭证是设计意图。

**判定**：**真 P0，但根因在"进包侧"而不是"写侧"**。写侧放开是"记忆比归属重要"的产品选择；把不可信作者的内容写进**系统提示**才是劫持面。

**修法**：唯一可信判定（owner 为空/unattributed/unknown 或 citizens.kind='visitor' → 不可信）+ 四个取数口统一过滤 + `inject.allow_untrusted`（默认 False，且**永不放行 visitor**）+ 三条能红的判据（visitor lesson/visitor rule/unknown rule）+ 变异。

**存量**：不改历史行；过滤后自动不进包。是否逐条治理 7+14+47 条由主人决定（提供清单，不自动改归属——避免重蹈 P1-1）。

### 2.6 P1-7：HTTP 无认证（需产品决策）

**核实**：`fish_workbench_api._origin_allowed` 对无 Origin 放行；`do_POST` 只看 `write_allowed`（回环）；数据 ACL 只保护文件，不保护端口。

**判定**：真风险，但"加 token"会改变 UI 使用方式（需要注入/粘贴 token），且**同用户的本机进程天然可读 token 文件**——token 只能挡"其他 Windows 用户"，挡不住同用户进程。要真正解决需要命名管道/按用户 ACL 的 IPC 或全口认证 + 用户输入密钥。

**建议方案（待拍板）**：
- 方案 A（低改动）：仅写口要求 `X-Fish-Token`；token 文件放 `p0/data/_audit/workbench.token`（ACL 当前用户）；UI 通过同源 `GET /api/auth` 仅在 loopback+Origin 白名单下发——这挡不住同用户进程，但挡其他用户。
- 方案 B（彻底）：改用命名管道（Windows ACL）或全口 token + UI 首次粘贴。
- 方案 C（接受风险）：单人本机、威胁模型不含"同机其他用户"，文档写明。

**我的倾向**：先做 A（写口 token，防误改/跨用户），读口用 `--require-token` 可选；把 B 立专项。**需要你拍板**。
