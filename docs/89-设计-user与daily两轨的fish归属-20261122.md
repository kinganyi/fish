# `user` 与 `daily` 两轨在 fish 现有表达里的归属设计

> 2026-11-22。约束：**只用 fish 现有的表达**，不新增"轨道"概念。
> 所有数字来自真实文件统计，不是估计。

---

## 一、先看清要搬的东西有多大

| 文件 | 条目 | 字符 | 备注 |
|---|---|---|---|
| `MEMORY.md` | **38 条** | 14,518 | 其中 **7 条**是 WorkBuddy 导入的低质量副本 |
| `USER.md` | **20 条** | 1,838 | 其中 **10 条**是 WorkBuddy 导入，与 profile 槽位**内容重复** |
| 项目 `KEY.md` | 7 个项目 / **28 条** | — | 最多 5 条/项目 |
| `daily/` | **110 天** | 1.42 MB | 约 13 KB/天 |

**关键判断：要搬的"记忆"只有 86 条（38+20+28）**，对一个已有 681 条记忆的 fish 库来说很小。
**真正大的只有 `daily`（1.42 MB），而它恰恰最不该整体搬**——见第三节。

## 二、`user` 轨 → 三类分派（不需要新概念）

`USER.md` 的 20 条实测可以干净地分成三类：

### 2.1 稳定的画像 → `profile_slots`（现有 9 个槽位，够用）

`USER.md` 里真正的"画像"正好这些：

| USER.md 的内容 | 落到哪个槽位 |
|---|---|
| 姓名徐安 / 通用名安逸 / 2001-11-10 生 | `称呼.名字`、`称呼.怎么叫我` |
| 哈尔滨出生 / 常州成长 / 成都工作 | `生活.所在地` |
| PPT 从业者 / AI 漫剧 / FDE / KVP | `工作.身份` |
| 现成都量传引擎合伙人（前鳍漫/演示引擎） | `工作.公司` |
| 五大业务线 | `工作.业务线` |
| 对 AI 的要求（简洁/文档化/先确认） | `性格.沟通偏好` |
| 价值观（存在主义底色/图名型） | `性格.价值观` |
| 语言：只用中文 | （并入 `性格.沟通偏好`） |
| 说话风格 / 写作风格 | （并入 `性格.沟通偏好` 或新增 `性格.写作风格` 槽） |

**9 个槽位刚好装下。** 而 fish 的 `profile_slots` 本来就有 `permanence`（stable/lasting）与 `version` 字段——比 md 的一行文本更严格。

### 2.2 约束类 → `remember --type rule`

```
敏感事项：工资发放主体不进记忆；工资/分成不写入对外产物；凭据只引用位置不复制值
```
这不是"画像"，是**约束**——`mem_type=rule` 正是它的位置（fish 的 `rule` 永不衰减）。

### 2.3 低质量导入 → **不迁**

那 10 条 `来源: C:\Users\15596\.workbuddy\USER.md#2026-09-23` 是同一个人的信息被导入两遍：

```
- **Name:** 安逸
- **What to call them:** 安逸
- **出生地:** 哈尔滨
- **上学地:** 常州（家人也在常州）
- **目前工作城市:** 成都
```

**这些内容 2.1 的槽位全都有。** 搬过去只会制造重复条目——**而重复条目会让注入内容变长、让模型难以判断哪条权威。**

**建议：迁的时候直接丢弃这 10 条**（原件留在 `USER.md` 不动，作为档案）。

## 三、`daily` 轨 → 摘要进 `episode`，全文留档（不需要新概念）

### 3.1 为什么不能整体搬

`daily` 是 **110 天 / 1.42 MB**，平均 13 KB/天。而 fish 记忆条目的中位长度是 **293 字符**。

**把一天的日志原样写成一条记忆，会是一条 13 KB 的记忆——比现有最长记忆大几十倍。** 后果：

- `recall` 会把整段日志当一条结果返回，挤掉别的候选
- 注入包的预算制度（L2 索引按条数）会被一条巨无霸撑破
- 而它根本不是"可复用的事实"，是**流水账**

### 3.2 正确答案：摘要进 fish，全文留 md

| 内容 | 去哪 | 依据 |
|---|---|---|
| "那天做了什么"（1-3 句） | `remember --type episode --occurred-at <ISO>` | fish 已有 89 条 episode 实例，语义完全吻合 |
| 当天的流水细节 | **留在 `daily/*.md`** | 它是档案，不是记忆 |

**这不是妥协**——`daily` 的规范本身就写着分工（`~/.dsh/memories/notes/机制总表.md` 那套）：流水进日志，可复用事实进记忆。

### 3.3 但要补一个参数：`recall` 现在**没有日期过滤**

实测：

```
fish recall --help  →  --limit / --by / --scope / --code / --project / --tags
                       **没有 --since / --until / --occurred**
```

**这意味着：episode 写得进去，但"按日读回来"做不到。**

**这是本设计里唯一需要的代码改动**：给 `recall` 加 `--since` / `--until`（按 `occurred_at` 过滤）。

- 工作量：约 20 行（`fish.py` 的 recall 子命令 + 查询条件）
- 不带这两个参数时行为**逐字节不变**（向后兼容）
- 验收：`fish recall --since 2026-11-01 --until 2026-11-22 --project 大肥鱼生命系统` 只返回这段时间的

## 四、迁移映射总表

| hive 轨 | fish 表达 | 搬迁量 | 备注 |
|---|---|---|---|
| `memory`（全局） | `remember --type fact/rule/lesson`（`project` 空或=全局） | 38 − 7 = **31 条** | 7 条低质量导入丢弃 |
| `user` | `profile_slots` 9 槽 + `--type rule` 1 条 | **9 + 1 条** | 10 条重复导入丢弃 |
| `project` | `remember --project <项目名>` | 已在 fish 里 | 无需搬 |
| `key` | `remember --project <项目> --tags key` + **`profile_proposals` 式的确认队列** | **28 条** | fish 需补一个"建议队列"给记忆（见 4.1） |
| `daily` | `remember --type episode --occurred-at <ISO>`（**只搬摘要**） | 110 条摘要 | 全文留 md |

### 4.1 `key` 轨的确认队列，fish 有现成的模式可以照

hive 的 `key` 轨特殊在：**AI 建议 → 用户确认 → 才进 KEY.md**（写 `SUGGESTIONS.jsonl`）。

fish 的 `profile_proposals` 就是同一个模式（`propose → accepted/rejected/superseded`）。

**所以：给 `key` 记忆也建一张同构的确认表**（或复用 `memory_suggest` 的队列）——这是"用现有表达"，因为模式已经存在，只是没用在 `key` 上。

## 五、两条必须写清的边界

### 5.1 `profile_slots` 是**固定槽位**，不是自由条目

这既是优点也是限制：

- ✅ 优点：结构稳定、有 `version`、有 `permanence`、写入要经 `profile_propose`（AI 不能直接改画像——这是已有的 R1-2 写权分离）
- ❌ 限制：**装不下自由条目**。所以 `USER.md` 里那些"这张图的 .yaml 绑定了记事本"之类的**环境事实**不该进画像，该进 `remember --type fact`

**判断标准**：**"这是关于这个人的，还是关于这台机器的？"** 前者进画像，后者进 fact。

### 5.2 `daily` 摘要由谁写

hive 现在是 AI 每轮自己写 daily（`memory` 工具的 `daily` 轨）。搬到 fish 后：

- **写入仍由 AI 发起**（`remember --type episode`）——fish 不自动生成日志
- **fish 只负责存储与检索**

**这条要写进约定，否则会出现"以为 fish 会自动记日志，实际没有"的落差。**

## 六、工作量与顺序

| 步 | 内容 | 规模 | 可回退 |
|---|---|---|---|
| 1 | `recall` 加 `--since/--until` | ~20 行 | ✅ 干净（不带参数则行为不变） |
| 2 | `profile_slots` 补齐 9 个槽位（对照 USER.md 填值） | 数据操作，0 行代码 | ✅ 原件不动 |
| 3 | 搬 `MEMORY.md` 31 条 → `remember` | 一次性脚本 ~80 行 | ✅ fish 有 `withdraw` |
| 4 | 搬 `KEY.md` 28 条 → `remember --tags key` | 同上 | ✅ |
| 5 | 搬 `daily` 110 天摘要 → `episode` | 要**人工/AI 逐天写摘要**（不能机械截取） | ✅ |

**第 5 步不能自动化**——"那天的摘要"要靠理解，机械截取前 200 字会得到半句话。**110 天需要 110 次判断**，这是真实成本。

---

## 七、我的建议

**先做第 1、2 步（约半天），它们零风险且立刻见效：**

- `recall --since/--until` 一加，`daily` 的归档能力就有了基础
- 9 个槽位一填，**下次会话开始注入的画像就来自 fish 了**（如果同时切换注入源）

**第 3、4 步可以批量做**（86 条记忆，脚本能处理）。

**第 5 步要做，但别指望快**——110 天的摘要是一次性的人力投入，而且**它不阻塞前四步**。

**最后一件事**：这份设计只解决"两轨归属"。**要真正让 fish 成为唯一真相，还得改 hive 的 `memory` 工具与注入段**——那是另一个量级的工程，且在本次约束（不退役 Agent 预设）下需要单独排期。
