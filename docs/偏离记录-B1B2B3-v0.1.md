## R1（主理人裁决）· 记忆索引文件预算：32 KB → **128 KB**

| 项 | 内容 |
|---|---|
| 设计/PRD 原口径 | PRD §6.3：`layout render` 产物单文件 ≤ 32 KB |
| 实际 | `LAYOUT_INDEX_MAX_BYTES = 128 * 1024`（128 KB 硬上限）；超限按行截断并在页内脚注明示；页头常驻「文件预算：上限 128 KB」一行 |
| 实测背景 | 生产 `fish-home/20-记忆库/索引-2026-10.md` 65 KB / 246 行——按 32 KB 判定它"超预算"，但它是**正常月份** |
| 裁决理由 | 32 KB 那条数字来自**看板文件**撑到 396 KB 而读不动的实证；索引不进注入上下文、按月份分片、由人逐行读，口径不能直接搬 |
| 同批改动 | 归属列由完整 citizen ULID 改为 `display_name`（取不到才回落短 id）；标题列截到 48 字（超出加 `…`）；「正文相对路径」列**保留**（HOME-3 要求） |
| 判据 | `test_layout.py::test_memory_index_r1_readable_and_budgeted`；变异见 `docs/变异自证-B1B2B3-v0.1.md` 的 M-B1-1 / M-B1-2 |

## 其它实现自定（不违反设计，但设计没写死）

1. **`_last_active_of` 的日期按时区换算**：库里的 `recorded_at` 是 UTC+`Z`，状态表显示
   `YYYY-MM-DD` 时按 **as-of 的时区**换算（`_pst_local_date`）。设计只写"显示 YYYY-MM-DD"。
   直接截前 10 位会把 `+08:00` 的凌晨记成前一天，与同一页的 as-of 行互相打脸。
2. **`_open_loops_of` 先探一次 `code_index`**：`_open_loop_rows` 对 `sqlite3.Error` 是
   静默返回空列表（注入包的既有容错，改它会动 467 条既有判据）。状态表不能把"表坏了"
   渲染成"未了事项 0 条"，所以在调用前显式探表，让异常走到按列降级。
3. **`include_retired=True` 时 `retired` 列表为空**：退役项目已进主表，折叠区不再重复列
   （否则同一行出现两次，读者会以为有两条记录）。另提供 `retired_total` 供调用方读总数。
4. **`_open_loop_rows` 的 `project` 过滤没有上界（`recorded_at <= as_of`）**：为了与注入包
   保持**同一个查询**（同源优先于"冻结更纯"）。已知代价：as-of 冻结在过去时，之后写入的
   未闭合事项也会被计数。同 as-of 两次渲染仍然逐字节全等（幂等判据不受影响）。
5. **`layout render --all` 不再有占位状态表**：T02 的 `_render_status_table_stub` 已删除，
   由 `render_project_status` 接管（设计 §4.6 ① 的"T03 换成真渲染器"）。
6. **`test_b1b2b3_foundation.py::test_placeholder_commands_exit_2` 改写**：原文断言
   `project status` / `kb vault list` 两个**占位**实现 exit 2。T03/T04 实装后该断言失效
   （继续留着等于"实现了也要假装没实现"）。改为：argparse 三族仍注册、
   `layout render` 缺 `--all` 仍 exit 2、两条命令被真的分派到各自 `cmd_*`（替身函数捕获）。
   判据强度未降：parser 被误删/改名仍会红。

## B3 · 知识库（T04 实现时发现的设计缺口与自定细节）

1. **reparse 检查必须跑在"未解析"路径上（设计 §5.1 伪代码在这一点上是错的）**。
   设计写 `target = realpath(root.joinpath(*parts))` 之后 `_kb_first_reparse(real_root, target)`
   ——`realpath` 已经把 junction 换成目标路径，之后再 `lstat` 永远看不到 reparse 位，
   这个检查会恒返回 `None`。实现改为两条路径并行：`lexical = real_root.joinpath(*parts)`
   （未解析，用于 ⑤ 逐级 reparse）与 `target = realpath(lexical)`（真实落点，用于 ④
   commonpath 与 ⑥ 存在性）。判据 `test_junction_inside_vault_to_inside_dir_is_reparse_point`
   与变异 M-B3-6 钉住这一点。
2. **`_kb_ignored` 同时试"文件形态"与"目录形态"**（`rel` 与 `rel + "/"`）。设计只说
   "对路径本身与每一级祖先目录分别匹配"；实测只按祖先补 `/` 时，`.obsidian/**` 能挡住
   `.obsidian/app.json`，却挡不住 `kb open .obsidian`（同一规则对同一棵树给两种答案）。
3. **`write_id` 不写回 `kb_access.meta`**。设计 §3.5 写"meta.write_id"，但 `write_id` 的
   前缀就是该行 `id`，写回等于对"只增不改"的审计表做 UPDATE。实现：先写流水拿 id →
   `write_id = f"{id}-{8hex}"` → 写进**备份目录**的 `meta.json` 并随回执返回。
   > **2026-10-26 第二轮修订（R4）**：原文写"`rollback` 只解析前缀定位行（不依赖 meta）"，
   > 那是当时的实现，正是评审 🟠-3 指出的缺陷（8 位后缀不参与校验 → 旧凭据可删新文件）。
   > 现在 `rollback` **必须**读备份 `meta.json` 的 `write_id` 做全串相等校验，不符 →
   > `not_found` 且文件不动；备份里没有 `write_id`（历史备份）同样拒绝。
   > 判据 `test_b3_round2.R4RollbackWriteIdTest`，变异 M-B3-6 之外另见 M-R1..M-R15 段。
4. **`kb_tree` 的返回形状**：`dirs` 按 §3.5 给"起点下的**一级目录**"；另加 `summary`
   （起点的合计：rel/notes/attachments/bytes/more/children），因为树根自身的读数
   在 `dirs` 里没有位置。文本渲染只走 `summary` + 递归 `dirs`（不重复列同一批条目）。
5. **`append` 不要求 `base_sha256`**（设计未要求）。诚实标注代价：append 读旧字节→拼→
   原子替换，中间若有人改动会被覆盖；`update` 有乐观锁，append 没有。下一批若把 append
   也纳入"高价值写"，建议补 `--base-sha256`（改法是加一个可选校验，不动既有调用）。
6. **CLI 的 `--append` 与 `--frontmatter` 互斥**（`bad_usage`，exit 2）：追加不该动文件头。
   实现细节：CLI 把 `--frontmatter` 解析成 `{}`，所以校验用 `if frontmatter and ...`
   而不是 `is not None`——第一版用 `is not None` 时 CLI append 恒被判用法错误（验收
   6f 抓到，测试 `test_cli_append_without_frontmatter_works` 已补）。
7. **Obsidian CLI 探测不启动 app**：设计提到 `Obsidian.com --version`（5 s 超时），但
   该命令可能把 app 拉起来，与"只探测、不打扰"冲突。实现改为 `shutil.which` +
   `tasklist /FI "IMAGENAME eq Obsidian.exe"`；找不到或没运行 → `unavailable`，
   读写在两种状态下都照常（KB-14 的判据只认 `available` 布尔）。
8. **`kb_stats` 的"未读"是估算**：`未读 = 当前 .md 数 − 有 open 记录的去重路径数`。
   文件被改名/删除会让这个差值偏大；页面上标为「未读（估算）」，不做精确统计
   （精确统计要维护集合，超出本批范围）。
9. **空路径的语义**：读路径（tree）= vault 根（合法）；写路径 = `path_invalid`。
   > **2026-10-26 第二轮修订（R7）**：`kb open` 的目标是**文件**，所以空路径（解析到库根）
   > 与显式目录一律 `bad_usage`（原实现会在 `read_bytes()` 上抛 `PermissionError`，CLI 出
   > traceback）。设备名（NUL/CON/COM1）、含 NUL 字符、ADS 形态（`x.md:hidden`）→
   > `path_invalid`。四类输入都会落一条 `reject` 审计（`_kb_guard` 现在也兜 `OSError`）。
   > 判据 `test_b3_round2.R7BadPathDomainErrorTest` / QA `test_qa_b1b2b3.QAKBPathTest`。
10. **`result` 词表只有 10 个值**（`KB_RESULTS`，第二轮加了 `sensitive`），错误码有 20 个。
    拒绝落审计时 `mode_ro` / `exists` / `path_invalid` / `content_too_large` /
    `reparse_point` 等不在词表里 → 一律记 `result='denied'`（`_kb_reject`）。
    > **2026-10-26 第二轮修订（R18）**：原文写"原始 code 放在 `meta.reason`"——那是文档
    > 口径，实现当时只把中文说明放进去（评审 🟡-3 抓到的漂移）。现在 `meta.reason_code`
    > 存**错误码**，`reason` 只存截断中文（≤160 字）；两者都进 `KB_META_KEYS` 白名单。
    > 判据 `test_b3_round2.R18ReasonCodeTest`。
11. **`kb open` 的三句声明是固定文案**（判据认其中关键词：`知识库（未建索引）` /
    `按需扫描` / `已截断|未截断`）。第三句补了字节与字符两个比例，方便判断"截掉了多少"。

## T05 · MCP 工具面（T05 实现时发现的设计缺口与自定细节）

1. **设计 §6.1 的"必须改的既有测试"清单漏了 3 个文件（实测才发现，不是口味问题）**。
   设计只列了 `p0/test_mcp.py` 一处集合断言；实测全量跑下来，另外三个文件也把**工具集合**
   冻成了字面量，加工具必然红：
   - `test_identity_p1b.py::test_H_no_mcp_session_tool`（模块常量 `MCP_TOOL_NAMES`）；
   - `test_identity_p1c.py::test_G_tool_signature_only_adds_optional_token`（`len(names)==16`
     + `BASELINE_TOOL_PROPS` 逐工具字段）；
   - `test_push_p0.py::test_G_tool_contract_unchanged`（工具名单 + 逐工具字段集）。
   处理方式：**只加 `kb` / `kb_write` 两个名字与它们声明的业务字段**，`16 → 18`；
   三处仍是"集合/字段集严格相等"，判据强度一个字没降（误删一个工具照样红）。
   教训（写给下一批）：**"改工具面必须同提交更新 test_mcp.py"这条纪律不完整**，
   真实的判据面是"任何把工具表冻成字面量的测试"，grep 口径应是 `mcp_server.TOOLS`
   而不是文件名。
2. **MCP 的 `open` 默认 `max_chars=8000`，CLI 是 64000**。schema（设计 §3.3）只声明了一个
   `max_chars`（默认 8000），MCP 回执要进模型上下文，所以按 schema 取 8000；
   CLI 的 64000 面向"人逐段读"。差异在回执里明说（`已截断：显示 A/B 字；要更多请显式传 max_chars`）。
3. **`kb(action="vaults")` 也落一条 `kb_access`**（`vault_id=""` = 整个库级动作，
   `action='vaults'`，`meta.reason='list_vaults'`）。设计只说"列已注册库"，没说要不要审计；
   落一条的理由：`vaults` 是"AI 知道了你的库长什么样"这一步，与 tree/open/search 同属读面。
   失败静默（K4），列清单本身不因审计写不进而失败。
4. **整数入参在服务端再夹一次**（`_kb_int_arg`）。schema 声明了 `depth 1..4` / `limit 1..30`，
   但 schema 不是判据——手写 JSON 的客户端可以不遵守；`depth=100` 会把一次调用炸成几万行，
   且**不会报错**。实现夹到 `[lo,hi]`，非整数 → 工具错误（`isError=true`，不崩服务）。
5. **`kb_write` 的 `frontmatter` 非对象 → 工具错误；`reason` 超 200 字 → 截断而非拒绝**。
   理由不该成为"写不进去"的原因，但审计里也不能长出无界文本（§5.6）。
6. **`open` 三行头的第三行格式**：`truncated=false / shown=4344/2097152 bytes`
   （设计 §3.3 写的是 `truncated=true|false, shown=A/B bytes`）。取 `/` 作分隔、`shown`
   用"字节/上限"，与 tree/search 的 `scan=N files / M bytes / x ms` 保持同一种标点习惯。
7. **新增 `p0/mutation_t05_selfcheck.py`**（设计只要求"变异留痕"，没指定执行器）。
   必须新写一个的理由：T05 的判据在**进程边界**上（工具表 / JSON-RPC 分发 / `isError` 转换），
   `mutation_b2b3_selfcheck.py` 那种"改 fish.py 跑库内单测"的形状证明不了工具面。
   5 条变异 + 对照组，读数见 `docs/变异自证-B1B2B3-v0.1.md` §4。

### 1. 敏感文件默认拒读（R15 · 安全 F4）——**这是本批最重要的行为变更**

- 旧：`kb open 80-资料库/凭证管理_v1.0.md` 直接返回全文；`kb search 密码` 会把凭证行做成片段。
- 新：命中内置名单（`*凭证*`/`*credential*`/`*secret*`/`*密码*`/`*.pem`/`*.key`/`id_rsa*`/`.env*`）
  → `KBError('sensitive')`，文案给**文件名 + 大小 + "建议在 Obsidian 里打开"**；
  要正文必须显式 `--allow-sensitive`（CLI）/ `allow_sensitive=true`（MCP）；`kb search`
  对这些文件只计数（`scanned.skipped_sensitive`），不进片段。
- 为什么这是"变更"而不是"修 bug"：它改变了一条**合法读**的默认结果。裁决 R15 明确要求如此
  （凭证类的读取必须是二次授权），并且名单**不可由用户删除**（`KB_DEFAULT_IGNORE_GLOBS`
  之外的独立常量，重登记 vault 也消不掉）。
- 判据：`test_b3_round2.R15SensitiveTest`（3 条）；变异 M-R15。

### 3. `kb tree --depth` 真的裁剪（R3 · 评审 🟠-2 / 安全 F6）

- 旧：`max_depth` 是死代码，层数由仓库结构决定；根节点渲染成 `//`；每次调用遍历两遍。
- 新：`level == max_depth` 的目录**仍扫**（给直接子文件计数）但**不下钻**；`depth=1` 的
  `scandir` 次数 = 根 + 一级目录数；根节点用 **vault 名**；`summary` 与 `scan` 来自**同一次**遍历。
- 诚实标注：合计只覆盖已展开的层（`scan.partial=true` + `scan.hidden_dirs=N`，
  文本里明说"还有 N 个下级目录未展开，不统计不下钻"）。这条是**与"全树统计"的取舍**：
  本轮按裁决优先"深度契约 + 受控成本"，用 partial 标注代替假装完整。
- 判据：`test_b3_round2.R3TreeDepthTest`（3 条，含 `os.scandir` 打桩计数）；变异 M-R3。

### 1. `allow_sensitive` 改严格布尔解析（N7 · 安全 🟡）——**这是本轮的 fail-open 修复**

- 旧：MCP 两个入口都是 `bool(a.get("allow_sensitive"))`。`bool("false") is True`，
  于是宿主/模板/YAML 把布尔渲染成字符串时，`"false"` / `"0"` / `"true"` / `1` **全部放行**
  （只有整数 `0` 被拒）——一个"看起来拒绝、实际同意"的授权旗。
- 新：`fish._strict_bool(value, name)` 是**唯一**解析点。接受 `True/False`、`1/0`、
  `"true"/"false"/"1"/"0"`（大小写与首尾空白不敏感）；`None`（不带键）= **缺省即拒绝**
  （与 schema `default: False`、CLI `store_true` 同义）；其余（`"yes"` / `"on"` / `"真"` /
  `""` / `2` / 浮点 / 列表）→ `KBError('bad_usage')`，**不猜**。
- 落点：解析放在 `_kb_open_impl` / `_kb_write_impl` 的**第一行**，不是只放在 MCP 层——
  CLI、MCP、直接调 `fish.kb_open` / `fish.kb_write` 三方共用一条规则，没有通道能绕过；
  两处 CLI 命令（`_kb_cmd_open` / `_kb_cmd_write`）同时去掉 `bool()` 强转，转换只发生在一处。
- 判据：`test_b3_round2.N7StrictBoolTest`（6 条：假写法必拒 / 真写法必放 / 模糊写法
  `bad_usage` + `reason_code` / 写面同解析 / 审计留痕 / `None` 缺省拒绝），
  `test_mcp_kb.MCPKBToolsTest.test_15_allow_sensitive_needs_explicit_boolean`（进程边界上验读+写两面）。
  变异 `M-N7`：把 `_strict_bool` 退回 `return bool(value)` → `test_read_face_false_spellings_do_not_authorize` 必红。
- **残余（登记，不修）**：flag 仍在模型手里（设计面，见安全审计 R-10① 与 N6 残余）——
