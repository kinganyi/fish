## 发现清单

### 🔴 致命

#### 🔴-1 `kb_search` 失败时把 **query 原文**写进 `kb_access.path`（隐私硬边界被破）

- **位置**：`p0/fish.py:11539-11551`（`kb_search` 把 `query` 当 `rel` 传给 `_kb_guard`）→ `p0/fish.py:11267-11273`（`_kb_guard` 把该值原样交给 `_kb_reject`）→ `p0/fish.py:11259-11264`（`_kb_reject` 写入 `kb_access.path`）
- **问题**：`kb_search` 的第二个位置参数是 `query`，`_kb_guard` 的同名形参是 `rel`，一次「语义借用」把检索词当成路径落库。成功路径没事（`_kb_search_impl` 自己用 `rel=""` 记流水），**只有失败路径泄漏**。
- **为什么是致命**：裁决 §四.6 与 PRD §7.5 是**硬边界**：「`kb_access.meta` 只存 `query_hash`（sha256 前 12）、不存 query 原文」，理由是「人的搜索词可能涉私密（凭证、姓名、金额）」。`kb_access` 是**只增不删**的审计流水，一旦落库不可撤回、不可改正，等于给知识库永久加了一份搜索历史。附带损害：`kb_path_stats` / `kb_stats` 的「未读率」会把这些伪路径当真实路径统计。
- **证据（事实，实测两态）**：
  ```
  # 离线（vault 目录被删）：
  kb_search(conn, vault, "银行卡密码-张某某-1234567") → KBError('offline')
  kb_access 行：('银行卡密码-张某某-1234567', 'reject', 'offline')
  # 在线但 limit 非法：
  kb_search(conn, vault, "私密词-某公司-欠款-88888", limit="abc") → KBError('bad_usage')
  kb_access 行：('私密词-某公司-欠款-88888', 'reject', 'denied')
  ```
  两条都已用临时库复现（脚本见文末 V3）。现有测试**未覆盖**这一路径（`test_kb_security.py:238` 只断言 `meta` 的键集合，未断言 `path` 列内容）。
- **修法建议**：`_kb_guard` 拆出显式参数——读/写路径传 `rel`，`kb_search` 传 `rel=""` 并把 `query_hash` 单独透传（`_kb_guard(..., rel="", audit_meta={"query_hash": …})`）；同时补一条判据：**任何 `action='reject'` 行的 `path` 必须能通过 `kb_resolve_target` 的合法性校验**（或直接断言 `path` 不含 `query` 的任何子串）。

### 🟠 严重

#### 🟠-1 非 UTF-8 文件的写路径：`append` 静默损坏、`update` 抛裸异常

- **位置**：`p0/fish.py:11886-11917`（`_kb_write_impl`：`kb_detect_text` 只用了 `media`/`is_text` 两个字段，**从不检查 `encoding` 是否 utf-8 族**；`append` 直接 `before + addition.encode("utf-8")`；`update` 里 `before.decode("utf-8", errors="strict")`）
- **为什么是问题**：设计 §5.8 降级矩阵明写「非 UTF-8 → **写路径：拒绝（不写不确定编码）**」，KB-12 同口径。实际实现把两种损坏都放进来了：
  1. **`append` → 文件混合编码（静默数据损坏）**：原 GB18030 字节保留，追加段是 UTF-8 → 文件既不是 GB18030 也不是 UTF-8；写后校验 `kb_sha256_file == written["sha256"]` **必然通过**（比的是"我写进去的字节"），回执打印「校验=通过」，AI 与人都看不出已把人的笔记弄坏。
  2. **`update` → 裸 `UnicodeDecodeError`**：不是 `KBError`，`_kb_guard` 只转 `KBError`，`cmd_kb` 只捕 `KBError`/`sqlite3.Error` → CLI 打 Python traceback（不是 `错误[bad_encoding]`），MCP 侧丢掉契约里承诺的 `bad_encoding` 码。
- **证据（事实，实测）**：
  ```
  # 文件 = "# 中文标题\n\n这是 GBK 编码的正文。\n".encode("gb18030")
  kb_detect_text → {'is_text': True, 'encoding': 'gb18030', ...}      # 认得出是 GB18030
  append    → 成功，回执 verified=True；结果 decode('utf-8') 失败：'utf-8' codec can't decode byte 0xd6
  update    → UnicodeDecodeError @ fish.py:11917（traceback 见 V2 脚本输出）
  ```
  现有测试只钉了**读**路径（`test_kb_security.py:197 test_gb18030_is_readable`），写路径对 GB18030 **零覆盖**。
- **修法建议**：在 `_kb_write_impl` 拿到 `before` 后加一档：`detected["encoding"] not in ("utf-8", "utf-8-sig")` → `KBError("bad_encoding", …, hint="另存为 UTF-8，或用 Obsidian 转码后再写")`；`update` 的 `decode` 改用同一 `encoding`（或先过上面那道闸，永不用 strict-utf8 裸解）。补两条判据：GB18030 + append / update 各一条，断言 `KBError.code == "bad_encoding"` **且文件字节未变**（sha256 前后相等）。

#### 🟠-2 `kb tree --depth` 完全不生效（KB-2 / P0 的契约未实现，且注释与实现相反）

- **位置**：`p0/fish.py:11279-11337`（`_kb_tree_dir` 收了 `level`/`max_depth`，**全程没有一次比较**，`11308-11309` 无条件向下递归）+ `p0/fish.py:11353-11366`（`_kb_tree_lines.emit` 递归所有 `dirs`，无层数上限）+ `p0/fish.py:11427`（传参处）
- **为什么是问题**：KB-2 是 **P0**：「默认 **2 层**（`--depth` 可配 1–4）」。实际输出层数由仓库结构决定，最后被 8000 字符预算**从中间截断**——用户要"浅层总览"，拿到的是"深层树的前 8000 字"，且断点在一个节点内部。附带两个具体缺陷：
  1. 根节点渲染成 `- // 3 篇笔记 …`（`11355-11356`：`name = node["rel"] or "/"` 再拼 `"/"`）；
  2. `_kb_tree_dir` 的 docstring（`11283`）写着「深度超过 `max_depth` 不再下钻」——**这句话与实现相反**。这正是本批"注释仍可信吗"该抓的那类漂移，且 `docs/偏离记录` 未登记此偏离。
- **证据（事实，实测）**：同一棵树（`A/x.md`、`A/B/y.md`、`A/B/C/z.md`）分别 `depth=1 / 2 / 3` 调用，三次输出**除 as-of 行外完全一致**（chars 均 498），`depth=1` 仍列出 `A/B/`、`A/B/C/` 与 `z.md`——见 V1。
- **修法建议**：`_kb_tree_dir` 里 `if level >= max_depth: 只统计不下钻`（统计仍要全树以给每目录汇总，但 `dirs` 不再下发）；`emit` 增加 `if level >= depth: return`；根节点用 vault 名而不是 `//`。判据：造 4 层树，`depth=1` 的输出**不得含**第 3 层及以下的目录/文件名（断言字符串不存在），并断言 `depth=1` 的 `chars` 明显小于 `depth=4`（防"预算截断凑巧相等"）。

#### 🟠-3 `kb rollback` 不校验 `write_id` 的 hex 后缀 → 回滚凭据可伪造

- **位置**：`p0/fish.py:11971-11980`（正则 `^(\d+)-([0-9a-fA-F]{4,32})$` 匹配后只用 `m.group(1)` 查行，后缀**丢弃**）
- **为什么是问题**：设计 §3.5 明写「`write_id = <kb_access.id>-<8hex>`…**后缀防跨库/跨年碰撞**」，并把它当"精确找到那次写"的可撤销凭据交给用户/AI。实现只认前缀，等于后缀是装饰：任何 4–32 位十六进制都能"通过"。真风险场景是 `index.sqlite` 被重建/换快照后 `AUTOINCREMENT` 重排——旧 `write_id` 会命中**另一次写**，而 `create` 的回滚动作是**删文件**（`11917-11920`），即"用旧凭据删掉别人的新笔记"。
- **证据（事实，实测）**：`kb_write` 返回 `write_id=4-970e0281`；用 `4-deadbeef` 调用 `kb_rollback` **被接受并执行**，`removed=True`，文件被删除（见 V1）。测试只覆盖"存在/缺失"两态，未覆盖"后缀不匹配"。
- **修法建议**：`rollback` 把 `meta.json` 里的 `write_id`（`_kb_backup_finalize` 已经写了，`11946-11948`）读回来做**全串相等**校验，不匹配 → `KBError("not_found"/"bad_usage")`；或把后缀改成对 `(id, vault_id, rel, sha256_after)` 的短摘要，从而真正起到篡改检测作用。补判据：错后缀必须红（且文件仍在）。

### 🟡 警告

#### 🟡-1 `_layout_write` 的"禁止写进 data_root"断言在 6/9 个调用点没生效

- **位置**：`p0/fish.py:9275-9298`（`data_root=None` 时第三条断言整段跳过）；未传 `data_root=` 的调用点：`fish.py:9378`（README）、`9427`（索引降级分支）、`9481`（索引）、`9502`（最近降级分支）、`9515`（最近）、`9556`（vaults）。传了的三处：`9711`（系统页）、`9758`、`10553`（状态表）。
- **问题**：设计 §6.4 声称"所有门面写盘只经 `_layout_write`，它内部 `assert` …且不在 `data_root` 内"，实现只有 1/3 的路径真正带这条闸。**当前不可利用**（`resolve_home_root` 已先断言 home 不在 data_root 内），属纵深防御缺口。
- **修法**：`render_layout` 系调用链统一传 `data_root`（或把 `data_root` 做成 `_layout_write` 的必有参数），并加一条判据：把所有 README/索引渲染函数单独喂一个 `home_root == data_root` 的用例，必须 `RuntimeError`。

#### 🟡-2 `_ensure_boards_home_paths` 的注释自相矛盾；未知 scope 会打断 `migrate()` 全链

- **位置**：`p0/fish.py:8039-8065`
- **问题**：docstring 同时写了「未知 scope **一行不碰**」与「出现未知 scope 时它抛 `ValueError`，那是数据病，要让人看见」——两句互斥。实际行为是后者：`board_relpath` 对未知 scope `raise ValueError`（`fish.py:7993`），而该函数挂在 `migrate()` 链尾，`migrate()` 被**每条命令**（含 hook）调用 → 一行脏数据会让全系统起不来。另外每次 `migrate()` 都做一次全表 `SELECT`（7 行目前无痛）。
- **修法**：docstring 二者取一（建议保留"看得见"的语义，但把异常收窄成 `degraded` 记录 + 跳过该行，避免"一条脏数据锁死所有命令"），并明确"未知 scope 计入 `layout render` 的 degraded 段"。

#### 🟡-3 审计里"拒绝原因码"丢失，且与偏离记录不一致

- **位置**：`p0/fish.py:11259-11264`
- **问题**：`_kb_reject` 把 `exc.message`（中文说明）写进 `meta.reason`，`result` 在 code 不在 `KB_RESULTS` 时统一降级为 `denied`（`KB_RESULTS` 只有 9 值，而错误码 19 个）。`docs/偏离记录-B1B2B3-v0.1.md` §B3-10 却写「原始 code 放在 `meta.reason`」——**文档与实现不符**：按现有实现，`mode_ro`/`exists`/`reparse_point` 这些码在库里一个字都不留（只留中文）。后果：想统计"最常见的拒绝原因"必须正则猜中文。
- **修法**：`meta={"reason_code": exc.code, "reason": message[:160]}`（`KB_META_KEYS` 加一个 `reason_code`，白名单机制已就位），并同步改偏离记录那句。

#### 🟡-4 `board_render` 里根板刷新失败被 `except Exception: pass` 吞掉；落点算式有 3 处

- **位置**：`p0/fish.py:8784-8787`（`try: board_render_root(...) except Exception: pass`）、落点算式 `fish.py:8680`、`8762`、`8775`（均为 `home / board["path"]`）与 `fish.py:8007`（`board_out_path` 的同一算式）
- **问题**：① 根板是聚合视图，失败静默 → "根板停在昨天"这件事对渲染者、对 `layout verify` 都不可见（verify 只查链接目标存在，不看时效；`stale_render` 查的是 as-of 而非看板）。② 设计 §6.2 说 `board_out_path` 是**唯一落点入口**，实际 `board_render`/`board_render_root` 各拼一次——今天同式故无 bug，但"改口径漏改一处"的窗口开着。
- **修法**：失败至少 `print(..., file=sys.stderr)` 或进 `board_render` 的返回 dict；三处改成调 `board_out_path(root, board, home_root=home)`。

#### 🟡-5 `render_layout` 的 `degraded` 收集不全，且 `attempt()` 只捕 `OSError`

- **位置**：`p0/fish.py:9781-9789`（`attempt` 只 `except OSError`）、`9763-9866`（`degraded` 只在 `code_registry` 查询失败与凭证拦截两处 append）
- **问题**：`render_memory_index`/`render_memory_recent`/`_vaults_projection` 的降级**在函数内部**完成并返回 `degraded=True`，`render_layout` 只把它算进 `written`，**不汇总到 `degraded`** → CLI 不打印「降级」行、`--json` 不反映（文件里的"数据源不可用"段还在，HOME-9 的字面要求满足）。另外除 `OSError` 外的异常会从 `render_layout` 逃出，与设计 §4.6「异常按源记 degraded 而不中断」不一致。
- **修法**：`attempt` 里 `res.get("degraded")` 时往 `degraded` 追加一条；`attempt` 的 `except` 扩到 `(OSError, sqlite3.Error)` 并把其余异常按源降级（`Exception` 只在这一层兜一次，留 `_exc_text`）。

#### 🟡-6 `kb tree` 每次调用遍历整棵树**两遍**

- **位置**：`p0/fish.py:11427-11435`（先 `_kb_tree_dir` 递归一遍，再 `_kb_walk` 走一遍只为拿 `files`/`bytes` 两个数）
- **问题**：`scan.files`/`scan.bytes` 与 `summary` 里的同类数据来自两次不同的遍历，成本约 2×（设计预期 586–652 ms，真库上实际约翻倍；`--depth` 又不起作用，`--depth 1` 与 `--depth 4` 同价）。两遍之间若文件变动，两个数字会互相打脸。
- **修法**：`summary` 已有 `notes/attachments/bytes`，只需在 `_kb_tree_dir` 里一并累计 `files`，删掉第二次 `_kb_walk`。

### ⚪ 遗漏

#### ⚪-1 HOME-6 判据的范围小于条文（CLI 级会写 `data_root`）

- **条文**：HOME-6「渲染前后对 `p0/data` 做文件清单 + mtime 快照比对，必须**零变更**」。
- **事实**：`test_layout.py:183 test_data_root_untouched` 只包住函数级 `render_layout()`。CLI 级 `fish layout render --all` 会先 `connect()` + `executescript(SCHEMA)` + `migrate()`（`fish.py:10126-10128`），实测在**全新根**上首跑会在 `data_root` 下新建 `index.sqlite`（V4）。已存在库上重跑无 diff（我实测 `REPEAT render → data_root diff: none`）。
- **判断**：这是既有命令的通用模式（不是本批引入），实际危害小；但判据与条文的口径差应写进偏离记录，否则"零变更"会被当成已证明。
- **建议**：判据补一句"以已初始化库为起点"，或在 CLI 级快照里排除 `index.sqlite`（`-wal`/`-shm`）。

#### ⚪-2 `kb_backup` 同秒同路径的第 50 次写会静默覆盖旧备份

- **位置**：`p0/fish.py:11776-11782`（`for idx in range(2, 50)` 找空位；全满时 `base` 仍是原目录，`mkdir(exist_ok=True)` 后 `payload` 被覆盖）
- **判断**：极窄（同一秒、同一 rel 的第 50 次写），但后果是"回滚点被后来的写顶掉"且无提示。
- **建议**：循环耗尽时 `raise KBError("backup_missing"/"bad_usage", …)` 或改用 `uuid` 后缀，别复用已存在目录。
