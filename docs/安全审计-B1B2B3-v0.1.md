## 2. 发现详述

格式：**位置 → 攻击路径 → 影响 → 修法 → 证据 → 判据面缺口**。

### F1 🟠 忽略规则被 Windows 大小写 / 尾随空格绕过

- **位置**：`_kb_ignored`（`p0/fish.py:10885-10910`，用 `fnmatch.fnmatchcase`）＋ 默认规则 `KB_DEFAULT_IGNORE_GLOBS = (".obsidian/**", ".trash/**")`（L10627）。命中点在 `kb_resolve_target` 的 ③（L10983）与 `_kb_walk`/`_kb_tree_dir`（L11136/L11304）。
- **攻击路径**（实测，两条都通）：
  1. MCP `kb(action="open", path=".OBSIDIAN/app.json")` → `fnmatchcase` 大写不匹配 `.obsidian/**` → 放行 → 读到 Obsidian 配置（实测返回 `vimMode` 等键）；
  2. MCP `kb_write(action="create", path=".OBSIDIAN/坏插件.json")` → 父目录存在 → **在真实 `.obsidian/` 里建出文件**（实测落盘成功）。
  3. CLI 同形：`fish kb open ".obsidian /app.json"`（`obsidian` 后一个空格）也被放行——Windows 会剥掉组件尾随空格。
- **影响**：§5.2 / §7.4 / 用户文档（`知识库接入与回滚说明.md` L17、L114）三处都承诺"`.obsidian` 读不了、也不许写"。实际可读配置 → 泄露 vault 路径、插件清单、同步账号信息；可写 → AI 能把 Obsidian 配置写坏（应用起不来 / 插件失效），属**完整性事故**且可被 prompt 注入触发。
- **修法**（二选一，推荐 A）：
  - A：忽略判定前把路径组件 `normcase` 归一，并把每段 `rstrip(". ")` 后重拼（只用于**判定**，不改变真实落点）；`.obsidian` → 一律 `.obsidian` 比较；
  - B：把默认忽略改成"组件黑名单 + 大小写不敏感比较"（`.obsidian`、`.trash`、`.git`、`.obsidian-*`），glob 只留给用户自加规则。
- **证据**：探针 P1（`_kb_resolve_target` 对 `.OBSIDIAN/app.json` 返回 RESOLVED，`kb_open` 返回 READ_OK 25 B）、P17（MCP 通道读成功）、P17c（MCP 通道写入后 `VAULT/.obsidian/坏插件.json` 存在=True）、P2（`.obsidian /app.json` 也 RESOLVED）。
- **判据面缺口**：`test_kb_security.py::test_ignored_paths_are_rejected_even_when_existing` 只测小写原样写法；18 条判据全绿而此洞仍在。建议加：`for rel in (".OBSIDIAN/app.json", ".obsidian /app.json", ".TRASH/x.md")` 三条必须 `ignored`。

### F2 🟠 `kb search` 失败时 query 原文落进审计表

- **位置**：`kb_search(conn, vault_row, query, ...)` 把 **query 当作 `rel`** 传给 `_kb_guard`（L11548）→ `_kb_reject(conn, vault_row, rel, exc)`（L11259）→ `_kb_log_quiet(..., rel=rel)`（L11262）→ 写 `kb_access.path`。
- **攻击路径**：库离线（盘拔/目录改名）或 `limit` 非整数时，`fish kb search "某私密词"` → 抛 `offline`/`bad_usage` → 审计行 `action='reject', path='某私密词'`。`fish kb stats` 的「最近变更」直接把 `path` 打印出来（实测可见）。
- **影响**：直接违反 PRD §7.5 与裁决 §四.6（"`kb_access` 不存 query 原文"）。搜索词恰恰是"人不想留痕"的那类内容（凭证、姓名、金额、病情）。这也让 §5.6 的白名单（`query_hash`）在失败路径上形同虚设。
- **修法**：`kb_search` 里不要复用 `rel` 通道——`_kb_guard(conn, vault_row, "", fn, ...)` 或给 `_kb_guard` 加 `audit_rel=` 参数，失败行一律 `path=''`；query 只以 `meta.query_hash`（L11624 已有）出现。同时 `_kb_reject` 的 `meta.reason` 也要截掉 query（`offline` 文案里没有 query，安全）。
- **证据**：探针 P9（offline 后 reject 行 1 条，`path` 含探针词；`limit="abc"` 再 1 条）；P18（同一探针词出现在 `fish kb stats()["text"]` 里 = True）。真实副本库已有 20 行 `kb_access`，其中 `search`/`search_hit` 的 path 为空或文件相对路径——说明**成功**路径是干净的，洞只在失败路径。
- **判据面缺口**：`test_meta_never_contains_query_or_body` 只跑成功路径。建议加：先让 vault 离线再 `kb_search`，断言 `SELECT path FROM kb_access WHERE action='reject'` 里不含探针词。

### F3 🟠 MCP 写面没有身份门槛（无 token 也能写）

- **位置**：`tool_kb_write`（`p0/mcp_server.py:1533-1586`）→ `fish.kb_write(..., citizen_id=ident.citizen_id)`；`ident` 无 token 时是 `IDENTITY_ANONYMOUS`（`citizen_id=None`），`kb_log_access` 把它映射成 `'unattributed'`（L11243）。`_attach_token`（L123）刻意**只加 optional、绝不进 required**。
- **攻击路径**：任何能连上 MCP 的客户端/会话（包括没跑过 `session_start`、或 token 已过期被降级成 `none` 的那一个）调 `kb_write` → 对 `mode=rw` 的库 `create`/`update` 成功。实测：`create` 成功（`isError=False`），审计行 `('unattributed','mcp:kb_write','create','ok')`；用真 sha256 对既有笔记 `update` 也成功。
- **影响**：写操作**无法归属到会话**（`kb_access` 只存 `citizen_id`，连 `session_key` 都没存），事后无法回答"是哪个 AI 改的"。对比：`tool_board` 的 checkin/post 明确拒绝无 token（实测 `isError=true`）。同一产品里"写看板要凭证、写知识库不要凭证"，这是口径分裂，不是设计选择。
- **修法**（两条都合法，请主理人拍：这是**口径决定**，不是纯技术缺陷）：
  - A（推荐）：`tool_kb_write` 在 `ident.citizen_id is None` 时返回 `isError=true`（文案同 board），并把 `session_key` 写进 `kb_access.account_id`；CLI 面保留"本地可信"不要求 token。
  - B：维持现状，但在 PRD §6.2 与 `知识库接入与回滚说明.md` 里显式写"授权来自 `mode=rw` 的人工登记，凭证只用于归属"，并把 `unattributed` 写升级为"红色告警"提示。
- **证据**：P10（`kb_write create` 无 token → `isError=False`）、P10b（审计行 `unattributed`）、P10c（无 token `update` 既有笔记成功）、P10b-对照（board checkin 无 token → `isError=true`）。反证：`test_mcp_kb.py::test_11_kb_write_rw_creates_backup_and_audits_unattributed` **把这个行为写成了断言**——即这是实现者有意的，不是漏写。
- **判据面缺口**：现有判据把"无 token 可写"锁成了期望行为；若采纳修法 A，需同步改 `test_11`（并保留一条"有 token 时归属正确"的正面判据 `test_13`）。

### F4 🟠 知识库里的凭证文档可被无条件读出

- **位置**：`kb_open`/`_kb_open_impl`（L11470-11528）、`_kb_search_impl`（L11554-11655）；防线只有 `KB_DEFAULT_IGNORE_GLOBS`（不含任何凭证类模式）、`KB_MEDIA_EXTS`（只挡二进制）、`max_open_bytes`（2 MiB）。
- **攻击路径**：MCP `kb(action="open", path="80-资料库/凭证管理_v1.0.md")` → 6970 B / UTF-8 / 非媒体 → 判定为可读文本 → 正文整篇进回执 → 进模型上下文 → 进宿主会话日志（而 `.gitignore` L25 恰恰把"含历史 token 明文"的会话全记录列为不可提交 —— 同一类内容从这个口子绕过去了）。`kb search "密码"` 同理会把这些行做成 snippet 返回。
- **影响**：本机唯一的凭证权威文件（其 Obsidian 副本）在知识库内，且格式/大小完全满足 `kb open` 的可读条件（实测 `is_text=True, encoding=utf-8, 6970 B < 2 MiB`）。一旦被读，凭证值进入**不可撤回**的上下文链路（多轮对话、宿主日志、可能的第三方模型路由）。
- **修法**：
  1. 默认 deny 名单（与 `KB_DEFAULT_IGNORE_GLOBS` 同级、不可被用户删除）：`**/*凭证*`、`**/*credential*`、`**/*secret*`、`**/*密码*`、`**/*.pem`、`**/*.key`、`**/id_rsa*`、`**/.env*`；
  2. 命中时不返回"ignored"（否则人不知道为什么读不了），而是返回 **`sensitive` 码 + 文件名 + 大小 + "请在 Obsidian 里打开"**，并要求 `--allow-sensitive` 显式二次授权才给正文；
  3. 文档同步：`知识库接入与回滚说明.md` 的"不敢读清单"一行。
- **证据**：`_kb_resolve_target` 对该路径返回 ok（未被忽略规则拦下）；`kb_detect_text` 判 `is_text=True`；`len=6970 < 2097152`；本报告**未打印其任何内容**。
- **判据面缺口**：目前没有一条判据覆盖"敏感文件名"。建议加 3 条：`凭证*.md`/`*.pem`/`.env` 必须 `sensitive`；`--allow-sensitive` 才给正文；`kb search` 不得把它们的行做成 snippet。

### F5 🟡 写路径缺 `max_open_bytes` 上限（读写口径不一致）

- **位置**：`_kb_write_impl` 的 `before = abs_path.read_bytes()`（L11886）——之前只有 `content` 的 512 KiB 检查（L11870），没有对**既有文件**的大小检查；读路径 `_kb_open_impl`（L11494-11499）与 `kb_read_text`（L11085-11090）都有。
- **攻击路径**：对一个 4.4 MB 的 `.md` 执行 `append`（或 `update`）→ 全文读进内存 → `new_bytes = before + addition` → `kb_backup` 再写一份完整 payload（+4.4 MB 磁盘）→ `kb_atomic_write` 再写一份新文件。放大系数 ≈ 3 倍文件大小，且**没有上限**（真实库有 315 个 >10 MB、10 个 >100 MB 的文件，其中只要有一个是文本就够）。
- **影响**：内存尖峰 / 磁盘放大；在 MCP 面可被反复触发（每次写都留一份备份）。
- **修法**：`before` 读取前先 `stat().st_size > max_open_bytes` → `too_large`（同读路径口径）；真正的长文档走"分段 append"这类显式路径时另行放行。顺带把 `kb_backup` 的 payload 也纳入同一上限判断。
- **证据**：P7（同一文件：读=`too_large`，写=`append-ok`，4,400,000 B → 4,400,014 B）。
- **判据面缺口**：`test_kb_read.py::test_open_refuses_too_large_with_byte_count` 只测读；`test_kb_write.py` 只测 `content_too_large`。建议加"目标文件 >max_open_bytes 时 append/update 必须 `too_large`"。

### F6 🟡 `tree` 的 `max_depth` 是死代码（遍历不封顶）

- **位置**：`_kb_tree_dir`（L11279-11337）递归时只传 `level+1`，**没有 `if level >= max_depth: return`**；`max_depth` 只影响回执里的 `depth` 字段（L11388 夹到 1..4）。
- **攻击路径**：`kb tree --depth 1` 仍会遍历整棵树。真实库实测 `depth=2`：**248 次 `scandir`、583 ms、覆盖 11,497,542,860 B 元数据**（depth=2 只需要约 10 次 `scandir`）。更深/更宽的自建库线性放大；目录嵌套极深时 `_kb_tree_dir` 递归会撞 `RecursionError`（未实测，属静态判断）。
- **影响**：资源耗尽（IA/CPU/时延）与"文档承诺的预算不存在"（§4.1 "深度超过 max_depth 不再下钻"、PRD §6.3 "每目录最多 20 子项" 只实现了后半句）。
- **修法**：函数入口加 `if level >= max_depth: return {"...": 空但要保住 notes/attachments/bytes 的合计语义}`——注意合计口径：要么在超深处只做一次 `_kb_walk` 汇总（不再递归建树），要么在 `_kb_tree_impl` 用一次 `_kb_walk` 算合计、树只建到 max_depth（后者更简单）。补判据：把 `os.scandir` 打桩计数，断言 `depth=1` 的调用次数 = 根 + 一级子目录数。
- **证据**：P6（自建 6 层库 `depth=1` 仍 14 次 scandir）；真实库度量（248 次 / 583 ms / 11.5 GB 元数据，`notes=297 attachments=2195`）。
- **判据面缺口**：现有 tree 判据只断回执文本与预算，不断"实际走了多少目录"。

### F7 🟡 非 `KBError` 异常逃逸：不给错误码、也不留审计

- **位置与触发**（4 条实测）：
  | 触发 | 位置 | 实测异常 |
  |---|---|---|
  | gb18030 文件 `update` | L11917 `before.decode("utf-8", errors="strict")` | `UnicodeDecodeError`（读侧明确支持 gb18030，写侧却硬按 UTF-8 解） |
  | `kb open <目录>` / `kb open ""` | L11494 `abs_path.stat()` → L11500 `read_bytes()` | `PermissionError [Errno 13]` |
  | 路径含 `\x00` | L10939 起（`os.path.realpath`/`Path` 抛） | `ValueError: embedded null byte` |
  | ADS 形态 `note.md:hidden`（create） | L9105 `open(tmp,"wb")` | `OSError [WinError 87]` |
- **攻击路径**：任何人（含无 token 的 MCP 客户端）发这 4 类输入 → 服务不崩（MCP 层兜住），但：① 回执是 `错误：<Python 原文>`（含绝对路径/内部函数名）；② `_kb_guard` 只捕 `KBError`（L11271），所以**一条 `reject` 审计行都不落**——"谁试过读什么"没有痕迹；③ CLI 面直接吐 traceback。
- **影响**：A09（日志与监控不足）：审计的"全事件流水"承诺（偏离记录 B3-10）在这 4 类输入上不成立；错误文案把内部路径带进模型上下文（并入 F14）。
- **修法**：在 `kb_resolve_target` 把所有 OS 层异常包成 `KBError("path_invalid"|"not_found")`；`_kb_open_impl` 对"目标是目录"显式判 `is_dir()` → `bad_usage`；`_kb_write_impl` 的 `before.decode` 改用 `detected["encoding"]`（读侧已经算出来了，L11888 就在手边）；`_kb_guard` 增 `except OSError as exc: _kb_reject(..., 伪 KBError)` 分支并记 `result='denied'`。
- **证据**：P4 / P5 / P11（`00-首页/a.md\x00.txt` → `UNCAUGHT:ValueError`）/ P13（`WinError 87`）。
- **判据面缺口**：建议加"坏输入矩阵"判据：4 类输入各自必须 (a) 得域错误码，(b) `kb_access` 增一条 `reject`。

### F8 🟡 frontmatter 值可注入换行（YAML 注入 / 结构破坏）

- **位置**：`_kb_scalar`（L11669）只判类型；`_kb_quote`（L11687）的"需加引号"字符集 `:#{}[]&*!|>'"%@`,` **不含换行**，而加引号也只是首尾加 `"` 且只转义 `\` 与 `"`——**不转义换行**；`_kb_merge_frontmatter` 直接 `f"{key}: {rendered[key]}"`（L11735）。
- **攻击路径**：MCP `kb_write(action="update", frontmatter={"tags": "正常值\nadmin: true\nsecret_note: 注入"})` → 落盘：
  ```
  ---
  tags: "正常值
  admin: true
  secret_note: 注入"
  ---
  ```
  Obsidian 会把 `admin` / `secret_note` 当成**真属性**。另一种：值里带 `\n---\n` → 文件头被提前闭合，后续文本落进正文区（实测 `---\ntitle: 标题\n---\n这不是 frontmatter 的正文\n---\n\n真正的正文`）。
- **影响**：违反"frontmatter 只增改给定键"（PRD §6.2 / 裁决 C4）。带 `publish`/`aliases`/`cssclasses` 这类属性时，可让笔记被导出/改名/改样式而调用方"只申请改 tags"。属 prompt 注入的可利用面（第三方内容诱导 AI 写一条带注入属性的 frontmatter）。
- **修法**：`_kb_scalar` 对 `str` 值拒绝 `\r`/`\n`（`bad_frontmatter`）；`_kb_quote` 的转义表补 `\n`→`\\n` 并把引号条件改成"含控制字符或 YAML 敏感字符"；`_kb_merge_frontmatter` 里对渲染结果再做一次"单行断言"。
- **证据**：P14（落盘头 4 行如上面代码块）、P14b（结构破坏后的完整落盘）。
- **判据面缺口**：`test_kb_write.py` 覆盖了"正文不要带 frontmatter"（L11866 的守卫），但没有一条覆盖"frontmatter 值里带换行"。

### F9 🟡 裁决 Q13「禁写 `90-模板/`」未实现（静默偏离）

- **位置**：`KB_DEFAULT_IGNORE_GLOBS = (".obsidian/**", ".trash/**")`（L10627）——全仓 grep `90-模板` 在 `p0/*.py` 里 **0 命中**。
- **攻击路径**：`kb_write(create|update, path="90-模板/xx模板.md")` → 一路放行（只受 `mode=rw` 限制）。
- **影响**：裁决 Q13 的理由是"模板决定人以后所有产出，风险高"。现在 AI 能改模板 → 影响面是**未来全部产出**，且这类改动能被备份/回滚（可恢复），但很难被察觉（模板不会被天天读）。
- **修法**：`KB_DEFAULT_IGNORE_GLOBS` 增 `"90-模板/**"`（与 `.obsidian` 同级、不可被用户删），并在 `偏离记录`/`知识库接入与回滚说明.md` 的"不敢写清单"里点名。
- **证据**：全仓 grep（`p0/*.py` 无 `90-模板`）；`kb_vault_add` 永远只 prepend 那两条默认规则（L10743）；`偏离记录-B1B2B3-v0.1.md` 11 条 B3 偏离里没有这一条。
- **判据面缺口**：建议加一条与 `.obsidian` 同形的判据：`90-模板/x.md` → `ignored`。

### F10 🟡 备份无保留策略（写一次复制一份整篇）

- **位置**：`kb_backup`（L11767-11792）每次写都在 `<data_root>/_backups/kb/<vault_id>/<ts>-<slug>/` 留 `payload`（原文字节）+ `meta.json`；全仓唯一的 `KEEP_DAYS` 在 `daily_report.py`（与 kb 无关），kb 段只有一句文案提到"备份可能被清理（KEEP_DAYS）"（L11989）。
- **影响**：长期使用后 `_backups/kb/` 无界增长（每次写 = 一份整篇副本，且 F5 允许大文件），磁盘被静默吃掉；`kb rollback` 的失败文案还把"可能被清理"说成已发生的事，与实际"永不清理"不符。
- **修法**：写时按 vault 计保留（N 天 / M 份，超出按 ts 删最旧）；`kb doctor` 增一段"备份目录体积 + 最旧/最新"，并给 `fish kb backup prune --keep-days N` 显式命令；把 L11989 的文案改成"备份若不在了（人为清理/mode 切换）"。
- **证据**：代码段全文；本副本 `p0/data/_backups/` 已有目录（`ls` 可见 15 个条目）。

### F11 ⚪ `write_id` 的随机后缀不参与校验

- **位置**：`write_id = f"{access_id}-{secrets.token_hex(4)}"`（L11944）写进备份 meta；`kb_rollback` 的解析正则 `^(\d+)-([0-9a-fA-F]{4,32})$`（L11972）只用 `group(1)`，后缀弃之不用。
- **攻击路径**：知道/猜到一个连续 id（`fish kb stats` 就打印 id）即可 `fish kb rollback 17-0000`。
- **影响**：本地单用户场景危害有限；但"看起来是能力令牌，其实谁都能造"是**假保证**——将来若把 rollback 暴露成 MCP 工具或 API，就会直接变成未授权撤销。
- **修法**：二选一——(a) 存后缀哈希到备份 meta，rollback 时比对；(b) 承认它不是令牌，改名为 `access_id`，回执里去掉随机后缀。
- **证据**：P8（真后缀 `bf69245e`，用 `9-0000` 也撤成功，`removed=True`）。

### F12 ⚪ 硬链接穿越（reparse 检查的盲区）

- **位置**：`_kb_first_reparse`（L10913-10936）只判 `FILE_ATTRIBUTE_REPARSE_POINT`；硬链接不是 reparse，`st_nlink > 1` 未检查。
- **攻击路径**：`mklink /H vault\00-首页\hard.md C:\某库外文件.md` → `kb open` 读到库外内容，`kb write update` **改写库外文件**（实测库外文件内容被改）。
- **影响**：越界写的一种横移形态。前置条件：攻击者已能在 vault 内建硬链接（同卷 + 对 vault 有写权限）——本地威胁模型下不算高，但它把"只写 vault 内"这条承诺打了个洞。
- **修法**：`kb_resolve_target` 的 ⑤ 步之后加一条：`os.stat(abs).st_nlink > 1` → 新错误码 `hardlink`（或复用 `reparse_point` 但文案点明"硬链接"）。
- **证据**：P15（`mklink /H` 成功 → `READ_OK/WRITE_OK` → 库外文件被改=True）。

### F13 ⚪ `--home` / `layout.home_root` 可把门面指到任意绝对路径

- **位置**：`resolve_home_root`（L8984-9062）只有两条断言（不在 `data_root` 内、不在已登记 vault 内）。
- **影响**：`fish layout render --all --home C:\Windows` 会把 20 个 md 写进系统目录（`_layout_write` 只保证"在 home 内"，不保证 home 本身合理）。人的误操作面，非攻击面。
- **修法**：加第三条断言——拒绝盘根、拒绝 `%WINDIR%`/`%ProgramFiles%`/用户家目录根；或在 `--home` 非标准位置时要求 `--i-know` 之类的显式确认。
- **证据**：P16/P16b 说明 `_layout_write` 自身守得住（`..` 与盘符都 `RuntimeError`）；缺口只在 home 的**选择**上。

### F14 ⚪ 错误串与 `meta.reason` 带绝对路径

- **位置**：`not_found` 的"父目录不存在：{parent}"（L11019）、`offline` 的"{root}"（L11419/L11561）、`kb_read_text` 同类；`_kb_reject` 把 `exc.message[:200]` 写进 `meta.reason`（L11264）。
- **影响**：vault 绝对路径本来就在 `tree` 头与 `vaults` 列表里公开（设计如此），所以不算新泄露；但错误串会进宿主日志/模型上下文，且 `meta.reason` 让审计表长期存着人机路径（含用户名）。
- **修法**：错误文案用 `vault 名 + 相对路径`；`meta.reason` 只存 code + 相对路径。

### F15 ⚪ 开发副本曾对生产 vault 执行写入（已回滚）

- **证据**：本副本 `p0/data/index.sqlite` 的 `kb_access` id 17–20：`create MCP-复核.md` / `append 旧正文.md` / 两条 `rollback`；当前 `kb_vault.mode='ro'`。实测真实库内 `**/MCP-复核.md`、`**/旧正文.md` **均不存在**（rollback 生效，无残留）。
- **影响**：无残留，但说明"开发副本不碰生产库"这条纪律在 T04/T05 期间被破过一次（当时 `mode` 是 rw）。风险是下一次有人忘了回滚。
- **修法**：把"devA 副本的 `mode` 恒为 `ro`"写进 `分支开发说明.md`；需要 rw 的验收改用 `tempfile.mkdtemp()`（现有测试本来就是这么做的，只有手工验证那几次破了例）。

## 4. STRIDE 威胁建模（知识库读写）

### 4.1 信任边界

```
  人 ──CLI(fish kb ...)──┐                       ┌── Obsidian.app（直接读写同一批文件）
                         ▼                       ▼
                   ┌───────────────────────────────┐
                   │  fish 进程（fish.py / mcp_server）│
                   └───┬───────────────┬───────────┘
        AI 宿主 ──stdio json-rpc──▶ MCP 面    │ 文件系统 API（open/replace/scandir）
        （多会话共享一个进程）                  ▼
                                     ┌─────────────────────┐
                                     │ vault 目录（任意本地盘）│  ← 边界内：vault 外一律"不许"
                                     │ .obsidian / .trash  │  ← 边界内的"禁区"
                                     └─────────────────────┘
                    data_root/_backups、_audit（同机、明文、gitignore）
```

边界判定要点：**AI 与 fish 进程之间没有鉴权层**（token 只是归属标注，不是门禁）；**fish 与 vault 之间唯一的技术门禁是 `kb_resolve_target` + `mode`**；**Obsidian 与 vault 之间无中介**（fish 的写入会被 Obsidian 立刻看到，反之亦然——这是 append 无锁的根因）。

### 4.2 逐类威胁

| 威胁 | 现状（有/无/部分） | 残余风险 → 发现 |

## R-2 新增发现（本轮新增攻击面）

### N1 🟠 失效访问控制 · NTFS 8.3 短名别名绕过忽略规则（并在部分命名形态下绕过敏感名单）

**位置**：`kb_resolve_target` L11276（`_kb_ignored` 判在 `realpath` **之前**）+ L11289–L11305（realpath 只用于 `commonpath`）+ `_kb_open_impl` L12040（sensitive 判 `target["rel"]`，仍是**字面** rel）

**攻击路径**：任何调用方（CLI / MCP；MCP 写面只需任意会话 token，`session_start` 可自取）把目录/.md 名的 8.3 短名当路径 → 忽略与敏感两项判定都在**字面串**上做，真正打开的是**解析后**路径：
- `kb open OBSIDI~1/app.json` → 读出 `.obsidian/app.json`（Obsidian 配置；插件配置里可能有同步/第三方服务的 key）
- `kb write create OBSIDI~1/evil.md`（mode=rw 时）→ 往 `.obsidian/` 落文件（可覆盖 `app.json` / 植插件配置）
- 敏感名单：**ASCII 命名**的凭证文件在 8.3 派生时会被截断，关键词可能被切掉 → `credentials-prod.md` 的短名是 `CREDEN~1.MD`，不含 `credential` → `_kb_is_sensitive_name` 返回 False → **不授权就能读正文**；中文命名的短名（`凭证管~1.MD`）仍保留关键词、**不**被绕过（见证据 4 的更正）

**证据（实测，正文未打印）**：
1. 真实库 `E:\Obsidian\安逸知识库`（mode=ro）：`kb_open('OBSIDI~1/app.json')` → **NO_ERROR，82 B**（与 `.obsidian/app.json` 同尺寸）；同一文件走原名 → `ignored`。
2. MCP 面：`kb(open,'OBSIDI~1/app.json')` → `isError=False` 且回执含配置内容；`kb_write(create,'OBSIDI~1/evil.md', token=…)` → `isError=False` 且文件落在 `.obsidian/evil.md`。
3. 敏感绕过（temp 库）：`05-区/credentials-prod.md` 原名 → `sensitive`；短名 `CREDEN~1.MD` → **NO_ERROR 且正文泄漏（含探针命中）**。
4. 真实库短名（`GetShortPathNameW`，非编码猜测）：`.obsidian→OBSIDI~1`、`.trash→TRASH~1`、`attachments→ATTACH~1`；凭证文档 `→凭证管~1.MD`，`_kb_is_sensitive_name('凭证管~1.MD') = True` —— **该文件不因短名而漏保护**（只做名判定，未读正文）。
5. `fsutil 8dot3name query E:` → `8dot3 name creation is ENABLED`（C: 同样开启）。

> ⚠ 自我更正：第一版证据 4 我用 `dir /x` + GBK 解码读短名列，得出"凭证文件短名不含关键词"的结论——**那是错的**。改用 Win32 `GetShortPathNameW` 取真短名后推翻：中文短名保留了 `凭证`。**N1 的读/写越界（证据 1/2）不受影响，但"真实凭证文档可被短名绕过"这一条不成立**，已从结论里删掉；敏感绕过只适用于 ASCII 命名且关键词被截断的文件（temp 库已证明该形态可行）。

**修复建议（一处修、关三个洞）**：`kb_resolve_target` 在 `realpath` 之后补算
`resolved_rel = target.relative_to(real_root).as_posix()`，对 **`resolved_rel`** 再跑一次 `_kb_ignored`，并在 open/write 层对 `resolved_rel` 再跑 `_kb_is_sensitive_name`；任一命中 → 拒绝（新码 `alias_path`，或复用 `path_invalid`）。正常路径下 `resolved_rel == rel_posix`，不会误伤大小写变体（归一化已覆盖）。
**判据**：`kb_open('OBSIDI~1/app.json')` → `ignored`；`kb_write create 'OBSIDI~1/x.md'` → `ignored`；`kb_open('<敏感文件短名>')` → `sensitive`；并加一条"正常大小写变体仍可读"防过度拒绝。

## R-9 新发现

### 🟡 N7 · 失效鉴权（类型转换 fail-open）· `allow_sensitive` 的字符串 `"false"` 等于"同意"

- **位置**：`p0/mcp_server.py:1513`（读面）、`:1602`（写面），写法均为 `bool(a.get("allow_sensitive"))`。
- **攻击路径**：宿主/客户端把布尔当字符串传（YAML/env/模板渲染很常见）→ `allow_sensitive="false"` → `bool("false") is True` → 敏感正文照样返回。实测 `"false"` / `"0"` / `"true"` / `1` **全部放行**，只有整数 `0` 被拒。
- **为什么算本轮**：读面同款写法是既有（R15），但**写面是本轮新增**（S6）——同一个 fail-open 被带进了"改凭证"这个动作，所以我按增量面登记。
- **修复建议**：一个 `_bool_arg(name, value)`（只接受 `True/False/1/0/"true"/"false"`，其余 `bad_usage`），两处共用；判据：`"false"` 必须拒、`"true"` 必须放行。
- **证据**：`T|T_allow_type|{"value": "'false'", "isError": false, "leak": true}`；对照整数 `0` → `isError: true`。

### ⚪ N8 · 失效访问控制（别名形态覆盖不全）· 硬链接不在 S1 覆盖面内

- **位置**：`p0/fish.py:11430–11444`（realpath 后复判）。硬链接不改变 realpath，故复判看不见它。

## R-10 题目点名的三个面

### ① `allow_sensitive` 的权限路径能否被 prompt 注入利用

**能，前提只是"有 token"，而 token 本来就发给模型。** 注入指令只需说"带 `allow_sensitive=true` 调 `kb` / `kb_write`"：

- 读：MCP `kb` + token + flag → `isError:false`，凭证正文真的返回（`S8_open_allow_token.leak=true`）；
- 写：MCP `kb_write` + token + flag → `isError:false`，凭证文件真的被 append（`S6_mcp_write_selfauthorized.changed=true`）。

**净风险仍低于本轮之前**（不带 flag 一律 `sensitive`，默认拒绝有效），但"显式二次授权"的文案对人是有误导的：它不是"人批准"，是"模型自己写的一个布尔"。可选收口：**(a)** MCP 不暴露写面 flag（只留 CLI —— 那时人真在终端里）；**(b)** 保留但要求 `reason` 必填 + 回执顶部加一行"本次是授权访问敏感文件" + 审计记录 `allow_sensitive`（配合 N9）。

### ② 强制忽略项是否"看起来挡了、其实路径变体仍可"

**没找到新变体。** 对 `90-模板/t.md` 逐一实测：大小写、尾随空格、尾随点、双斜杠、`./` 前缀、`..`（`path_invalid`）、ADS（`path_invalid`）、绝对路径 / UNC / `\\?\`（各 `path_invalid`）、8.3 短名（CJK 目录在本卷未生成短名，同名即 `ignored`）、junction（`ignored`）——**全部被拒**。唯一仍可的是硬链接（N8，已登记 F12）。

### ③ S1 复判是否覆盖读 / 写 / 搜索三条路径
