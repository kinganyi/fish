## 0. 一页结论

五句话（第 4 条 v2 新增，第 5 条 v4 新增）：

1. 两个宿主**不是没有父子**，而是**父子不在 hook 拿得到的地方**：DSH 有会话头 `parentSession` 与父会话 `subagent/catalog`；WorkBuddy 有团队 `runtime.json` 的 `leadSessionId` 与 `<父会话>/subagents/agent-*.jsonl` 路径。而 fish 的身份写路径（SessionStart/PostToolUse hook）只看得到 `session_id`。
2. 根因不是"缺字段"，是**三层错位**：维度合并（代理没有独立身份，`presence.agent_id` 填的是 session_key 的复制）、数据源错位（有父的地方不写身份，写身份的地方没有父）、双库分裂（语料库已有 652 条父链，却不驱动 index 侧归属）。
3. 目标模型是**两维、一表、一个适配器**：会话维落 `session_lineage`（父边 + 物化路径 + basis），代理维落 `agent_id/agent_role`（DSH 显式 NULL——宿主就没有这个 id；WorkBuddy 取 transcript 文件名与 `providerData.agent`）。**真相在宿主日志，`corpus_session` 与 index 投影都是可重建的派生**。`ensure`（幂等建/继承身份）与 `rotate`（轮换凭证）拆开，子会话**继承父公民**，不再造新公民。**v3 定案（方案 A）**：继承走 `session_identity`（N 个会话键 → 1 个公民），`citizens.host_session_key` 仍是**单值领地**、不改语义；`end_session` 的吊销**保持会话级**（只用 `session_key`/`token_hash`/`parent_hash`，**永不**用 `citizen_id`）——"一改就塌缩到公民"的那种修法已在 PoC 里被证伪（§3.3）。
4. **但身份修好不等于投递修好**：子代理**早就在被当正常公民推送**（`push_log` 里 193 次 / 32 个会话，**32/32 都是 `origin=subagent` 的真子代理**）；两道闸门目前只生效一道——tool_after 挡无身份、prompt 不挡（501 条 `citizen_id` 为空的 prompt 推送即证）。**推送的目标必须是会话/代理，不是公民**（§3.5）。**v3 修正**：闸门与路由必须**解耦成三个开关**（`push.enabled` / `push.no_identity` / `push.target_mode`），且 `push.no_identity=skip` **只能在 W4.6（WB 身份）之后**才允许打开——今天开它，WB 的 prompt 推送按 7 天回放要掉 **76.7%**（243/317，§3.5.3）。
5. **模型不设深度上限**：DSH 的子 AI 下面还能再套子 AI，**层数不限**。所以 `parent_session` 只当**指针**、`delegationDepth` 只当**提示值**（宿主自己都不信任单个值，取 `max(头, 运行时)`，`depth.ts:28-36`），`depth` 一律由递归 CTE 从链上重算；必做的是**防环**（`relation='cycle'`）与**孤儿诚实**（`unknown`/`missing`，永不默认 `main`），而不是设一个上限（§3.6、§8-8）。

## 1. 四路调研的结论

### 1.1 DSH：有父链，父链是"会话级"的，且有三处独立抓手

**身份就是会话。** DSH 没有独立 agent id：会话注册表与 agent 注册表共用同一个 `sessionId`（`checkout/packages/core/agent/lib/types/index.d.ts:44-50`）。所以"代理"在 DSH 里不是一个可命名的实体，而是"一条会话在跑"。

**子会话头自带父链。** `SessionHeader.parentSession`（`core/session/lib/types/types.d.ts:71`）、`origin?: 'subagent'`（`:81`）、`delegationDepth`（`:87`）、`agentPreset`（`:94`）。写入点 `subagent/src/child-agent.ts:139-157`：`parentSession: parentHeader.id`（149）、`origin: 'subagent'`（153）、`delegationDepth: childDepth`（155），preset 从父的**活** scope 读（148）。真实样本（子代理自己的第一行）：

```json
{"type":"session","version":4,"id":"500a0110-a415-46f4-a86c-febc6dc2ad4d",
 "parentSession":"session-b6e726dd-9d2a-4707-bec1-6b7a15c6a154","isSeeded":false,
 "origin":"subagent","delegationDepth":1,"agentPreset":"dafish-team"}
```

**父会话日志里有子目录事件（catalog）。** `{"type":"subagent/catalog","seq":6352,"data":{"version":0,"childId":"500a0110-…","childCreatedAt":1795520705419,"mode":"continuable","label":"调研DSH子代理父子标识"}}`；写入 `subagent/src/catalog.ts:150`（`parent.append('subagent/catalog', …)`），投影 `listChildren/listDescendants`（`lib/types/list-children.d.ts:26,35`）。它同时是 OAR 规范里点名 DSH 的那条边（`_research-check/oar/docs/spec/session-graph-and-cursor.md:33-34`）。

**`subagent/start|end` 不落日志。** 它们是运行时事件（`subagent/src/lifecycle.ts:86-89`，经 `ctx.events.dispatch('emit', …)` 在 `:113` 派发）。实测父会话日志 6,788 条事件里 `subagent/*` **只有 catalog 57 条**，`subagent/start`、`subagent/end` 均 0（20:27 全量解压计数）。

**hook 侧拿不到父。** 基础键只有 `session_id / transcript_path(恒 '') / cwd / hook_event_name`（`hooks-claude-code/src/index.ts:327-336`，其中 `:332` 就是 `transcript_path: ''`，注释 "the persistence seam exposes no artifact path"）；`SubagentStart` 的 `agent_id` 就是**子会话 id**，且 `session_id` 也是子会话 id（`:359-366` 用 `base(child, event)`），README 原文"在 Claude Code 报告父会话的位置使用 child 会话 id"（`hooks-claude-code/README.zh.md:179`）。`SessionStart` 监听 `agent/created`（`:209-221`）——**这正是子代理被当新会话发证的机制来源**。**v3 精确化**：`agent_id` **只**出现在 `SubagentStart`/`SubagentStop` 两个 payload 里；`SessionStart` 与 `PostToolUse` 的 payload 都**没有**它。所以 DSH 侧判父的唯一来源是**会话头**，不是 payload——W4 的 `ensure` 必须在热路径读一次头。

**751 个会话头全量读数**（zstd 只读首行，0 解析失败；20:40 快照）给出四态，这是"会话树"需要的第一张表：

**v3 新取证：WB 的 hook payload 组装代码是可读的（推翻评审的"0 命中"）。** 评审在 `app.asar`（172.9 MB）里搜 `transcript_path` 得 0 命中——但那不是 hook 实现的位置。WB 的 CLI 运行时在**明文可读**的 `C:\Users\15596\AppData\Local\Programs\WorkBuddy\resources\app.asar.unpacked\cli\dist\codebuddy-lite-wb.mjs`（12,849,066 B / 3,721 行）。逐键计数（21:31）：`transcript_path` **39**、`hook_event_name` **56**、`buildAgentTrigger` **30**、`executeSessionStartHooks` **4**、`parentSessionId` **151**、`agent_id` **41**。四个关键实现都在 L2602 那一行区：

| **L1 从未有身份** | 该 `session_key` 在 `session_tokens` 里**一行都没有** | **7,366**（32.9%） |
| **L2 身份晚于会话** | 有 token，但行发生在该会话**首个** `issued_at` **之前** | **14,987**（67.1%） |

L2 不是"没登记"，是**登记得太晚**：`958af7a6` 首行 `2026-11-10T05:18:39Z`、首个 token `2026-11-22T16:58:43Z`（差 12 天，14,719 行里 13,161 行未归属）；`37b1f34d` 首行 11-11、首 token 11-20（差 9 天）。**镜像判据更硬**：L2 里"行晚于首 token 却仍未归属"= **0 行**——所以 L2 是纯时序，不是别的 bug。v2 那句"归属差异不是时间造成的"**作废**。

```sql
-- L1：从未有过身份
SELECT COUNT(*) FROM tool_activity t
WHERE t.host='workbuddy' AND IFNULL(t.citizen_id,'')=''
  AND NOT EXISTS (SELECT 1 FROM session_tokens st WHERE st.session_key=t.session_key);   -- 7,366

-- L2：身份晚于会话（seen_at 与首个 issued_at 对拍）
SELECT COUNT(*) FROM tool_activity t
JOIN (SELECT session_key, MIN(issued_at) first_at FROM session_tokens GROUP BY session_key) f
  ON f.session_key=t.session_key
WHERE t.host='workbuddy' AND IFNULL(t.citizen_id,'')=''
  AND (t.seen_at IS NULL OR t.seen_at < f.first_at);                                    -- 14,987
-- 镜像（必须 0；>0 说明两级归因不成立，别拿它当结论）
--   …… AND t.seen_at IS NOT NULL AND t.seen_at >= f.first_at  → 0
```

**events 与 UI 没有父位**：`actor_of`（`p0/fish_workbench_api.py:736-752`）只有 `system/citizen/session/none` 四档，键固定 `{name,labelKind,citizenId,host,sessionTag}`；`presence` 的自动行只 UPDATE 不 INSERT，且 `board_id NOT NULL`（`p0/fish_activity.py` `refresh_presence_cache` 的"只 UPDATE 已存在行"契约）。

### 1.4 外部标准：两维是硬约束，"单 parent 字段不够"要看场景

- **OAR**：归因是记录上的**一个字段** `agentPath`（`[]`=根），"同一维度不做第二编码"（`_research-check/oar/docs/spec/attribution.md:15-17`）；信封 `sessionId/agentPath/spanId?/seq/receivedAt`（`:52-63`）；**硬约束**："协议绝不能把 session 与 agent 合并成一维"（`:138-145`）；嵌套 session 的边另用 `session_linked {parent, child, via}`（`record-stream.md:785`），会话图只放真会话，agent 父子用 `agentPath` + 生成它的 `tool_call`（`session-graph-and-cursor.md:13-21`）。
- **OTel GenAI**：父子 = `SpanContext` 的 parent span id；`gen_ai.agent.id` 是代理标识，不是父子边；handoff 是**兄弟**。
- **LangGraph**：`checkpoint_ns`（`node:uuid|inner:uuid`）把嵌套编码进命名空间；**LangSmith**：`parent_run_id` + `dotted_order`。
- **OpenAI Agents SDK**：span 的 `parent_id` 只在 trace 层；**Claude Code**：同一个 session，子代理 transcript 是 `agent-{agentId}.jsonl`，关联靠 `parent_tool_use_id`（OAR 观测，非官方字段）；A2A/MCP **没有父子**。

## 2. 根因：三层错位

### 2.1 维度合并：代理没有独立身份

- 宿主层：DSH 明确没有 agent id（`agent/lib/types/index.d.ts:44-50`）。
- fish 层：`presence.agent_id` 存在且被填了 562/583 行，但值 = `session_key`（distinct 353 = distinct session_key），这不是"填了代理"，是**把会话字段换个名字再存一遍**。
- 凭证层：`parent_token` 与 `channel='parent'` 已设计（`fish_schema.py:87,93-94`）却 0 使用 → 凭证层面也没有"子代理"这一维。

### 2.2 数据源错位：有父的地方不写身份，写身份的地方没有父

- 有父的三处：DSH 会话头/catalog（§1.1）、`persisted_sessions`、WorkBuddy runtime/路径（§1.2）。
- 写身份的两处：SessionStart hook（发证、建公民）与 PostToolUse hook（写 `tool_activity`/`session_context`）。
- 两者交集为空：hook payload 只有 `session_id`（`hooks-claude-code/src/index.ts:327-336`）。于是**唯一能判父的进程不发身份，唯一发身份的进程判不到父**。

### 2.3 双库分裂：语料库有父链，但不驱动 index 侧

- `corpus_session` 652 条父链、`origin` 100%、`basis` 有值（`fish_corpus_store.py:119-136`），但它是**离线批量**；index 侧的归属是**在线**（hook）。两库只共享 `(host, session_id)`，没有"谁是谁的父"的在线投影。
- 结果：`corpus_session` 711 行 vs `session_context` 62 行 vs `session_tokens` 564 行——三张表三个覆盖率，没有任何一张能同时回答"这条动作属于谁、他爹是谁"。

### 2.5 统一术语表（v4 新增：先钉死词，再谈模型）

本节要治的不是"没定义"，而是**同一个词在三处指三样东西**：`agent` 在 DSH 指**会话**、在 fish 的 `presence.agent_id` 里指 **`session_key` 的复制**（§1.3）、在 OAR 指 `agentPath`；`parent` 在 DSH 指 **fork 种子血缘**（`types.d.ts:70` 注释原文 seed lineage）、在 WorkBuddy 指 lead 会话、在 fish 的 `parent_token` 里指**凭证父**（`fish_schema.py:87`）。三个维度，各有唯一载体：

| 维度 | 回答 | 唯一载体 | 不等于 |
|---|---|---|---|
| **会话 session** | 哪个会话单元 | `session_key`（保留宿主原始形态，§3.2） | 不等于人；不等于公民 |
| **代理 agent** | 哪个执行角色 | `agent_id` + `agent_role`（DSH 的 `agent_id` 恒 NULL） | 不等于公民；不等于会话 |
| **身份 identity** | 算谁的人 | `citizen_id`（N 会话 → 1 公民，落 `session_identity`） | 不等于会话；不等于执行体 |

六个关系词，每个只回答一件事：

- **父会话 / 子会话**：**会话树上的边**，载体是 `parent_session` 指针（DSH 写进子会话头 `parentSession`，`types.d.ts:71`）——不是凭证，也不是公民。
- **兄弟**：同一父下的多个子级，**彼此不是父子**。WB 团队成员互为兄弟（`leadSessionId` 才是父、`members[].agentId` 只是标签，§1.2）；同一父派生的多个 DSH 子代理也互为兄弟（父 `b6e726dd` 的 catalog 57 个子，§1.1）。
- **fork（派生）**：用父的历史播种，**不是被 spawn**。DSH 判据是三条同时成立：`parentSession` 有值 + `isSeeded=true` + `delegationDepth=0`（`types.d.ts:71,76,87`；16 行样本见 §1.1 表）。
- **身份继承**：多个会话**共用**父公民（N → 1，`session_identity`），子会话**仍是独立会话**。
- **凭证继承**：子 token 的 `parent_token` 指向父的 `token_hash`（`fish.py:3589` 映射到列 `fish_schema.py:87`），父结束则级联吊销（`fish.py:4527`）。
- **代理归属**：动作记到哪个**执行角色**（`agent_id/agent_role`），与身份、会话**正交**——`presence.agent_id` 今天填的就是 session_key，它既不是身份也不是会话。

**一句话铁律（本节唯一要背下来的一条）**：

> **父子只描述会话树；继承只描述身份与凭证；代理只描述执行角色。三者不得互相替代。**

三条推论，每条都能反过来当判据：

1. **继承父公民 ≠ 同一会话**：子会话在 `citizens` 里 **0 行**、`session_identity` 里 **1 行**（§3.3 方案 A）。
2. **WB 成员是 lead 的子，成员之间才是兄弟**：互相连边会画成斜树且 `parent_session` 自指（§7-1）。
3. **fork 不是子代理**：`parentSession` 一列两义，删掉 `isSeeded` 判据，16 行 fork 立刻落进 subagent（J8）。

**三种宿主形态对照**（承认它们**不是同一件事**，这正是 §4 适配器只输出三列、不做统一抽象的原因）：

| 形态 | 独立会话？ | 父链载体 | 执行体载体 | `relation` |
|---|---|---|---|---|
| **DSH 子会话** | **是**（自己一份 session 日志 + 头） | 头 `parentSession`（`types.d.ts:71`） | `agent_id=NULL`；`agent_role=agentPreset`（`:94`） | `spawn` |
| **WB 子代理** | **否**（`sessions` 表 0 行，只有 `subagents/agent-<uuid>.jsonl`） | 路径 `<父sid>/subagents/` + payload `agent_id`（§1.2） | `agent_id=agent-<uuid>`（= payload 的 `storeId`） | `spawn` |
| **WB 团队成员** | **否**（in-process，挂 lead 会话） | `runtime.leadSessionId`（`runtime.json:4-5`） | `agent_id=agent-<uuid>`（= `resumeSessionId`）；`agent_role=role@team` | `team_member` |

**统一闭集**：`relation ∈ {spawn, fork, team_member}`。三类边共用一个词表，但**每条边只落一个值，不许混边**（`continue` 表示"同一会话续接"，不是父子，v4 不动它；`cycle` 是 v4 新增的**非正常边**，见 §3.6.2）。

## 3. 目标模型

### 3.1 用几维：两维，但**不要** OAR 的完整 `agentPath` 数组

**结论：会话维（session tree）+ 归属维（agent attribution），两维；代理维只要 `agent_id + agent_role` 两个标量，不引入数组。** 理由四条，每条有读数：

1. **fish 的记录粒度是行，不是流**。`tool_activity` 每行已带 `session_key`；再给每行加"路径数组"是把父链在记录上再编码一遍——这正是 OAR 自己禁止的"同一维度第二编码"（`attribution.md:15-17`）。fish 的"路径"应该只存**一份**：会话行上的物化路径。
2. **两个宿主都不交错**。DSH 父日志 6,788 条只有 catalog，子消息在子日志；WorkBuddy 父 transcript 105,636 行 `isSubAgent` 为 0。**不存在"一个流里混着多个代理"的场景**，数组没有对象可装。
3. **递归深度用会话链表达**。DSH 已有 129 个 `depth=2` 会话；每一层都是独立会话行，`parent_session` + `lineage_path` 一次查询就能拿全链。OAR 需要数组是因为 kimi-cli **无界递归压进一条流**（`attribution.md:122-128`）——fish 不接这类宿主。
4. **DSH 的代理身份就是会话**，硬造 agent id 等于编造。

**唯一预留**：`agent_path TEXT NULL` 列（JSON 数组），本期**不填**。它是给"同会话子代理"宿主（Claude Code 的 `parent_tool_use_id` 形态）留的；一旦接入，那条就是真正的数组场景，且 `parent_session` 会自指，必须用路径。**不许为了对称现在就开始填。**

代理维的取值：
- DSH 子会话：`agent_id = NULL`（宿主没有），`agent_role = agent_preset`（`dafish-team`/`cordis`/…），`agent_label = catalog.label`（"调研DSH子代理父子标识"）。
- WorkBuddy agent transcript：`agent_id = agent-<uuid>`（文件名），`agent_role = providerData.agent`（`software-architect`），`agent_label = runtime.members[].taskDescription`。
- WorkBuddy 顶层会话：`agent_id = NULL`，`agent_role = expert agentName`（如 `software-team-lead`）。

### 3.2 单一真相源：真相在宿主；corpus 与 index 都是投影

**结论：`corpus_session` 不能作唯一父链源；唯一要"单一"的是解析规则 + `basis` 字段。** 理由：

1. **覆盖率不够**：DSH 711/751、subagent 635/679、WB 25/310 会话 + 734/2,092 transcript（§1.3）。缺的 44 条子会话如果按"corpus 无父=根"读，会把 44 个子代理变成 44 个主会话。
2. **延迟不够**：语料是离线摄取，`corpus.sqlite` mtime 与实时动作差小时级（`docs/108` §P0-1 已记为已知问题）；而撞车判定在 PreToolUse 的热路径上。
3. **需要的是"规则唯一"，不是"表唯一"**：一个适配器（`p0/fish_lineage.py`），两种运行模式——在线 `resolve(session_id)`（单会话、按需）与离线 `scan()`（批量回填）；两处落点（corpus 的历史列、index 的投影表）都由它写。规则一改，两张表都能重建。

**index 侧建投影表 `session_lineage`，不把 parent 写进 `session_context`。** 三个理由：`session_context` 只有 62 行且语义单一（cwd），塞父链会让它承担两种职责；它是 PostToolUse 热路径的写表，加列会放大写事务；投影表可以整体重建、可以按 host 删了重来，`session_context` 不能。投影表带 `source` 与 `observed_at`，**任何一行都能回答"这是哪一刻、从哪读到的树"**。

**读取路由三级**：`session_lineage` → adapter 现算（单会话，读 DSH 头/WorkBuddy 路径）→ `unknown`（`basis='missing'`）。**任何一级都不许 fallback 成 `main`**——当前 `_origin_of` 的 `default → main`（`fish_corpus_tag.py:240`）就是这条错。

表结构（index 侧，投影可丢弃）：

```sql
CREATE TABLE IF NOT EXISTS session_lineage (
  host            TEXT NOT NULL,
  session_id      TEXT NOT NULL,          -- 裸 id，不带 'host:' 前缀
  parent_session  TEXT,                   -- 裸 id；NULL = 根或判不到（看 basis）
  lineage_path    TEXT NOT NULL,          -- '/root/child/grandchild'；根 = ''
  depth           INTEGER NOT NULL,          -- 链上重算值（真相，§3.6.1）
  depth_host      INTEGER,                   -- 宿主给的 delegationDepth，仅对拍；与 depth 不等 → basis='conflict'
  origin          TEXT NOT NULL,          -- main | subagent | fork | unknown
  relation        TEXT,                   -- spawn | fork | team_member | continue | cycle（§3.6.2）
  agent_id        TEXT, agent_role TEXT, agent_label TEXT,
  agent_path      TEXT,                   -- 预留，本期 NULL
  cwd             TEXT, agent_preset TEXT,
  basis           TEXT NOT NULL,          -- header|catalog|db|path|runtime|depth|inferred|missing|conflict（§3.6）
  source          TEXT NOT NULL,          -- 'dsh:header' / 'wb:runtime' / …
  observed_at     TEXT NOT NULL,
  retracted_at    TEXT,
  PRIMARY KEY (host, session_id));
CREATE INDEX IF NOT EXISTS idx_lineage_parent ON session_lineage(host, parent_session);
```

**v3 补一条 join 纪律（评审 🟡-4）**：`session_id` / `parent_session` **保留宿主原始形态，不做前缀归一**。理由不是洁癖而是实测——DSH **774** 个会话头里 **662 裸 uuid / 112 带 `session-`**；`parentSession` 则是 **565 带前缀 / 136 裸**（21:49 全量扫描，0 解析失败）。fish 的 `session_tokens` 与头 id 形态**本来就一致**（两种都在库里），所以今天不漏；一旦规范化，两种形态就会被拆成两棵树。join 一律按原始值比较。

**WB 侧还有一个命名空间问题（v3 新增，直接决定 J-P2① 怎么写）**：同一个宿主有两个 id 空间——**离线**真相是 `agent-<uuid>`（transcript 文件名），**在线** hook 报的是**父 sid**（`resolveHookSessionId`）。所以 `session_lineage.session_id` 对 WB 填 `agent-<uuid>`、`parent_session` 填父 sid；而 `push_log.session_key` 是 `codebuddy:<父sid>`。两者的正确 join 是 **`p.session_key = 'codebuddy:' || l.parent_session`**，不是拿 `session_id` 去比。v2 的 J-P2① 就是比错了，所以在 WB 侧恒为空集（评审 🟠-4 命中）。

### 3.3 身份模型：`ensure` / `rotate` 拆开；子会话继承父公民（**v3 定案：方案 A**）

**结论先行：选 A**——把身份**解析**扩到会话级，**不动吊销粒度**。判据是回归面：A 只改解析（`find_session_citizen` 一处）+ `end_session` 入口，`revoke_session_tokens` 的四口径（`session_key`/`citizen_id`/`token_hash`/`parent_hash`，`fish.py:3576-3597`）**一个没删、一个没加**，没越过"改 >3 模块 / 动吊销契约"的红线。

**继承为什么会炸（三处代码）**：① `find_session_citizen` 只认 `citizens_all.host_session_key`（`fish.py:3741-3752`），而它挂在 `citizens` 上是**单值列**（`fish_schema.py:653-669`，无 UNIQUE 但语义单值——`:3751` 只取 `ORDER BY created_at LIMIT 1` 一行）；② 于是 `end_session` 的无 token 入口必然 `raise ValueError("当前会话没有登记过公民…")`（`fish.py:4528-4534`）；③ `revoke_session_tokens` 的**级联只在 `end_session` 的 `parent_hash` 支**（`:4527`），`start_session` 轮换只按 `session_key`（`:4401`）——"父轮换时级联吊销"这句是错的。

**PoC 三支实测**（21:47，`tempfile.mkdtemp()` 临时库 + `fish.SCHEMA`+`fish.migrate`；脚本 `%TEMP%\fish-poc-110v3.py`，跑完删库，不碰生产）：

| 支 | 做法 | 读数 |
|---|---|---|
| **A 现状** | 子会话用**今天已有**的 `--citizen`+`--bind-token` 继承父公民（`fish.py:4367-4383`） | `citizens` 1→**1**、`created=false`（**没有第二公民**）；子键在 `citizens` **0 行**；`end_session(子)` → **`ValueError`** |
| **B 变异（错误修法）** | 吊销改 `revoke_session_tokens(citizen_id=…)` | 吊销 **2 行**，父凭证一并失效 —— 粒度塌缩实证 |
| **C 方案 A 形态** | `session_identity` 解析 + 吊销仍按 `session_key` | **不抛**、`revoked=1`；子活 **0** / 父活 **1** / `citizens` 仍 **1** |

一句话：**"继承"今天已经有半条路**（显式绑定不产生第二公民），缺的只是解析与 `end_session` 入口。

**A 的改动清单（5 个函数 + 1 张表，不是 5 个模块）**：`fish_schema.py` 新表 `session_identity(session_key PK, citizen_id, inherited_from, origin, created_at)`，`citizens.host_session_key` **不加列不改语义**；`find_session_citizen` 改两级（`session_identity` → `host_session_key`，返回行带 `inherited`）；`find_or_create_session_citizen`（`fish.py:3771-3812`）新建公民时**同事务**写 `session_identity`；`end_session`（`:4509-4551`）换解析、**`:4536` 的 `session_key` 吊销一个字节不改**；`session_status`（`:4554-4578`，`:4574` 也读它）同步；`fish_activity.resolve_citizen`（`:294-306`）加第三级。**明令：`end_session` 永不用 `citizen_id` 口径**——那一支只归 `citizen merge`（`fish.py:7319`）与 `citizen retire`（`:7439`）。

### 3.6 无界深度：DSH 子代理可以无限层嵌套（v4 新增）

**事实先行**：DSH 这类宿主的子 AI 下面还能再套子 AI，**层数不限**。所以本设计**不得假设 0/1/2 层**——§1.1 那张四态表里的 `delegationDepth` 分布（0/1/2）是**今天的样本**，不是**上界**。宿主实现也印证"上限是逐请求可选项、不是出厂常量"：`resolveChildDepth` 只在 `maxDepth !== undefined` 时才抛错（`child-agent.ts:50-59`），而 `maxDepth` 的校验器把 `undefined` 当合法（`depth.ts:42-51`）。

#### 3.6.1 不设 depth 上限；`delegation_depth` 是提示值

`parent_session` 是指针，天然支持 N 层；会写坏的是"把宿主那个数当结论"。三条证据说明**宿主自己都不信任单个值**：

1. `delegationDepth` **可缺省**（`types.d.ts:87`，注释 `:83` "absent (zero) for a top-level session"）——"没有"与"是根"在字段层面不可区分。
2. 宿主取值是 `Math.max(header.delegationDepth ?? 0, runtime.subagentDepth ?? 0)`（`depth.ts:28-36`）；注释 `:20-23` 明说理由：resume 会带新 options，runtime 只能加深、不能降低。
3. 写入点只做 `parent+1`（`child-agent.ts:51,155`），**不与链做一致性校验**——父链一被搬动/裁剪/回填，这个数就悄悄错。

所以 `session_lineage.depth` **一律由递归 CTE 从链上重算**；宿主值另存 `depth_host`，仅作对拍。两值不等 → `basis='conflict'`，**以重算为准**，两个值都留在行上（可审计）。这条直接改写 §4 的 `depth` 行与 W2 判据。

```sql
-- 深度重算：根 = 0；环被 instr 守卫切断（path 里已有该 id 就不再展开）
WITH RECURSIVE walk(sid, d, path) AS (
  SELECT session_id, 0, '/' || session_id || '/'
    FROM session_lineage WHERE host = :host AND parent_session IS NULL
  UNION ALL
  SELECT c.session_id, w.d + 1, w.path || c.session_id || '/'
    FROM walk w JOIN session_lineage c
      ON c.host = :host AND c.parent_session = w.sid
   WHERE instr(w.path, '/' || c.session_id || '/') = 0
)
SELECT sid, d FROM walk;
```

**为什么必须 `UNION ALL` + 显式 `instr` 守卫**：`UNION` 去重的是整行，而 `path` 每层都变，A→B→A→B 的每一行都"不同"→ 去重永不触发 → **无限递归**。`instr` 是唯一可靠写法。

#### 3.6.2 防环：`parent_session` 链必须无环

投影/写入时检测；发现环 → `relation='cycle'`、`basis='conflict'`，**不参与继承、不参与推送、不参与 UI 展开**，并报警。环上的行不会出现在上面那条 walk 里，所以"环检测"= **对 walk 求反**，再按父是否存在与孤儿二分：

```sql
-- 未被 walk 覆盖 = 环 ∪ 孤儿；父存在却仍不在树上 = 环
SELECT l.session_id,
       CASE WHEN EXISTS (SELECT 1 FROM session_lineage p
                          WHERE p.host = l.host AND p.session_id = l.parent_session)
            THEN 'cycle' ELSE 'orphan' END AS why
  FROM session_lineage l
 WHERE l.host = :host
   AND l.session_id NOT IN (/* 上一段 walk 的 SELECT sid */);
```

`relation` 闭集因此从 `{spawn,fork,team_member,continue}` 扩到 **`{…, cycle}`**（§3.2 DDL 注释同步改）。**J-D3**：构造 A→B→A，两行必须落 `cycle`，且**不进入** `session_identity` 的继承行（`ensure` 在 `basis='conflict'` 时不走继承分支 → `SELECT COUNT(*) … WHERE inherited_from IS NOT NULL AND session_key IN ('…A','…B')` = 0）。**变异**：删掉 `instr` 守卫 → 查询变无限递归（超时/`LIMIT` 判红），且这两行被误标成正常树节点。

#### 3.6.3 孤儿（父缺失）：`unknown`/`missing`，禁止默认 main

父不在库或被裁剪 → `origin='unknown'`、`basis='missing'`、`relation=NULL`。**任何一级读取路由都不许 fallback 成 `main`**（§3.2 末条；`fish_corpus_tag.py:240` 的 `default → main` 就是这条错）。

**必须纠正 v3 一处口径**：§1.3 / §8-1 反复引用的"46 条 DSH 缺口"是**覆盖率缺口，不是孤儿行**。本轮复跑（只读）：日志侧 **763** 个头 vs 语料 **711** 行 → **日志有语料无 52（50 有父 + 2 根）、语料有日志无 0**；而语料内**父不可解析的行 = 0**（652 条有父行全部可解析）。所以**今天没有孤儿行**，46/52 只证明"语料不是全集"；J-D4 **必须构造**，那 2 个缺失的根是"潜在孤儿源"。

#### 3.6.4 递归吊销（进 W4）——先看清它今天为什么是安全的

**现状**：`revoke_session_tokens` 的 `parent_hash` 口径就是一条 `UPDATE … WHERE parent_token=?`（列名映射 `fish.py:3589` → SQL `:3596`），**只吊销直接子级**；唯一调用点 `end_session:4527`。看着是 N 层漏吊销，但**今天是安全的**——因为另一条守卫：

`issue_agent_token` 的 docstring 写着"**只允许一跳**"（`fish.py:4470`），守卫 `assert_agent_parent_allowed`（`:4446-4466`）**只允许 `machine` 级父**（`:4462-4466` 抛"不能链式继承"），判据 E 与变异自证在 `test_identity_p1b.py:669-686,688-705`。**链最多两层，"直接子级"恰好等于"全部后代"**——单跳不是 bug，是配套前提。

**无界深度会推翻这个前提**：§3.6.5 要"从最近的有身份祖先继承"，N≥3 时子级必须能拿着 `inherited` 父再签一次 → **一跳守卫必须放开** → 一放开，单跳吊销立刻成**真缺口**（结束 A，C/D 的凭证仍活）。**所以 W4 两件事必须同波做**：放开链式签发 + 递归吊销；只做前一半比今天更糟（链更长、更吊销不到）。

递归改法——只换 `parent_token` 那一支，另三口径（`session_key`/`citizen_id`/`token_hash`，`:3587-3592`）一个字节不动，§3.3 的"不动吊销粒度"继续成立：

```sql
WITH RECURSIVE t(hash) AS (
  SELECT token_hash FROM session_tokens WHERE parent_token = :root
  UNION
  SELECT s.token_hash FROM session_tokens s JOIN t ON s.parent_token = t.hash
)
UPDATE session_tokens SET revoked_at = :now
 WHERE token_hash IN (SELECT hash FROM t) AND revoked_at IS NULL;
```

**四个细节——前三条都在本机 `sqlite3 3.45.1` 内存库上实测过**（脚本 `%TEMP%\_a110_v4_cte2.py`；顺带确认 `WITH … UPDATE` 语法可用，本机版本远高于所需的 3.8.3）：

① **`UNION` 而非 `UNION ALL`**——对 `t.hash` 去重在这里是正确且必要的：行已存在，环只会重复"已见 hash"。实测环 A↔B **未无限递归**，被吊销集合 = `{A, B}`。**副作用要知道**：环存在时"后代"集合会包含**起点自身**（A 的 `parent_token` 指向 B，B 又是 A 的子）——`end` 场景无害（A 本来就要吊销），但"只吊销子级"的语义在有环时不成立，所以 §3.6.2 必须先把环切掉。
② **保留 `revoked_at IS NULL`**——实测第二次执行 `changes() = 0`，幂等靠的就是这一条（`end_session:4537-4539` 用"实际吊销数"判 `already`）；删掉它，重复 end 会从幂等变成报错。
③ **`cursor.rowcount` 在 `WITH … UPDATE` 上不可用（实测返回 `-1`）**——正确值走 `SELECT changes()`（实测 = 3）或 `UPDATE … RETURNING token_hash`（实测 3 行）。**这条不补就会写坏返回值**：`end_session:4527` 把它的返回值直接塞进 event 与 CLI 输出（`:4547,:4550`），用户会看到 `children_revoked: -1`。
④ **`children_revoked` 语义会变**（从"直接子级数"变成"全部后代数"），这是可观测的行为变化，必须在 W4 判据里声明，不许静默改。

**J-D2**：构造 A→B→C，结束 A，**C 必须失效**（`… WHERE session_key='dsh:C' AND revoked_at IS NULL` = 0）。**变异**：SQL 改回单跳 → 同一断言红（C 仍活 = 1）。**对照组必须绿**：B 也失效、A 自己的 token 也失效——否则"全红"可能只是判据读空。

#### 3.6.5 身份继承的传递性：从最近的有身份祖先继承

子级向上找**第一个**有身份的祖先（`session_identity` → `citizens.host_session_key` 两级，§3.3 方案 A），继承其 `citizen_id`，写 `inherited_from=<该祖先 session_key>`。**整条链都没有身份** → `provisional`，**不造"每人一个公民"**。

**一处必须先补的 schema 事实**：`evidence='provisional'` **今天写不进去**——`SESSION_EVIDENCE_LEVELS` 只有三值（`fish.py:3265` = `machine/inherited/self-reported`，`:3557-3558` 会抛），DDL 的 CHECK 同样只有三值（`fish_schema.py:92`）。所以 W4 落 `provisional` 要**同时改两处**（常量 + CHECK；SQLite 改 CHECK 需重建表的十二步流程），这不在 v3 的 W4 清单里，v4 补进去。

**J-D5**：造 4 层链 A→B→C→D，`citizens` 只允许 **1** 个（根 A 的），且 B/C/D 三行的 `session_identity.citizen_id` 全等于 A 的。**变异**：每层各建一个公民 → 计数变 4，判据红。

#### 3.6.6 推送路由：寻址到"发起动作的那一层"

§3.5.1 规则 1 已立"不寻址到公民"；无界深度只加一条：**不向祖先冒泡**。动作在哪一层发生（`session_key`/`agent_id`），提示就递给那一层；祖先只出现在**级联清理**里，**不因为是祖先就多收一份**。拿不到父、或落在环上 → **不推**。

**J-D6**：A 结束后 D 的推送不再发生（end 时刻之后 `push_log` 无 D 的新行，且 D 已无活凭证）。**变异**：把路由改成"沿 `parent_session` 向上找最近可投递目标"→ D 结束后提示被投给 A，判据红。

#### 3.6.7 UI 与性能

树视图按递归 CTE 展开并显示层数（`depth`），**可折叠 + 懒加载**：默认展到第 1 层，点开再取下一层（一次 `LIMIT n`，不做全树展开）。深度**不设渲染上限**，但渲染要防环（`path` 里出现过的 id 不再展开）。

`parent_session` 已有索引（§3.2 `idx_lineage_parent`），但 **`session_tokens.parent_token` 没有索引**——递归吊销在 N 层时逐层扫表，**W4 必须补 `CREATE INDEX idx_tokens_parent ON session_tokens(parent_token)`**。当前量级（763 / 570 行）无压力；到 10 万会话时用 `lineage_path` 做**展示**加速，但**真相仍是指针**——路径只是缓存、可整体重建，且深链时线性变长（深度 100 就上千字符），**只许用于展示，不许用于判据**。

## 7. 风险与不做清单

1. **不要把 WorkBuddy 团队成员当父子**。`members[].agentId` 是 `role@team` 标签，`leadSessionId` 才是父（`runtime.json:4-5,12-23`）；成员互为兄弟。做错会把团队画成斜树，且 `parent_session` 自指。
2. **不要从 title 猜父**。WB 759 条里 735 条 title 为空；DSH 子会话 title 是首条消息片段（实测 `## 身份覆盖（宿主自动附加，`），同一父下大量重名。只有 `basis='inferred'` 且 `infer_rule` 白名单（当前仅 `self:depth>0`）才允许，且必须可被 SQL 过滤掉。
3. **不要回填不可证实的归属**。22,190 行 WB 未归属里，有的会话在 `sessions` 表有行（可 ensure），有的连会话都没有（`[判不到]`）。规则：**能 ensure 才回填，不能就留空并标 `basis='missing'`**；绝不按 cwd/时间相近并人。
4. **不要用 trace span 当父子**。实测 13 个 agent span 里 5 个 `parentId=null`（`trace_8b07de…`），且 span 不带 session 映射；trace 只能做"这一轮消耗"的旁证。
5. **不要把 `persisted_sessions.parent_session` 直接当子代理**。16 个 fork 行 depth=0、2 行 parent+depth=0（`seed_length≈977`）。
6. **不要把 corpus 当唯一真相**（711/751；44 条子会话缺口）。
7. **不要给每个子会话发新 token**：564 条已偏多，token 应随"会话"而非"每次 SessionStart"增长；继承后子会话凭证挂在父下（§3.3）。
8. **不要双写两库**：只允许 corpus → index 单向投影；反向写会重演 `fish_hosts.py:9-10` 记录的那种"两套真相"。
