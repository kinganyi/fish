### 定性

**设计如此 + 配置未开 + 计划任务失效，三者叠加。** 不是代码 bug。

### 建议修复

## 7. BUG-6 🟠 七个语料源永久 degraded，没有重试机制

### 现象

`corpus_degraded` 有 7 条记录：

```
dsh        oversize_frame   kept=1713   2026-11-19T19:14
dsh        oversize_frame   kept=1713   2026-11-19T19:14
workbuddy  bad_json         kept=7148   2026-11-19T20:35 ~ 20:39
workbuddy  oversize_text    kept=1123   2026-11-20T02:38
workbuddy  oversize_text    kept=6340   2026-11-19T22:30 ~ 23:01
workbuddy  oversize_text    kept=5773   2026-11-20T00:07
workbuddy  oversize_text    kept=5005   2026-11-19T19:48
```

对应 `corpus_source` 里 7 个源 `status='degraded'`（dsh 2 个、workbuddy 5 个）。

具体原因：

- `oversize_frame`（2 条，dsh）：帧解压输出超过 64 MB 上限（`67108864 B`），帧起点之后的内容全部落空。原文写「已交付 66846720 B」——也就是刚好卡在 64 MB 边上被截断。
- `bad_json`（1 条，workbuddy）：第 36,421 行 JSON 坏（`Expecting value: line 1 column 1`），之后的内容按行号跳过。
- `oversize_text`（4 条，workbuddy）：单条消息正文超过 200,000 字被截断。

### 影响

这 7 个会话的数据**永久不完整**。`oversize_text` 只是截断（内容还在但被切了），`oversize_frame` 和 `bad_json` 是**真丢**（后面的段完全没进）。

我判不到丢了具体多少段——`corpus_degraded.segments_kept` 记的是「已经保住了多少段」，不是「丢了多少」。

### 定性

**确证的现象。** 是否算 bug 取决于设计意图：如果「超限就跳过并记降级」是有意的，那这是设计；但**没有重试机制**这一点，我认为是可以改进的。

### 建议修复

三个方向，按代价排序：

一是**提高上限**。64 MB 的帧上限和 200,000 字的消息上限，对长会话是偏紧的。可以先量一下这几次超限的实际值，看是超一点还是超十倍。

二是**支持分片重采**。对超限的源，别整源标 degraded 就完事，应该记一个「从第 N 行/第 N 字节继续」的游标。

三是**至少在日报里报出来**。现在降级只落在 `corpus_degraded` 表里，日报那一行是「降级 N」——数字太小容易被忽略。如果连续多天有降级，应该单独喊一声。
