## §0 一页结论

要解决的不是"加个分类字段"，而是一个 fish 今天回答不了的问题：**一个人 + 多支 AI，凭什么处理第 20 个项目时不再犯第 3 个项目犯过的错。**

用户原话给了三个判断，我全部落成结构：① 单一会话扛不住大量项目的上下文 → 需要"职能"这个维度；② "项目进项目系统，经验进经验系统" → 经验不能是项目记忆的一个标签；③ "让独立 AI 扛住大量项目" → **可达性比数量重要**。

**五条结论**：

1. **作用域是二元组 `(scope_kind, scope_key)`，成员唯一**；跨作用域"适用面"用 `links` 边表达，不用多重成员。
2. **`project` 列不改语义**（它继续表示"这条在哪个项目学到"）。实测它已被三种含义占满：真项目 786 条、`NULL`=全局规矩（`fish_inject.py:35,44`）、`''`=未归属（`fish_workbench_api.py:303`）。再让 `NULL` 承担第四义，就要把四处谓词逐个"教会"新语义——那就是补丁序列。
3. **经验不是新记忆类型，是 `lesson`/`rule` 的作用域子集**。判据：`scope_kind IN ('role','global') AND mem_type NOT IN ('lesson','rule')` 必须为 0。建 `experience` 表会立刻有两条真相。
4. **写作用域默认 project，提升到 role 是一条显式命令**。实测 `memory.recorded` 786 条里"同一标题跨项目出现"**0 条**——跨项目复用今天没发生，自动提炼等于编造。
5. **第一批必须只读**。不是保守，是行数：`fish.py` 10599/10600（余 1）、`fish_push.py` 1550/1550（余 0）、`fish_schema.py` 699/700（余 1）、`fish_rebuild.py` 559/565（余 6）。这一层最肥的部分全落在余 0–1 行的文件里。

**成本**：S1–S3 估 **5 任务 / 26 人时**；S4 需先做一次拆包，另计。

## §1 概念钉死

### 1.1 项目 / 职能 / 记忆

- **项目**：`code_registry(prefix, namespace, status)`（`fish_schema.py:625`），23 行，`active/closed/retired` 三种状态都在用，同时是编码前缀注册表。
- **记忆**：`code_index` 786 行 + `events` 2992 行（唯一真相）。
- **职能**：**不存在**。`citizens_all.role` 不是它——实测 319/343 为 NULL，剩下 24 条各是一句自由描述（每句只出现 1 次）。它是"这个人干什么"的自报，不是"这类活怎么判断"的词表。

一句话：**项目是"在哪做"，职能是"做什么类别的判断"，记忆是"据此留下的结论"。一条记忆落在唯一一个作用域上。**

为什么职能必须独立：同一项目里"做架构判断"与"跑数据修复"是两类活，要的经验完全不同；同一职能跨项目时经验可搬运。把职能挂成项目属性，跨项目就永远搬不动——这正是用户说的"单一会话扛不住"的结构原因。

### 1.2 经验 vs 知识：三条判据

用户问"经验是'怎么做才对'、知识是'世界是什么'，还是别的划分"。我给三条，**第三条可机械检查**：

**判据一（主语）**：主语是人/流程 → 经验；主语是世界 → 知识。"评审前先自己读产物再对照实现者说明"是经验；"`index.sqlite` 在 `p0/data/`、48 张表"是知识。

**判据二（失效方式，决定性）**：经验因"照着做却错了"被推翻（要**反例**）；知识因"来源更新"而过期（要**重读来源**）。动作不同，所以不能放进同一个管理流程。

**判据三（出处类型，可机械判）**：**有外部权威出处 = 知识；出处是我们的记录 = 经验。**
- 知识必须指回外部：kb 的 `rel_path`（`kb_index` 296 条）、URL、文档路径。
- 经验只能指回内部：语料门牌 `log:<host>:<sid>#seq=`、记忆编码、`cause`。
- 落成判据：role/global 条目的正文或 `cause` 里必须至少有一个内部门牌。**没有出处的判断不进经验层**——它既不是经验也不是知识，是意见。

**落到六个 mem_type**（实测：artifact 246 / fact 172 / lesson 158 / episode 99 / rule 97 / identity 14）：

| mem_type | 归哪侧 | 理由 |
|---|---|---|
| `lesson` | 经验 | "踩过，下次别这样"，判据一、二都成立 |
| `rule` | 经验（被授权那类） | 同 lesson，区别是"谁有权定"（`test_rule_authorization.py` 锁着） |
| `fact` | 知识 | 描述世界，失效方式是来源变了 |
| `artifact` / `episode` / `identity` | 都不是 | 产物清单 / 流水 / 坐标，都不是可复用判断 |

这张表就是判据三的落地，也顺带划清了 kb 与经验的边界（§3.1）。

### 1.3 一条记忆只能属于一个作用域

**结论：恰好一个 `(scope_kind, scope_key)`。** 三条理由按强度排：

1. **多重成员让"谁维护它"无解**。职能合并、项目归档、失效降级都需要一个归属者；两个归属者 = 谁都不动。
2. **多重成员是隐形的两份真相**。用户担心的复制是"两条一样的记录"，更常见的是"一条记录出现在两条检索路径里、各自被不同判据过滤"——于是它在项目视角是"项目经验"、在职能视角是"通用经验"，读者给的信任等级不同而内容相同。
3. **编码制度已经隐含单成员**：前缀即项目（`fish_common.py:827 split_code_prefix`，右锚定），`rebuild_projection` 靠它推 `project`（`fish_rebuild.py:312-324`）。让一条记忆属于两个前缀，要动的是编码制度。

**适用面用边，不用成员**：同时适用"代码评审"与"交付验收"的经验，归属仍是其中一个，适用面写 `links(src=code, dst='role:delivery-review', rel='applies_to')`。检索时它参与**加权**，不参与**归属**。`links` 已存在（`fish_schema.py:36`，实测 458 行：related 432 / supersedes 19 / derived 7），加一个 `rel` 值不改结构。

### 1.4 经验树是什么

三个候选——层级路径 / 图 / 标签——**分工，不让一个东西干三件事**：

- **文件夹 = 职能**：`data_root/roles/<role_key>/<code>__<slug>.md`。正文唯一副本必须在 `data_root` 下（`fish.py:9120` 的布局判据："与 `data_root/projects/**` 内容相同的 md 会被 `fish layout verify` 判红"——这条反重复机制我要沿用而不是绕过）。
- **树 = 受控二级词表** `role → topic`（`role_topic` 表）。**不是**从 tags 长出来的树：实测 164 条 active 的 lesson/rule 上挂着 **368 个不同 tag**，top 之后迅速掉到 1 次（`铁律` 10 / `纪律` 6 / `工程铁律` 3 / `方法论` 2）。自由标签在这个规模下已是墓地，让它长成树只会长出更多单例。
- **关系 = `links` 图**：跨枝引用、提炼谱系（`derived`）、替代（`supersedes`）、适用面。7 条 `derived` 已存在，证据写着"写入时 cause 指向"（`fish.py:1773`）——**提炼谱系已有实现，不需要新机制**。

一句话：**树解决"找得到"（受控、有序、可枚举），图解决"有关联"（开放、可加权）。让树管关联会失控，让图管浏览会没有边界。**

## §2 作用域模型

### 2.1 `scope` 定义与生命周期

```
scope := (scope_kind, scope_key)
scope_kind ∈ {'project','role','global'}     -- 本期；tenant 不是 scope_kind（见 §5）
scope_key  := 项目名 | role_key(kebab-case) | '*'
```

三条硬约束：**① `scope_kind='project'` ⇒ `scope_key = project`**（同字符串，让"零迁移"成立，也让打架情形一句 SQL 判出）；**② `role` ⇒ `scope_key` 必须在 `role_registry` 且 `status='active'`**（拼错即拒）；**③ `global` ⇒ 只允许 `rule`，且必须带凭证声明**。第三条的理由：全局规矩进每个会话的注入包，能影响所有 AI 行为。实测 `mem_type='rule' AND project IS NULL` **0 条**——全局规矩段（`fish.py:5920-5923` 的第二栏）从未在生产渲染过，这条路**没有生产见证**，第一批不铺量。

| 事件 | 触发 | scope 怎么变 | 落点 |
|---|---|---|---|
| 项目归档/关闭 | `project.closed`/`project.retired`（实测各 2 条） | **不变**，只是不再被路由选中（closed 项目的经验不推） | 读侧按 `code_registry.status` 过滤；`resolve_name` 已返回 status（`fish_common.py:548-550`） |
| 经验提升 | `experience.promoted`（新增） | 产生**新条目**（role），原条不变 | §4.2 |
| 作用域改写 | `memory.scoped`（新增） | 原条 scope 改为 role | §4.2 |
| 职能合并 | `role_registry.merged_into` + `name_aliases(kind='role')` | **不改数据**，旧 key 走别名解析 | §4.1 |

第四条是刻意的：项目别名机制已跑通（`name_aliases` 实测 3 行、全 project），合并职能复用它，而不是"批量 UPDATE 786 条 scope_key"。批量改写就违背"真相是事件"——真要改就走 `memory.scoped` 事件流。

### 2.2 写入时怎么决定 scope

先补一个被漏掉的现状事实：`record_memory` 签名是 `record_memory(conn, root, *, project, title, ...)`（`fish.py:901`），**`project` 必填**，`body_relpath` 用它拼正文路径（`fish_common.py:809`）。**今天写入方没有任何"可复用性"判断入口，只能声明项目。**

| 路 | 机制 | 致命问题 |
|---|---|---|
| ① 显式声明 `role=` | 多一个参数，不填=project | 依赖自律，会被滥用成"什么都标 role" |
| ② 默认 project + 定期 distill | 后台聚类提升 | **自动制造跨项目真理**。97 §A5 同款亏：presence 自动登记 340 条同一句话，读者把"没信息"读成"有信息" |
| ③ 双写（project 条 + role 条） | 一次写两条 | 两份正文/衰减/去重；且 **`events.refs` 实测全表 0 条有值**——指望它做关联等于新建机制 |

**推荐：①为主 + ②降级为显式提炼命令，不做后台自动。**

1. **缺省 = project**，行为与今天逐字节一致（零回归的判据来源）。
2. **`role=` 只在有依据时用**，且必须给"适用条件"（正文首段）。判据见 §1.2 判据三。
3. **提炼是显式命令**（`fish role promote <code…> --as-role X --topic Y`）：产出一条**新文本** + `experience.promoted` 事件 + `links(rel='derived')` 指向源条。不聚类、不定时。
4. **为什么不是双写**：两条记忆就有两份衰减与两份推送去重记录（`_recent_pushed_codes` 按 code 去重，`fish_push.py:836`），"同一经验推两次"会在 24h 窗口外重现。单条 + 两条读路径不会：去重仍按一个 code。

**防两份真相——四条，全部可判**：**A** 全库 `body_sha256` 重复数 = 0（基线：实测 167 条带哈希、**167 个不同值、0 重复**；变异：把 A 的正文复制给 B → 红）；**B** `experience.promoted` 必须同时给出源与产出的 `body_sha256` 且不相等（相等即"提炼没改文本"= 复制）；**C** 任一条 role 经验必须能一句答出"从哪几条提炼来"（`derived` 反查），答不出即红；**D** 同一编码在注入包里最多出现一次（现有 `exclude` 纪律，`fish.py:6221`，经验层不得引入新重复点）。

### 2.3 读取时怎么路由

排序分三层：**第 1 层（类型）** `rule > lesson > fact`；**第 2 层（作用域宽度）** `project > role > global`；**第 3 层（同层内）** 现有分数（`benefit−cost`、衰减、静默降权）。

**为什么 project 在 role 前**：项目内经验有具体证据，角色经验是归纳；归纳更通用但更可能不适用，读者在具体项目里应先看到具体的。这与 `fish_push._cand` 现有三档同源（同项目 rel=1.0、跨项目 0.1，`fish_push.py:325-332`），我加第四档 `role 命中 = 0.6`（理由见 §3.4）。

预算（实测约束：`inject.budget_tokens` 生产 config = **2000**，默认 1600（`fish_common.py:239`）；`open=450` / `after_tool=100` / `prompt=120`）：

| 通道 | 角色经验份额 | 判据 |
|---|---|---|
| 注入包 inject | **本期 0**（段渲染在 `fish.py`，余 1 行） | 段集合与段头文字在加层前后逐字相等 |
| 工具后 tool_after | 最多 1 条；同 role 24h 不重复 | 同一 role 两次推送间隔 > 24h |
| 提示词 prompt | **0**（不推角色经验） | prompt 通道 role 条数 = 0 |
| recall（MCP） | 路由时 role 桶最多 3 条 | 单次 recall 里 role 条 ≤ 3 |

**冲突裁决给规则，不给"谁"**：① **两条都出，project 在前**，role 版后标 `（自 N 个项目提炼）`——不许合并，合并会丢反例；② 同一 `(scope_kind, scope_key, topic)` 下两条 role 互斥 → 新的 active、旧的**手动** `supersede`（`memory.superseded` 已存在 48 条），**不做自动 supersede**（会自动压掉"旧答案 + 反例"）；③ `rule` 与 `lesson` 冲突 → rule 赢，lesson 降为附注里的"反例"——这是 `fish.py:6213-6215` 三段分工（规矩=规范 / 注意=临时 / 错题本=踩过的坑）在作用域维度的延续。

### 2.4 与 search / FTS / 衰减 / 去重

**结论：作用域是过滤条件（不是排序因子）；"作用域宽度"才是排序因子。** 两者分开，因为正确性判据不同：过滤错是"看不到"（假阴性，这个仓库最恨的一类，见 `fish.py:2377-2380` 记的"23 命中返 0"），排序错只是体验。

- **FTS 与真相的偏差**：`memory_fts` 786 行里 **365 行指向非 active**（325 withdrawn + 40 superseded）。任何绕过 `search_memories` 直接 MATCH 的实现都会把作废记忆搜出来（K8 的活判据）。作用域过滤必须加在**唯一读入口**内或之后，不能另起一条 MATCH。
- **索引现状**：`code_index` 只有主键自动索引（`PRAGMA index_list` 实测返回 `sqlite_autoindex_code_index_1`），**零个二级索引**，四种典型查询全部 `SCAN code_index`：`project+status`、`mem_type+status`、`tags LIKE`、`ORDER BY COALESCE(occurred_at,recorded_at)`（末者还 `USE TEMP B-TREE`）。786 行下 0.15 ms 看不出问题，但这一层会让它从"项目记忆表"变成"项目+职能+全局记忆表"，量级先涨到几千再上万。**加索引是这一层的一部分，不是优化项。**
- **实测收益**（临时副本建索引后，n=200，缓存暖）：无索引 `project+status` **0.1497 ms / SCAN**；有索引 `scope_key+status` **0.0357 ms / SEARCH … USING INDEX (scope_key=? AND status=?)**，**4.2×**；FTS 命中 + 作用域过滤联合 3.2185 ms（`SCAN f VIRTUAL TABLE` + `SEARCH ci USING PK`）。

**三条 DDL 级建议**：① `CREATE INDEX ix_mem_scope ON code_index(scope_kind, scope_key, status)` —— 角色路由唯一热路径，EXPLAIN 实测走 `SEARCH code_index USING INDEX ix_mem_scope (scope_kind=? AND scope_key=? AND status=?)`；② `CREATE INDEX ix_mem_project_status ON code_index(project, status)` —— 现有项目过滤一并收掉（现在也是 SCAN），**不动语义只让它快**；③ **不把 scope 塞进 `memory_fts` 的 token**：它是派生表（`fish_schema.py:680-688` 明写"可由 code_index + 正文文件重建"），当过滤面会让"改一个作用域要重建全文索引"；过滤应发生在 join 之后的行上。

**衰减**：不参与。`decay.*` 语义是"多久失效"，作用域是"属于谁"，后者不随时间变。`decay.lesson_days=365`（`fish_common.py:270`）对 role 经验同样适用，不另设参数。

**去重**：去重键仍是 `code`（`fish_push.py:836` 已按 code），但**不同作用域下的相似正文要能被发现**——即 §2.2 判据 A。

## §3 与既有系统的关系

| 既有系统 | 它回答 | 经验层加什么 | 接口 | 会不会重复实现 |
|---|---|---|---|---|
| 记忆 | 确认过什么 | 一个作用域维度 | 写走包装、读走 `search_memories` 路由 | 否 |
| 知识库 kb | 资料里怎么写的 | 无 | 只借"树"的呈现，不借存储 | 否 |
| 看板 board | 此刻谁在动哪块 | 经验被谁引用 | 帖文里的编码（已有 `board.post_auto_link`） | 否 |
| 语料 corpus | 当时原话 | 证据门牌 | `cause` 存 `log:` 门牌 | 否 |
| 推送 push | 现在该看什么 | 一个相关性档位 | `_cand(relevance=)` 既有入参 | 否 |
| 工作台 97 | 谁在动 / 这条背后是谁 | 页签二多一段文字 | 只读 SQL | 否 |
| 宿主 98 | 这套装没装 | 无 | 通道能力决定走哪条路 | 否 |

### 3.1 与知识库：不是一种 vault

1. **真相位置相反**。kb 真相在库外（唯一 vault 的 `mode='ro'`，实测 `kb_vault` 1 行、`is_default=1`；fish 只有索引：`kb_index` 296 / `kb_fts` 296 / `kb_asset` 2196 / `kb_access` 2450）；经验真相在库内（`events` + `data_root` 正文）。注册成 vault 会让经验真相跑进 `ro` 目录，写入路径直接死。
2. **写入纪律不同**：kb 走 `kb_write`（备份、`base_sha256` 乐观锁、敏感文件拒绝、审计），经验走 `record_memory`（编码、事件、FTS、衰减）。两套不能共用一个入口。
3. **可判边界（回答"会不会重复"）**：能指回外部权威（文件/URL/文档）→ kb；只能指回我们的记录 → 经验（§1.2 判据三）。机械判据：role/global 正文出现 kb 路径 → 告警"这条可能在描述资料"，不拦。

**只复用两样**：`kb_index.headings/summary` 的"分段摘要"形态用于列表渲染（不建第二张摘要表，读取时算）；`kb_fts` 的多 vault 同检语义用于"跨作用域检索"的体验（返回形状照它，不合并代码）。

### 3.2 与看板：靠"编码出现在帖子里"

**正向不需要新机制**：`board.post_auto_link=True`，且 `fish_board` 已有 `recent_memory_code_for_session` / `autolink_memory_code`，所以"帖子正文出现记忆编码"**已经**在发生。

**反向加一个读数、不加表**：某条 role 经验"最近被哪个项目用上" = `memory_access_log` 里 `via` 落在该项目处的行（该表已有 `project` 列；实测 1051 行：`recall` 806 / `read_body` 91 / `push` 71 / `inject` 71 / `resolve` 12）。显示"被 3 个项目用过"就是 `COUNT(DISTINCT project)`。判据：这个数字必须能从该表复算，不允许单独维护计数器。

**不做**：看板不加"经验"栏（97 §A6 减法纪律：8 项删除各写了"不承载哪个任务"，经验栏也答不出"谁需要它"）。

### 3.3 与语料：只做证据，不做正文

语料是原始对话（`corpus.sqlite` 419 MB，独立库；本库 corpus 相关表 **0 个**，实测）。规则一条：**语料只能以门牌进经验**（`log:<host>:<sid>#seq=` 或 `conv:`），正文必须是重写的判断。判据：role/global 条目的 `cause` 或正文里必须出现至少一个门牌或记忆编码（同 §1.2 判据三）——这条同时挡住"从语料抄一段原话当经验"（抄来的没有判断，过不了经验的定义）。

不产生第二份真相的理由：语料段是不可变原始记录（独立库），经验是可变判断（有 supersede 状态机），两者不是同一种东西的副本；真正的风险是"同一判断写进两条经验"，那由 §2.2 判据 A 管。

### 3.4 与推送/召回：三组硬数据定权重

`push_log` 快照 **2026-11-23T21:40:36**（总 5889 行，三通道合计 5889），`rate = accepted/(accepted+ignored)`，未判定不计入：

| 通道 | 推送 | accepted | ignored | pending | 采纳率 |
|---|---|---|---|---|---|
| `tool_after` | 4593 | 67 | 3878 | 648 | **1.70%** |
| `prompt` | 1070 | 3 | 914 | 153 | **0.33%** |
| `inject` | 226 | 18 | 201 | 7 | **8.22%** |

取用通道（`memory_access_log` 1051 行）：`recall` **806（77%）**、`read_body` 91、`push` 71、`inject` 71、`resolve` 12。

四条设计：① **`prompt` 不推角色经验**——1070 次换 3 次采纳（约 300 次里 1 次有用），在 0.33% 的通道里加内容等于主动制造噪音，而噪音会训练 AI 跳过整段（`fish_push.py:1399` 原文："错推一次，模型就学会忽略整个通道"）；② **`inject` 是唯一高效面（8.22%）但本期进不去**（段渲染在 `fish.py`，余 1 行）——所以第一期可达性靠 `recall`（77% 的实际取用面），这就是"MCP 可检索"是硬要求而非加分项的原因；③ **加第四档相关性**：现有三档（`fish_push.py:325-332`）是同项目 1.0 / 无当前项目 0.0 / 跨项目 0.1，而角色经验**本质跨项目**，落默认档 0.1 等于**被现有打分器封杀**——加 `role 命中 = 0.6`（高于任何跨项目候选的 0.1、低于同项目 1.0），可判：它必须让 role 条在 `(benefit−cost)×weight` 排序里落在"同项目 lesson 之后、任何跨项目候选之前"；④ **`tool_after` 最多 1 条且必须带"适用条件"一行**（100 token 里约 15 字）——1.70% 说明内容对但时机差，补这一行是让人自己判断要不要看的唯一低成本手段。

**召回侧引导**：`recall(role=…)` 未命中要引导而非报空，照 `TAGS_ONLY_HINT` 既有做法（`fish.py:2487-2489`）："该职能还没有经验；相近的是这 3 条"。判据：未命中回包必须含至少一条可执行下一步（`fish.py:6609` 的原则："提示语必须是可执行的下一步，而不是一个可能错误的归因"）。

### 3.5 与工作台 97：不进"需要你的"

**结论：右栏页签一四项集合不变，经验只在页签二账本出现。** 用 97 自己的尺子（§A4："位置由是否构成决策决定"）：**"经验缺失"不构成任何人的决策**——AI 缺经验该去 recall（工具侧），人不是经验的作者，人是"批准提炼"的人；把它塞进"需要你的"会让那栏从待办退化成读数，直接稀释前三项。**"经验冲突"也不需要人**：裁决规则是确定的（§2.3），人的介入只把可自动处理的规则变成一次审批。唯一值得人介入的是**"待批的提炼建议"**（AI 提议、人点采纳），它与 `profile_proposals` 同构（AI 只能写 proposals，人点采纳才进 slots，`fish_schema.py:552-583` 已实现）——放进二期。

**页签二加什么**（对齐 97 §A5 三段账本，不新增页签）：段一"这一条"里，role 经验多一行 `作用域：role:code-review（自 3 个项目提炼）`；段三"他的账本"里多一行"被引用于 <项目>，N 次"。判据：页签二的八行属性表形态不得回归（97 §A6 第 8 项）——这是加一行文字，不是加一张表。

**接缝一句话**：97 管"此刻谁在动哪块"（秒到分钟），经验层管"这类活该怎么干"（周到月）；两者只在页签二"这一条背后是谁"处交汇，交汇处只读。

### 3.6 与宿主接入层 98：通道降级，内容不变

98 §5.1 的通道表：DSH 有 `session_id` 且能签发 token；WorkBuddy 只查已有公民、刻意不签发；ZCode 靠模板变量；**Codex 只有 MCP**（无 hooks、无 `session_id`）。三条纪律：

1. **可达性建立在 MCP 上**——它是唯一所有宿主都有的通道（Codex 只能走 MCP 参数 `token=`），所以 `recall(role=…)` 与 `inject` 包是能力底座，hook 通道只是加速。判据：把 hooks 全关，经验仍可 recall 到（端到端判据）。
2. **降级必须可见**：注入包已在包尾打印"这次砍了什么"和 `as_of`（`fish.py:6538`），recall 已标匹配来源（`fish.py:2363-2364` 的 `sources`）。经验层沿用——hook 缺失时不假装"没经验"，而是"本次未经推送，可 recall 取得"。
3. **经验身份里永远没有宿主**：`scope_kind` 词表只有 `project/role/global`。判据：`scope_kind='host'` 出现即红。理由：宿主决定"怎么送到"，不决定"是什么"；一旦 host 进作用域，同一 AI 换宿主就看到不同经验集——那是 98 要消灭的 2.5% 一致率问题的翻版。

**接缝一句话**：98 管"每个宿主能拿到什么"，99 管"拿到的东西一样"；交点只有一处——`HostSpec` 的能力位（hooks/mcp）决定走哪条通道，经验内容不因宿主改变。

### 3.7 三者拼成一个系统

链条只有三层：**98 宿主接入层 → 通道能力（hooks / mcp）决定"送到哪里"；99 经验层 → 作用域 + 词表 + 提炼，决定"送什么"；97 工作台 → 只读投影，决定"看得见什么"。**

三者没有第二份真相，因为读的都是 `events` + `code_index`。

## §4 数据结构与迁移

### 4.1 DDL

放 `fish_role_schema.py`——`fish_schema.py` 现在 **699 行 / 上限 700**（`test_split_contract.py:190`），而 `code_index` 的现行 DDL 就在 `fish_schema.py:633-651`。这个仓库已有同款先例：`fish_git_schema.py` 就是撞窗口后拆出来的（`test_split_contract.py:257-258` 给它留 120–320）。**新维度自带 schema 模块是既有惯例。**

```sql
CREATE TABLE IF NOT EXISTS role_registry (
  role_key    TEXT PRIMARY KEY,              -- kebab-case，如 'code-review'
  display     TEXT NOT NULL,                 -- 中文名，如 '代码评审'
  purpose     TEXT,                          -- 一句话：这个职能负责哪类判断
  status      TEXT NOT NULL DEFAULT 'active'
              CHECK (status IN ('active','paused','merged','retired')),
  merged_into TEXT,                          -- status='merged' 时必填
  created_at  TEXT NOT NULL,
  retired_at  TEXT
);
CREATE TABLE IF NOT EXISTS role_topic (
  role_key  TEXT NOT NULL,
  topic     TEXT NOT NULL,                   -- 同一 role 内唯一
  ord       INTEGER NOT NULL DEFAULT 100,    -- 稳定次序：树的顺序不随字典序变
  status    TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','retired')),
  PRIMARY KEY (role_key, topic)
);
ALTER TABLE code_index ADD COLUMN scope_kind TEXT NOT NULL DEFAULT 'project';
ALTER TABLE code_index ADD COLUMN scope_key  TEXT;   -- backfill 一次填满，之后恒非空
CREATE INDEX IF NOT EXISTS ix_mem_scope          ON code_index(scope_kind, scope_key, status);
CREATE INDEX IF NOT EXISTS ix_mem_project_status ON code_index(project, status);
```

实测依据（**在 `%TEMP%` 的库副本上做，生产库一个字节未动**）：

```
ADD COLUMN scope_kind … NOT NULL DEFAULT 'project'
  → scope_kind='project' 786 行 / IS NULL 0 / 其它值 0
  → page_count 9155 不变（元数据级），ADD+commit 0.003 s
VIRTUAL 生成列 scope_key AS COALESCE(role_key, project) → 可加、可建索引、可 SEARCH
STORED  生成列                                          → 不能加（cannot add a STORED column）
DROP COLUMN 遇依赖索引 → error in index … after drop column；先 DROP INDEX 再 DROP COLUMN 成功
```

**为什么最后不用生成列/视图**（试过，记在这里免得下一个人再试）：生成列能建索引但 SQLite 不能事后加 STORED；VIRTUAL 每次读要重算，而我们每个注入包/push 都要查；视图不能建索引，而作用域过滤必须走索引（§2.4 的 4.2× 就是这么来的）。**结论：两列 + 两索引 + 两表，零视图。**

**为什么不是一列 `scope='role:code-review'` 字符串**：过滤会变成 `LIKE 'role:%'`，索引失效（实测 `tags LIKE` 走 SCAN），且把类型与键焊死，将来按类型统计要切串。

**为什么 `project` 不改语义**：见 §0 结论 2。补充：`body_relpath` 用 `project` 拼正文路径（`fish_common.py:809-825`，路径穿越校验也在那）。改它 = 同时改文件布局、rebuild 推导、注入包两栏谓词、工作台"未归属"桶——五处独立风险换不来收益。

**正文放哪**：`data_root/roles/<role_key>/<code>__<slug>.md`。实现给 `body_relpath` 加同族函数 `role_body_relpath`，**不改 `body_relpath` 本身**（它被 `record_memory` 与 `rebuild_projection` 两处调用，`fish_common.py:812-813` 明写"唯一入口，否则重建即断链"），新函数复用同样三段校验。

### 4.2 events 要不要新类型：要，两个

现有断言类事件 6 种，全是"后到的修正"：`memory.recorded` 786 / `memory.retired` 325 / `memory.superseded` 48 / `memory.archived` 38 / `memory.owner_fixed` 2 / `memory.accessed` 335。

```jsonc

//   {"code":"CZHY-261123-10","old_owner":"unattributed","new_owner":"1795…","reason":"…"}）
"memory.scoped" payload = {
  "code": "CZHY-261123-10",
  "old_scope": {"kind":"project","key":"CZHY"},   // 首次定作用域时 old = 当前推导值
  "new_scope": {"kind":"role","key":"code-review"},
  "topic": "评审纪律",                              // 仅 role 时给，必须在 role_topic 里
  "reason": "跨 3 个项目重复出现，判断与项目无关"

// ② 提炼谱系
"experience.promoted" payload = {

  "target":  "CZHY-261123-11",
  "role": "code-review", "topic": "评审纪律",
```

**schema 不升版本**。`events.schema` 现在 2992 行全是 `evt@1`（实测 `SELECT DISTINCT schema` 只有 `evt@1`）。先例：`memory.recorded` 的 payload 在 2026-11-19 加过 `body_sha256`（`fish.py:1031-1033` 记着理由）**没有**升版本——因为 `schema` 描述的是**信封**（`seq/ts/type/actor/subject/payload/refs`），payload 是自由对象。判据：`SELECT COUNT(*) FROM events WHERE schema<>'evt@1'` = 0。只有信封要改（比如给 events 加 `tenant` 列）才升 `evt@2`。

**为什么 scope 必须进事件，不能只进 `code_index`**——本文最关键的实测证据：`rebuild_projection` 第一步是 `DELETE FROM code_index`（`fish_rebuild.py:236`），然后按 `memory.recorded` 重放（`:247-249`），INSERT 是**显式列清单**（`:357-360`），快照只存 17 列（`:145-154`）、不含 scope。

后果可判：**作用域只存在列里的话，一次 rebuild 会把每条 role 经验静默降级成 project 经验**（`scope_kind` 落回 DEFAULT、`scope_key` 为 NULL），而没有任何东西会红——query 照常返回，只是它们从此只在一个项目里可见。这正是这个仓库反复吃过的"恢复手段变成破坏手段"（`fish_rebuild.py:159-176` 记着同款：畸形事件让投影 1→0 而 FTS 仍指旧）。

**重建怎么承接（只加 2 行）**：`fish_rebuild.py` 现在 **559/565**（余 6）。重放逻辑不写在 rebuild 里：

**结论：不逐条判定、不 emit 786 条事件，只做一次归一 UPDATE。**

**不猜的实证**：164 条 active 的 `lesson`/`rule` 里，命中"纪律/铁律/方法论/工程/通用/跨项目/原则"的 tag 只有 **28 个 tag 次**（`铁律` 10 / `纪律` 6 / `工程铁律` 3 / `方法论` 2 / 其余各 1）；更关键的是**"同一标题出现在多个项目"实测 0 条**（`GROUP BY title HAVING COUNT(DISTINCT project)>1` 返回空）。跨项目复用在今天**没有发生过**，任何自动判定都是编造。人工过一遍大约能提 **20–40 条**（占 164 的 12%–24%），这个量级适合 S1 的只读清单，不适合脚本。

## §5 权限与隔离

### 5.1 现有 visibility 到底是什么

- **开关**：`_visibility_enforced`（`fish_common.py:943-948`）读 config `privacy.visibility_enforced`，**默认 False**（`:436`），配置坏了当关。
- **SQL 谓词**：`_visibility_sql`（`fish_common.py:951-965`）——关着返回 `("", [])`；开着返回
  `" AND (LOWER(TRIM(COALESCE(visibility,'shared'))) <> 'private' OR COALESCE(owner,'') = ?)"`。
- **后置过滤**：`_filter_by_visibility`（`fish_visibility.py:22-47`），在 `search_memories` 用（`fish.py:2459`），规则"private 且 owner≠viewer → 剔除"，无 viewer 一律剔除（宁严勿松，代价不对称）。
- **生产实况**：`visibility` 786 行**全是 `shared`**，0 条 private——这个机制在生产**从未生效过**。与 `fish_common.py:424-435` 自述一致：那里明写"⚠️ 执行层未完成……实测打开它比不开更糟（藏不住 10 条读路径 / 自己看不到——`viewer_citizen_id` 全仓 0 个生产调用点）"。`memory_citizen_isolation` 是死开关（声明了但零读取）。

两件事：① `visibility` 是**个人隐私**语义（软过滤、可选），不是**隔离**语义；② 升级时**绝不能把它接进 `_visibility_sql` 这条链**——那条链自己还是坏的，接上去得到"两个都半坏"。

### 5.2 升级成按 scope 过滤：改哪里、改多少

**不是改 `_visibility_sql`，是增加第二层谓词，两层各管一件事。**

| 层 | 语义 | 失败代价 | 现有 | 本层 |
|---|---|---|---|---|
| L1 隐私 | 这条私不私 | 泄露 | `_visibility_sql`（有缺陷，默认关） | **不动** |
| L2 适用 | 适不适用当前上下文 | 噪音 | 不存在 | **新增 `scope_sql(conn, viewer_scope)`** |
| L3 隔离（未来） | 属不属于这个租户 | 越权 | 不存在 | 只留签名位 |

改多少（逐文件）：新模块 `fish_role.py` 的 `scope_sql` **约 40 行**，形状照 `_visibility_sql`（返回 `(sql 片段, 参数)`；无约束时返回 `("",[])`，保证零回归）；`search_memories`（`fish.py:2355`）**0 行**（它已调 `_filter_by_visibility`，作用域过滤由路由层分桶完成）；`_visibility_sql`/`_filter_by_visibility` **0 行**（混在一起会让"关隐私过滤"顺手关掉作用域过滤）；`fish_workbench_api.py` 若要显示作用域 +约 10 行；数据库两列两索引两表。

**为什么作用域过滤必须下推**：`_filter_by_visibility` 是后置的（先取再剔），`fish_common.py:958-959` 自己记着隐患（"带 LIMIT 的查询后置过滤会让'要 20 条'变成'17 条'，而数字对不上不会报错"）。role 经验天然是少数，命中这个坑更频繁，所以必须在 SQL 里。
