## 2 · 发现清单

### 2.1 严重（🟠 × 4）

#### S1 [🟠] `fish.py:9401-9407`（prompt 主路径）没有传 `project`/`now`，于是"推断当前项目"的前提不成立；交付报告未把这条列为 A 的合并必做项
- **问题**：`select_push_candidates(conn, cands, limit=…, prefer_kind="prompt_related")` — 没有 `project=`，也没有 `now=`。开启重排后，`rerank_candidates` 走 `_infer_project(ordered)`（`fish_push.py:1162`，取池内众数）。
- **为什么这不是"合理的缺省"**：该路径的池子来自 `build_prompt_candidates` → `search_memories_any(conn, terms, project=None, …)`（`fish_push.py:1036`，**不带项目过滤**），是跨项目候选。池内众数可能**不是**会话项目，于是 `project_match` 会给"别的项目"打 1.0、给当前项目打 0。
- **证据**：`fish_push.py:1036`（project=None）、`1162-1172`（众数）、`fish.py:9401-9407`（无 project/now）；交付报告 §9 只列了 4 个 config 键，**没有这一条**。
- **影响**：默认关 → 现在无影响；一旦把开关打开（34 §3.3 的原意就是要开），主要生产路径的项目亲和打错。`now` 缺失只影响窗口基准，可忽略。
- **修法**：A 合并时在 `fish.py:9405` 补 `project=project, now=now_dt`（`project` 在 9401 行前已解析好）；或退一步：`_infer_project` 只在"池内 project 唯一"时用，多个项目一律回中性 0.5。报告 §9 增加"合并必做项"清单。

#### S2 [🟠] `project_match` 对 kb / corpus 是**常数**（"六特征"里有 1 条是假特征），无判据
- **问题**：rerank 用 `cand.get("project")` 算亲和（`fish_push.py:1336-1337`）。但非记忆类候选的 `project` 字段装的**不是内容归属，是"生成时的上下文项目"**：kb 候选 `"project": project`（`fish_push.py:416`）；corpus 候选在为空时被回填成当前项目（`fish_corpus.py:1269-1270`）。只要调用点传了 `project`，这两类恒得 `project_match=1.0`（+0.15）。
- **同向叠加**：kb 候选没有 `freshness` 键 → `_freshness_of` 取 1.0（`fish_push.py:1185-1193`，+0.15 满格）；而一条同项目但陈旧的记忆可能只有 0.35（+0.0525）。合计 kb 相对陈旧记忆有 **≈ +0.25** 的结构性先手，与"六特征按内容质量排序"的叙事不符。
- **证据**：`fish_push.py:416` / `fish_corpus.py:1269-1270` / `fish_push.py:1336`；R7（`test_push_rerank.py:437-457`）只断言 `kind_class` 三集合齐全，**没有任何一条判据看 project_match 的跨类读数**。
- **修法**：非记忆类没有"自身项目"时给 0.5（中性），或把三类候选的 `project` 语义拆成 `project_scope`（生成上下文）与 `project`（内容归属），rerank 只用后者；并补一条判据：同一池里一条跨项目记忆与一条 kb 候选的 `project_match` 必须不同。

#### S3 [🟠] 判据对 `link_strength` 与 3 处状态位零判别力——5 个静默变异全绿
- **证据（我自己做的变异，未改判据）**：`_link_strengths` 恒返回 `{}`、`_alias_group_for` 恒 None、`_RERANK_TOP_K_MAX=10**9`、`_breaker` 的 `limit <= 0` 改 `< 0`、`_infer_project` 恒 None —— **每一个都 `Ran 15 / OK`**。
- **含义**：① `link_strength` 的取数/方向/权重/归一/抑制边（`fish_push.py:1257-1290`，34 行）**0 覆盖**；判据里没有一条 `links` 行（`test_push_rerank.py` 全文无 links 字面量）。② `project_match` 的 0.5 别名分支 0 覆盖。③ R1 只测显式 `top_k=50`，`top_k` 的上界/下界夹取从未被验。④ "breaker <=0 = 关闭"与"推不出项目取 0.5"只写在 docstring/报告里，判据不认。

## 3 · R6 口径（52 / 54 的"hook 端到端 < 2s"）——独立结论：**接受（条件式）**

**口径差异本身成立**：实现把 2s 落在"推送决策路径"，子进程墙钟只守 5s（`test_push_rerank.py:308-340`），报告 §2 偏差 2 + §10.1 已如实登记，符合 52 §4.2「改判据必须写进报告并说明捕获能力不变」的**形式要求**。

**我的实测支持"与 T03b 无关"**：rerank 开/关的 hook e2e 差 0.0–0.2s（噪声内）；真 vault 决策路径 0.509 vs 0.465s（+44ms）；2s 在温缓存下**可达**（1.03–1.20s），冷缓存 2.15–2.9s 才超线。

**但报告的关键归因不成立**：`executescript+migrate` 我实测 12ms（不是 0.6–0.9s）。真正的既有开销是**两个解释器进程**：hook 自己（0.10s 启动 + import hook_io/fish_activity）+ 它 spawn 的 `fish.py prompt-push`（0.10s 启动 + `import fish` 0.35s + 取数 0.3–0.45s）。这改变了两件事：
1. **pre-existing 的锅该谁背**：该由 **A/T05**（`cmd_prompt_push` 的进程模型）背，不该由 B 背——这点报告说对了，只是理由写错了。
2. **5s 守卫线太宽**：它把 2s→4.9s 的整段回退都放过去。T03b 自己的增量是毫秒级，用 5s 守它等于没守。

**条件（复评前须落）**：
- 判据改成两段式：`hook e2e < 2s（温缓存，真 vault）` **且** `相对基线 Δ ≤ 0.2s`（后者才是 T03b 真正能负责的）；
- A/T05 认领一条任务：把第二次解释器（`fish.py` 子进程）或 `import fish` 从每条 prompt 的路径上拿掉——否则 2s 线永远只在温缓存成立；
- 报告 §6 修正归因（见 W8）。
