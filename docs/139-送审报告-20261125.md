## 0. 一句话

fish 是"一个人 + 多支速生速死的 AI"的**个人 AI 基础设施**：以事件溯源为真相核，向 DSH / WorkBuddy 等宿主提供身份、记忆、语料、推送、看板与只读工作台。它不是聊天机器人，而是**控制面 + 投影层**。

---

## 1. 项目定位（审查前必须知道的三件事）

1. **单机、单仓、单用户**：没有多租户、没有公网服务。读口默认绑 `127.0.0.1`，写口极少且都是本机 CLI/hook。
2. **事件溯源**：`events` 是唯一真相；`code_index`、看板、工作台、推送、统计都是**投影**。投影可以整表重建，真相不能。
3. **宿主是外部系统**：fish 不拥有 DSH / WorkBuddy 的会话与配置；它只能**只读探测**、在 hook 里工作、通过 MCP/CLI 被调用。所有"写宿主配置"的动作都刻意没有自动化（或需显式人工执行）。

### B. 性能 / 效率

1. **启动/导入**：`import fish_hosts` 实测 242–627 ms（会经 `fish_ui` 拖进 `http.server`）；`fish_activity` 热路径 ~190–215 ms。hook 有 3–25 秒超时线——导入成本是否已逼近风险？
2. **HTTP 读口**：`/api/stream` 热态中位 39–68 ms、冷态 52–80 ms、`spawn→首响应` 1.33–1.37 s；`/api/hosts` 曾实测 ~1.1 s（无缓存）。哪些该加缓存、哪些该预计算？
3. **深翻页**：`/api/stream` 的 cursor pushdown 在 2,600+ 行、limit 40/50/500 下 rawSum==total（有 completeness boundary）；但在并发写入时会差几行——有没有更稳的分页设计？
4. **SQLite**：索引是否覆盖高频查询（`tool_activity` 的 session/time、`push_log` 的 session/code、`session_tokens.parent_token`）；WAL/写放大；`corpus.sqlite` 449 MB、118k 段的检索是否该另建索引/分表。
5. **hooks**：`fish_posttool_hook.py` 每次工具调用都起进程 + import；有没有可能合并/常驻？超时预算怎么定才不误伤？
6. **UI**：虚拟滚动 + 四栏布局的渲染成本；`dist` 353 KB（gzip 108 KB）是否合理；有没有重复请求/重复计算。

### C. 可靠性

1. **并发**：多会话（DSH + WorkBuddy + 子代理）同时写 `index.sqlite`；hook 是独立进程，SQLite busy/锁竞争怎么处理？`_WRITE_LOCK` 只在单进程内有效，跨进程呢？
2. **迁移**：`session_tokens.evidence` 的 CHECK 走 12 步重建（备份 → 关外键 → 建新表 → 拷 → drop → rename → 重建索引 → foreign_key_check → COMMIT）。这套迁移是否可中断/可重入？失败回滚是否完整？
3. **幂等**：`ensure_session`（不轮换）、`upsert_node`、回填 apply 二次 delta=0、`session_id` 来源不变——这些幂等点是否都有判据？还有哪些写路径没有？
4. **崩溃恢复**：hook 中途被杀、API 重启、备份文件损坏时的行为；有没有"半截状态"？
5. **测试可靠性**：见 §3.4 的抖动；`test_split_contract.py` 的行数窗口/棘轮是否过于脆弱（`fish.py` 只剩 2 行余量）。
