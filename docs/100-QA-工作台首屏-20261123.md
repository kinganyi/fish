- **现象**：`/api/stream` 翻到空页时，覆盖的原始行数远小于 `counts.total`；UI 页大小 40 下只能滚动约 602 条显示条目，然后静默停止。
- **期望**：翻到底覆盖行数 = `counts.total`（A-4 原文："拉到底条数 = 各源窗口内条数之和（去重后）"）。
- **实际**：40 → 632/3,549（缺 2,917）；50 → 782/3,550（缺 2,768）；500 → 3,065/3,550（缺 485）。无重复。
- **复现命令**（只读）：
  ```powershell
  cd I:\app\fish
  python -X utf8 -c "import json,urllib.request,urllib.parse;b='http://127.0.0.1:8790';g=lambda p:json.loads(urllib.request.urlopen(b+p).read());c=None;r=0;n=0
  while True:
   d=g('/api/stream?win=24h&scope=all&limit=40'+('&before='+urllib.parse.quote(c) if c else ''))['data'];i=d['items']
   if not i: break
   n+=1;r+=sum(x['fold']['count'] if x.get('fold') else 1 for x in i);c=d['cursor']
  print('pages',n,'raw',r,'total',g('/api/stream?win=24h&scope=all&limit=1')['data']['counts']['total'])"
  ```
  期望输出 `raw == total`；实测 `raw 632 / total 3549`。
- **根因**：`collect_stream` 把游标过滤放在 `WITH u AS (<四分支 UNION>)` **之后**（`fish_workbench_api.py:729-739`），而四个分支各自在子查询里先 `ORDER BY ... LIMIT branch_limit`（`:329、:338、:347、:360`，`branch_limit=min(max(limit*5,200),2000)`，`:727`）。游标越深，分支的"最新 N 行"窗口不动，第 N 行之前的行永远进不了并集。
- **修法（建议）**：把游标谓词下推进每个分支，在分支内 `WHERE sk < ?`（或等价的 `(ts, rk, pk)` 元组比较）之后再 `LIMIT branch_limit`；或去掉分支 `LIMIT`、只保留并集外层 `ORDER BY sk DESC LIMIT ?`（需先量 27k 行的排序成本）。修完必须补一条回归：**翻到空页后 `rawSum == counts.total`**，并跑 `limit=40/50/500` 三档。
- **回归判据**：上面的命令输出 `raw == total`，且 `duplicateKeys=0`；三档全过才算修好。

### F-2 🟠 停读口空态在交付拓扑下不可达（P1，需主理人裁决）
- **现象**：杀掉 8790 后，`http://127.0.0.1:8790/` 直接 `ERR_CONNECTION_REFUSED`；应用页打不开，`读口没有起来` 永远不出现。
- **原因**：`--dist ui/dist` 让静态文件和 API 同进程同源（`fish_workbench_api.py:1736-1748`），进程死则页面死。
- **复现/绕过**：`python -m http.server 8799 --directory ui/dist` + 8790 停 → 空态正确（`shot-down.png`）。
- **建议**：三选一——① 宿主壳层托管前端（98 的接入层就绪后天然成立，需在验收口径里写清"哪种拓扑"）；② 拆一个只读静态兜底（读口挂了仍能显示启动指引）；③ 若维持单进程，就把 A-2 的验收改为"前端由独立静态服务托管、读口停"，并在文档里注明生产拓扑下该空态只能由已打开的页面/宿主壳层呈现。
- 这一条不是工程师单方面能定，**建议主理人先裁决拓扑，再定 A-2 的判据**。

### F-3 🟠 性能：`limit=500` 中位 197.74 ms（P1）
- 期望 <150 ms；实际 5 次 183-203 ms，中位 197.74 ms。默认 `limit=40` 与 facets/stats/entry 都很快（4-5 ms），问题集中在 500 条的查询 + JSON 序列化。
- 建议：先 profile（是 4 分支 2000 行并集排序，还是 `json.dumps` 500 条）；修 F-1 时顺带把分支 LIMIT 降下来可能一并改善。回归：同一命令 5 次中位 <150 ms，且首屏 `limit=40` 不退化。

### F-4 🟠 推送未按设计折叠（P1）
- 97 §A3 第 4 行要求"同 code 连续推送折叠 ×N"；`fold_items` 只折 `src=="tool"`（`:661-672`）。结果：首屏 22.5% 是推送；项目视图 **90%** 是同一个 code；全窗口 13.7% 的行是同一个 code。
- 建议：为 push 增加"同 code 连续 → ×N"折叠（与 tool 折叠同一套游标/覆盖规则），并给出首屏 push 占比的回归判据（例如 ≤10% 或"同 code 连续出现 ≤1 行"）。

### F-5 🟡 折叠读数口径混用（P2）
按首屏页算且翻页不更新（`fish_workbench_api.py:755-758` + `workbench.ts:225` vs `:270-292` + `Stream.tsx:94-99`）。建议改文案"本页折叠"或让 `loadMore` 更新累计。

### F-6 / F-7 / F-8 🟡 小项
- **F-6**：启动日志只有"写操作已被拒绝并验证"的**声明行**，没有独立的"被拒写"事件；`assert_write_rejected` 拒绝时静默返回（`fish_ui.py:76-94`）。`App.tsx` 注释"页面内数字数 = 0 可机检"被 `p0` 里的 `0` 打破（机检会数到 1）。建议：启动时把"真试写"的拒绝异常类型/消息打一行 `log("readonly_proven", error=...)`，注释改成"除启动命令路径外无数字"。
- **F-7**：`AsyncBoundary.Block` 的 `availability === 'missing'/'partial'/'empty'` 分支**没有任何调用方传 `availability`**（`Rail.tsx:116/158` 只传 state），是死代码；缺表时走 error 文案"这一块没读出来"，原因仍显示（不冒充 0），但没用上专门的"该区数据未接：缺 X"文案。建议要么传 `availability`，要么删掉死分支，别两边都存在。
- **F-8**：`partial` 档无输入可构造（见 A2），文档若把它写成"五档"应改成"三档可达 + partial 预留"。
