# fish git 能力升级方案（2026-11-22）

> 起点：`2ef4356`。本文的所有结论都来自**真实代码与实跑实验**，不是设计推演。
> 文中 `F1…F10` 编号在后续所有提交与判据里复用。

---

## 一、取证：十个决定方案的事实

### F1 · `git_link` 是 0 行，自动关联命中 0%

```
git_repo        3 行    （含那个 impl 仓库：gitee.com/anyippt/czhy-caiwu）
git_checkout    3 行
git_obs       621 行
git_commit    175 行
git_link        0 行
```

对 175 条提交逐条在 `subject` 里搜 676 条记忆编码：**命中 0 条（0%）**。

**结论**：`link_commit_mentions` 的逻辑没错，但它的**前提**（提交正文提到记忆编码）
在这个项目里不成立。上一轮我说"接上线就有数据"，这个预期是错的。

### F2 · `files_changed` / `insertions` / `deletions` 是死字段

```
有 files_changed 的提交：0 / 175
```

`record_commit` 的 INSERT 语句里根本没有这三列。DDL 有、写入没有。

### F3 · `session_key` 在真相源里，投影表里没有

```
git_commit 表的列：      sha, repo_id, authored_at, committed_at, author_email,
                        author_name, subject, is_merge, files_changed, insertions,
                        deletions, branch_seen, content_root, event_id,
                        superseded_by, unreachable_since     ← 无 session_key
git.commit 事件 actor：  {kind, id, session_key}
带 session_key 的事件：  175 / 175            ← 全都有
```

### F4 · `session_actor` 的口径是不统一的

`code_index.session_actor` 的 121 个不同取值里混着四种东西：

```
dsh:session-61ee3576-3bea-...       会话键
codebuddy:c48fd810-f235-...          会话键
fsh_***（已打码：凭证前缀不留在文档里）  token 前缀
企业智能-视频AI                       项目/公民名
self:czhy-dev                        自报身份
```

填充率 552 / 676 = 81%。

### F5 · 「同会话」关联也走不通

```
提交侧会话 3 个；记忆侧会话 121 个；交集 1 个
```

**这条推翻了我自己的一个推断**：我看到 F3 就想"加 `session_key` 就能打开 `produced`"。
实测显示交集只有 1 个——加列能回答"这个提交是谁做的"，**但不能用来关联记忆**。

### F6 · 老库加列不会自动补，会报 `no such column`

`_GIT_SCHEMA` 被拼进 `fish_schema.SCHEMA`，而它是 `CREATE TABLE IF NOT EXISTS`——
**表已存在时一个列都不会加**。而 `fish_db.migrate()` 只管它自己那三张表 + 各种
`_ensure_*`，**git 表不在其中**。

现场实验（造一个没有 `session_key` 的老库，跑 `migrate()`）：

```
migrate 后列：…（无 session_key）
查询 session_key：**报错** no such column: session_key
```

### F7 · `rebuild_commit_projection` 只还原 7 / 16 列

现场实验（造一条完整投影行 → 清空 → 重建）：

```
重建前: author_name='Alice' is_merge=1 files_changed=7 branch_seen='main'
重建 1 行
重建后: author_name=None    is_merge=0 files_changed=None branch_seen=None
丢失: author_name / branch_seen / is_merge / files_changed
```

而且它读 `p.get("committed_at")`——**payload 里根本没有这个字段**（见 F9），
所以重建后 `committed_at` 是空字符串。

**「投影可从事件重建」这个承诺在 `git_commit` 上是不成立的**，而现有判据只验行数。

### F8 · `git_commit` / `git_obs` 只有展示用途

| 表 | 生产侧消费者 |
|---|---|
| `git_commit` | 4 处：去重检查、`git_repo_commits`、`git_link` 的 sha 校验、`fish.py:5813` |
| `git_obs` | 2 处：节流检查、`latest_obs`（给 `git_repo_status`） |

**没有一处是"用 git 数据影响 fish 的行为"。** 采了 621 次观测、175 条提交，
全部只用于展示。

### F9 · `record_commit` 的 payload 只有 5 个字段

```python
payload={"sha": sha, "repo_id": repo_id,
         "content_root": info["content_root"],
         "branch_seen": branch, "subject": info["subject"]}
```

投影写的 11 列里，`authored_at` / `committed_at` / `author_email` / `author_name` /
`is_merge` **都不在 payload 里**——所以它们原理上就无法从事件重建。

### F10 · 推送管线能装非记忆内容，但 `fish_push.py` 余量是 0

`situational` 候选用的 `code` 是**合成的**：

```python
code = f"activity:{shown}"          # 不是真的记忆编码
```

而 `_apply_push_gates` 只看 `score` / `kind`，不查 `code_index`。
所以 `git:<repo>` 这种合成码能过门。

但 `fish_push.py` 是 **1550 / 1550，余量 0**——加候选必须先腾空间。

## 二、由取证推出的三个判断

### 判断 1：**先修重建，再加列**

F7 说明投影重建本身就不完整。**在它修好之前加 `session_key` / `has_trailer`，
等于给一个会丢的投影再加两个会丢的列**——而且会让人以为"加了列就能用"。

所以顺序是：**重建完整性 → 加列 → 可见化 → 推送**。

### 判断 2：**`session_key` 的价值是「协作可见性」，不是「记忆关联」**

F5 已经证伪了"加列就能关联"。所以这项改动的定位必须写清：

- ✅ 能回答：这个提交是哪个会话做的
- ✅ 结合 `session_context.cwd` 还能答：在哪个工作空间做的
- ❌ **不能**回答：这个提交对应哪条记忆

如果定位写不清，下一个人（包括我）会重蹈 F5 的推断错误。

### 判断 3：**可见化（P0）的前提是「承认关联不上」，不是「造出一种关联」**

F1 的 0% 命中已经说明：五种关联路径（编码 / 同会话 / 改动文件 / 时间窗口 / 显式）
在真实数据上**没有一种能自动工作**。

所以 P0 不是"再修一种关联"，而是**让"关联不上"这件事本身可见**。
这是本轮最重要的一条。

## 三、实施计划（五个阶段，按依赖排序）

| 阶段 | 内容 | 文件 | 预计行数 | 余量 |
|---|---|---|---|---|
| **S0** | 修 `rebuild_commit_projection` 完整性 + payload 补字段 | `fish_git_store.py` | +28 | 40 ✅ |
| **S1** | 加 `session_key` / `has_trailer` 两列 + 老库迁移 | `fish_git_schema.py` / `fish.py` | +4 / +14 | 70 / 91 ✅ |
| **S2** | P0 可见化：healthcheck + `git_repo_commits` 回执 | `fish.py` / `mcp_server.py` | +14 / +10 | 91 / 无限制 ✅ |
| **S3** | P2-2 git 候选进推送（需先腾 `fish_push.py` 空间） | `fish_push.py` | +30 | **0 ❌** |
| **S4** | P1 `files_changed` 定性（DDL 注释标注"预留不采"） | `fish_git_schema.py` | +3 | 70 ✅ |

### S0 的细节

**payload 补齐**（新事件才完整；老事件改不了——事件是 append-only）：

```python
payload={"sha": sha, "repo_id": repo_id,
         "content_root": info["content_root"],
         "branch_seen": branch, "subject": info["subject"],
         # 2026-11-22（F9）：这五个字段原本不在 payload 里，
         # 于是 rebuild 原理上就还原不了它们。
         "authored_at": _iso(info["authored_at"]),
         "committed_at": _iso(info["committed_at"]),
         "author_email": info["author_email"],
         "author_name": info["author_name"],
         "is_merge": info["is_merge"],
         # 新增两列（S1）
         "has_trailer": ...}
```

**rebuild 改成读 payload + actor**：

```python
"SELECT event_id, payload, actor FROM events WHERE type='git.commit'"
```

`session_key` 从 `actor` 读——**历史事件也可以还原**（F3：175/175 都有）。

**老事件的缺失列如实为 NULL，不猜。** 这一点要写进 docstring——它是
「append-only 的固有约束」，不是 bug。

### S1 的细节

**两列：**

```sql
session_key  TEXT     -- 哪个会话提交的（从事件 actor 还原，历史可还原）
has_trailer  INTEGER  -- 提交正文有没有 Session: trailer（0/1/NULL=不知道）
```

**迁移放 `fish.py` 的 `migrate()`**（它已经 `import fish_git_store`，
且是"旧库升级"的唯一入口）。`fish_db` 不能 import `fish_git_store`——会成环（F6 旁证）。

### S2 的细节

**healthcheck 加一行**：

```
git 采集：3 仓库 / 175 提交 / 0 条关联（自动 0，显式 0）
⚠ 提交全部未关联到记忆——不是坏了，是关联的前提没成立
   想建立关联：`git_link` 工具显式断言（implemented_by / produced / revised_in）
```

**`git_repo_commits` 回执**：每条提交标「已关联 / 未关联」。
一次查出所有已关联的 sha（不能每条查一次）。

### S3 的细节

**候选形态**：

```python
{
  "code": f"git:{repo_id}",          # 合成码（F10 证明能过门）
  "kind": "situational",
  "title": f"{仓库名} 有 {n} 条提交，但 0 条关联到记忆",
  "reason": "提交在发生，记忆没跟上——这是 fish 的观测缺口，不是仓库的问题",
  "benefit": 0.5, "cost": 0.1,
}
```

**触发条件**（三条同时成立）：
1. 该仓库属当前项目（`project` 或 cwd 命中）
2. 近期（7 天）提交数 ≥ 阈值
3. 关联数 == 0

**节制**：`benefit` 给低值（0.5），让它永远排在有内容的候选后面。

### S4 的细节

`files_changed` / `insertions` / `deletions` 三列加 DDL 注释：

> 预留字段，当前**不采集**（`record_commit` 不写）。采它需要额外一次
> `git log --shortstat`，而即使采到也只能做"记忆正文提到这个文件"的弱关联——
> 收益不抵调用成本。要用之前先想清楚消费方是谁。

## 四、判据设计（每条都要能红 + 变异自证）

| # | 判据 | 变异体（去掉 → 必红） |
|---|---|---|
| J1 | rebuild 还原 `author_name` / `is_merge` / `branch_seen` / `committed_at` | 删掉 payload 里那几个字段 → 红 |
| J2 | rebuild 从 actor 还原 `session_key`（**历史事件也能**） | 改成只读 payload → 红 |
| J3 | 老库（无新列）跑 migrate 后能查 `session_key` | 去掉 migrate 那段 → 红 |
| J4 | `has_trailer` 有 trailer 时为 1、无则为 0 | 判断恒 False → 红 |
| J5 | healthcheck 在 `n_link == 0` 时输出告警行 | 去掉那条 if → 红 |
| J6 | `git_repo_commits` 标出未关联的提交 | 去掉标记 → 红 |
| J7 | git 候选：关联为 0 时才产生 | 去掉条件 → 红 |
| J8 | git 候选：有关联时不产生（**负对照**） | — |

**负对照是重点**（J8）：只验"该有时有"，不验"不该有时没有"，等于没验。

## 五、已知限制（如实写清，不假装解决）

| # | 限制 | 原因 |
|---|---|---|
| L1 | 老事件的 payload 缺字段，rebuild 后那几列为 NULL | append-only：事件不可改 |
| L2 | `has_trailer` 对历史 175 条提交都是 NULL | body 不存库，历史无从判断 |
| L3 | 加 `session_key` **不解决**记忆关联 | F5：交集只有 1 个 |
| L4 | 自动关联命中率仍然是 0% | F1：前提不成立；本方案不改变这一点 |
| L5 | git 候选是"观测缺口"不是"问题解决" | fish 能看见，但装不装 hook 不由 fish 决定 |

**L4 是这份方案最需要被记住的一条**：本方案**不提高自动关联的命中率**，
它做的是**让零命中这件事可见、可解释、可人工补**。
