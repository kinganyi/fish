### 🟠 A2 能力矩阵一处假否定：WorkBuddy 的「推送」判成未接

- **位置**：`fish_hosts.py:128`（`PUSH_HOOK_SCRIPT = "fish_push_hook.py"`）、`:1227-1228`（`push_hit = any(PUSH_HOOK_SCRIPT in cmd ...)`）、`:1429-1431`（渲染该 cap）。
- **证据（可复现）**：活接口 `workbuddy.capabilities.push = {"state":"no","label":"未接","evidence":"没有装推送采集器（fish_push_hook.py）"}`；但 WorkBuddy 的 PostToolUse 实际装的是 `fish_posttool_hook.py`，该文件 `:313 def maybe_push(req, host)`、`:426 maybe_push(req, host)` → **推送通道真实存在**。同一宿主的 `spec.collector` 还列着 `fish_push_hook.py`（`fish_hosts.py:285-286`），设置页据此显示"采集器 4 个"——两处自相矛盾。
- **影响**：设置页对 WorkBuddy 显示「推送 · 未接」，是**用户可见的错误判断**；一个专门用来"诚实报告能力"的层，在这一格上不诚实。
- **改法**：判 push 不看单一文件名，改为"该 command 指向的采集器是否具备 push 能力"（spec 声明 `pushes: bool` 或维护 `PUSH_CAPABLE_SCRIPTS`）；拿不准则降为 `unverified` 并写原因。同时 `collector` 要区分「声明」与「已装」。

### 🟠 A3 `configState` 五档只落三档，且占位符路径回归成「missing」

- **位置**：`fish_hosts.py:535-546`（`resolve_home` 判不到返回 `(None, reason)`）、`:1188-1216`（只有 missing/unreadable/ready）、`:549-557`（`home=None` 时 `{home}` 展开成空串再 `abspath`）。
- **证据（我做的变异）**：把 dsh 的 `home_env=None, home_default=r"C:\Users\<用户名>\.dsh"` 后 `detect()` 返回
  `configState=missing`、`configReason="配置不存在：I:\hooks.json"`、`home evidence.ok=null`。
  **它编出了一个不存在的路径**（`I:` 来自当前工作盘）。98 §6.2 的判据原文是："占位符路径未解析时必须是 `unreadable` + `reason=path_unresolved`，**不许**是 `missing`"。
- **现状**：当前所有 spec 的 `home_default` 都是 `~/xxx` 或 `None`，所以线上不触发；但 `C:\Users\<用户名>\...` 正是下一台机器的默认写法，一踩就是 §1.3a 那个假红的同款。
- **改法**：`home is None` 时直接 `config_state="unreadable"` + reason 用 `home_reason`（带 `path_unresolved` 标记），不要把空 home 拿去拼绝对路径；补一条变异（占位符 → 必须 `unreadable`）。
